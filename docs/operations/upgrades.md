# Оновлення й міграції

Сервіси Jane оновлюються незалежно один від одного: кожен сам оновлює схему свого сховища під час старту, а сумісність між сервісами тримають версіоновані контракти `/v1`. Сторінка описує, як сервіси мігрують свої дані, як оновити сервіс у dev-стеку і що робити, якщо оновлення не вдалося.

## Як сервіси оновлюють схеми

Окремої команди міграції немає: сервіс створює й оновлює свої таблиці під час кожного старту, до того як почне приймати запити. Міграції ідемпотентні — повторний старт на актуальній схемі нічого не змінює. Зворотних міграцій немає в жодному сервісі.

| Сервіс | Сховище | Механізм |
|---|---|---|
| Orchestrator | PostgreSQL `jane_orchestrator` | нумеровані міграції (зараз 7) у таблиці `schema_migrations`; транзакція під `pg_advisory_xact_lock`; у журнал пишеться `schema migrated` з номером версії |
| Registry | PostgreSQL `jane_registry` | `CREATE … IF NOT EXISTS` під `pg_advisory_xact_lock(hashtext('jane_registry_schema'))`; версія в `registry_schema_version` (зараз 1) |
| LLM gateway | PostgreSQL `jane_llm`, схема `llm` | `CREATE SCHEMA/TABLE IF NOT EXISTS` під advisory lock |
| Assistant, Handler Runtime | PostgreSQL `jane_assistant`, `jane_handler_runtime` | спільна міграція `jane_kit.stores.postgres.migrate`: `CREATE … IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS` під advisory lock |
| Web Collector | SQLite `state.db` | схема створюється під час відкриття; відсутні колонки додаються на місці |
| Telegram Collector | SQLite `state.db` | `PRAGMA user_version` (зараз 1); файл старішої версії оновлюється один раз; файл новішої версії, ніж код, — помилка старту `StateFileTooNew` |
| Storage | цільові сховища | адаптер викликає ідемпотентний `ensure_schema` під час першого відкриття підключення в процесі (PostgreSQL — таблиці `entities`, `entity_history`, `deliveries`, `objects` з префіксом під advisory lock; SQL Server — під `sp_getapplock`); власної бази стану Storage не має |

Ролі й бази PostgreSQL створює не сервіс, а провізіонер стеку (`infra/postgres/provision.sql`) — [infra/README.md](../../infra/README.md#postgresql-бази-й-ролі-сервісів).

Перевірено 2026-10-11 на стеку `jane-doc-ops`: перший старт Orchestrator записав у журнал `schema migrated` для версій 1–7; перестворений контейнер на тій самій базі не записав жодного рядка `schema migrated` і став `healthy`.

## Сумісність між сервісами

- **Контракти.** API версіонуються шляхом (`/v1`). Зміни в `contracts/` перевіряються на зворотну сумісність: `just contracts-compat [ref]` і job `contracts-compat` у CI (власний компаратор і `oasdiff`). Несумісна зміна вимагає нової версії API.
- **Пакети обробників.** Етап завдання закріплює версію пакета й дайджест архіву; версії в Registry незмінні. Оновлення сервісу не змінює коду, який виконується в завданнях.
- **Образ пісочниці.** Профіль виконання `python-extractor@1` відповідає образу з `JANE_HANDLER_RUNTIME_PROFILE_IMAGES`. В іншому середовищі, ніж dev, закріплюйте образ дайджестом (`repo@sha256:…`), щоб оновлення не змінило середовища виконання екстракторів.

## Процедура оновлення сервісу

Приклад для Orchestrator у dev-стеку; для інших сервісів кроки ті самі, крім кроку 2.

![Процес оновлення сервісу](../diagrams/operations/service-upgrade.light.png#gh-light-mode-only)
![Процес оновлення сервісу](../diagrams/operations/service-upgrade.dark.png#gh-dark-mode-only)

Зображення для теми: [світле](../diagrams/operations/service-upgrade.light.png), [темне](../diagrams/operations/service-upgrade.dark.png); джерело — [service-upgrade.drawio](../diagrams/operations/service-upgrade.drawio).

1. Зробіть резервну копію даних сервісу — [резервування](backup-restore.md). Без неї відкат після міграції неможливий.
2. Для Orchestrator зупиніть розклади й воркери, щоб під час оновлення не стартували нові запуски — [режим без планувальника](running.md#orchestrator-без-планувальника-й-воркерів).
3. Зберіть і перезапустіть сервіс із новим кодом. `just up` перезбирає образ і перестворює контейнер:

   ```powershell
   just up orchestrator
   ```

4. Перевірте журнал старту: нові міграції (`schema migrated`), помилки конфігурації, проігноровані шляхи профілю лімітів:

   ```powershell
   just logs orchestrator --tail 100
   ```

5. Перевірте health і версію:

   ```powershell
   curl.exe -s http://127.0.0.1:<порт>/v1/health
   ```

   Очікуваний результат — `"status":"ok"`. `GET /v1/info` (з токеном) показує `version`.

6. Поверніть звичайний режим Orchestrator: приберіть змінні `JANE_ORCHESTRATOR_SCHEDULER_ENABLED` і `JANE_ORCHESTRATOR_RUN_WORKERS` із середовища й виконайте `just up orchestrator --no-build`.

Незавершена робота після перезапуску продовжується: елементи черги Orchestrator з простроченою орендою (lease) бере інший воркер і повторює виклик із тим самим `delivery_key`, тож виконавець поверне збережений результат замість повторної дії — [масштабування](scaling.md#оренда-lease-і-повтори).

## Кілька екземплярів під час оновлення

- Міграції PostgreSQL виконуються під advisory lock, тому кілька екземплярів можуть стартувати одночасно: міграцію виконує перший, решта бачать актуальну схему.
- Міграції лише додають таблиці й колонки. Старий код зазвичай працює з новою схемою, але це не гарантовано й не перевіряється тестами: оновлюйте всі екземпляри сервісу разом.
- Екземпляри колектора, що ділять один каталог стану SQLite, треба оновлювати одночасно: Telegram Collector зі старим кодом не відкриє файл новішої версії (`StateFileTooNew`).

## Відкат

Зворотних міграцій немає. Відкат після оновлення зі зміною схеми:

1. зупиніть сервіс;
2. відновіть дані сервісу з резервної копії, зробленої до оновлення — [відновлення](backup-restore.md#відновлення);
3. запустіть попередню версію образу.

Якщо оновлення не змінювало схему (у журналі немає нових `schema migrated` для Orchestrator), достатньо запустити попередню версію образу. Відкат у dev-стеку з перевіркою не виконувався.
