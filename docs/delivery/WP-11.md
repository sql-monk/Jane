# WP-11. Асистент джерел

**Гілка:** `wp/11-assistant` · **Ревізія:** останній коміт гілки (звіт комітиться останнім; перевірки рев'ю 1 — на `f4807a2`, первинні — на `1d73a08`) · **База:** `7d3585d` (main після rebase у рев'ю 1; старт від `ef5a879`) · **Стан:** review

## Результат

Сервіс `services/assistant/` (створено `just new-service assistant`) реалізує весь `contracts/openapi/assistant.v1.yaml`:
`startOnboarding`, `getOnboardingSession`, `selectCandidate`, `acceptProposal`, `startImprovement`, `analyzeUnknownMaterial`,
`/v1/jobs/*`, `/v1/health`, `/v1/info`, `/metrics`.

| Модуль | Що робить |
|---|---|
| [`app.py`](../../services/assistant/src/jane_assistant/app.py) | API, строгі моделі запитів, 202 + Job, `Idempotency-Key`, `Dependencies` (транспорти/пошук для тестів) |
| [`onboarding.py`](../../services/assistant/src/jane_assistant/onboarding.py) | стан сесії, пошук і уточнення, аналіз, план екстракторів (bind / fork+adapt / create), варіанти, прийняття, автоактивація |
| [`sampling.py`](../../services/assistant/src/jane_assistant/sampling.py) | адаптивна вибірка: збір колектора, round-robin за «формами» URL, класифікація, впевненість = покриття Гуда–Тьюрінга × впевненість моделі, зупинка за порогом/межею/бюджетом |
| [`improvement.py`](../../services/assistant/src/jane_assistant/improvement.py) | групування проблем, спроби моделі, старі+нові тести, регресії на успішних прикладах, тести з параметрами кожної прив'язки, форк, `proposal_only`, погодження, `auto_activate` з відкатом при частковій відмові, стан групи проблем |
| [`unknown.py`](../../services/assistant/src/jane_assistant/unknown.py) | невідомі матеріали: 403 без виклику LLM, якщо прапорець вимкнено; інакше класифікація й пропозиція |
| [`guards.py`](../../services/assistant/src/jane_assistant/guards.py) | захист від виходу моделі: правила лише в межах хостів джерела, без `llm_explore`/`owner_policy`/лімітів у правилах; статична перевірка коду; JSON Schema контрактів |
| [`llm.py`](../../services/assistant/src/jane_assistant/llm.py), [`prompts.py`](../../services/assistant/src/jane_assistant/prompts.py) | довірені інструкції окремо від недовірених `data`; бюджет job, обрізання даних, локальна перевірка виходу |
| [`packages.py`](../../services/assistant/src/jane_assistant/packages.py), [`testing.py`](../../services/assistant/src/jane_assistant/testing.py) | маніфест будує асистент; тести пакета як файли (`origin: problem_sample`); чернетки в runtime inline-архівом |
| [`search.py`](../../services/assistant/src/jane_assistant/search.py) | URL/@channel напряму; провайдери `static` (каталог) і `http_json`; фейк у тестах |
| [`clients.py`](../../services/assistant/src/jane_assistant/clients.py) | клієнти сусідів строго за їхніми контрактами, детерміновані ключі ідемпотентності |
| [`settings.py`](../../services/assistant/src/jane_assistant/settings.py) | налаштування й модель лімітів (контрактні `llm.*`, `transfer.inline_max_bytes` + внутрішні групи) |

Тести ([`services/assistant/tests`](../../services/assistant/tests)): фейки сусідів прив'язані до контрактів
([`assistant_fakes/base.py`](../../services/assistant/tests/assistant_fakes/base.py)) — кожен запит асистента перевіряється
за схемою запиту сусіда (обов'язкові заголовки/query, тіло), кожна відповідь фейка — за документованим статусом і схемою;
будь-яке порушення валить тест. Асистент не мокається: сценарії йдуть через справжній застосунок (`TestClient`) і,
окремо, через окремий процес `python -m jane_assistant` зі справжнім HTTP до фейків на uvicorn. Детермінований фейковий
LLM — свій (`assistant_fakes/llm.py`, диспетчеризація за `output_schema.title`), від WP-10 не залежить; вміє «піддаватись
ін'єкції» (позадоменні URL, `llm_explore`, заборонені імпорти, несумісні зміни). Тести пакетів справді виконуються
мінімальним замінником runtime (`assistant_fakes/runtime.py`), тож pass/fail у сценаріях реальні.

Не зроблено / свідомо обмежено: читання blob без `download_url` з `s3://` (колектор просимо віддавати вибірку `content_delivery: inline`).

## Доповнення WP-11b: вибірка під час підключення джерела лише за назвою

**Гілка:** `wp/11b-adaptive-sampling`, база `main` `38766a7` · **Стан:** review, очікує незалежного рев'ю.

**Причина.** `sample_source` після кожного long-poll одразу класифікував навіть один матеріал і перевіряв
впевненість. Якщо колектор спочатку віддавав два товари, оцінка покриття Гуда–Тьюрінга при
`min_examples_per_type=2` ставала 1.0, і асистент скасовував збір до появи категорій та інших типів.
Це відтворено в S-M2-06 WP-13 (`test_s_m2_06_name_only_sample_distinguishes_material_types`): 2 матеріали,
1 тип, confidence 0.95, далі немає негативного прикладу для тестів згенерованого екстрактора.

**Виправлення.** Поки збір триває, впевненість вважається достатньою лише після класифікації
`onboarding.min_distinct_types` різних типів (типово 2). Якщо колектор вичерпав потік, використовується
вся доступна вибірка. Ліміт має типове значення й задається через конфігурацію; кількість матеріалів
не фіксується наперед. Межі `max_onboarding_samples`, бюджету LLM і кількості порожніх опитувань збережено.
README асистента пояснює правило й типове значення. Контракти не змінювались.

**Регресія.** Контрактний замінник колектора повертає по одному матеріалу: вісім товарів першими,
потім категорії й інші сторінки. Справжній асистент продовжує вибірку, розрізняє щонайменше два типи,
подає варіанти, і згенерований екстрактор проходить тести. Другий тест обмежує вибірку чотирма
товарами: попри високу оцінку покриття результат — `insufficient_sample`, а не хибна достатність.
Замінено лише сусідні сервіси за контрактами; реальний Web Collector і Linux не перевірялися в цьому
доповненні. Після злиття слід повторити S-M2-06 із WP-13 і прибрати його строгий `xfail`, якщо він перейде
в `XPASS`.

## Відомі обмеження
- Без `JANE_ASSISTANT_STATE_DSN` стан у пам'яті — лише одиночний запуск і тести. Job, що виконувався на убитому екземплярі, не відновлюється, а завершується `failed` після `limits.state.job_lease_ms` (сесію можна почати знову). Реалізації PostgreSQL-сховищ job/ідемпотентності повторюють підхід handler-runtime (WP-06) — кандидат на перенесення в jane-kit (див. запити).
- Поріг впевненості `onboarding.min_confidence` і пороги bind/fork — внутрішні ліміти (у `limits.schema.json` їх немає), тож у `/v1/info` вони не видні.
- `proposal_only` не має куди віддати сам код пропозиції: `ImprovementResult` містить лише `version` (неопубліковану) і звіти тестів (див. запити).
- Оцінка охоплення — нижня межа з кількості URL, знайдених під час вибірки, × частка вибірки, що відповідає розділам варіанта; вартість LLM на запуск = 0 (згенеровані екстрактори LLM не викликають).
- Статична перевірка коду — рання відмова, не пісочниця; справжня ізоляція — WP-06.
- Blob-вміст читається лише через `download_url` або `file://`; `s3://` без `download_url` → `not_implemented` (вибірку асистент просить inline).
- Повний набір тестів асистента ~1–2 хв (валідація кожного запиту/відповіді за великими схемами контрактів).

## Неперевірені інтеграції
- Усі сусіди — лише контрактні фейки (llm, registry, collector web/telegram, handler-runtime, orchestrator, storage). Не перевірено на реальних сервісах WP-02/04/05/06/09/10/07.
- Реальна LLM і реальний пошуковий провайдер (`http_json`) — не перевірено на реальному сервісі (провайдер `http_json` — лише на `httpx.MockTransport`).
- Формат результату SDK екстракторів (WP-06) взято з чернетки скілу `jane-handler-package`; інструкції генерації коду можуть потребувати уточнення після WP-06.

## Додаткова робота WP-11c: різноманітність вибірки за назвою джерела

Причина регресії S-M2-06: Good–Turing оцінював тільки класифіковані сторінки, а
`min_distinct_types=2` дозволяв завершення на 17 товарах і одній статті, хоча колектор іще не
віддав категорії та інші форми URL. Розподіл за порядком обходу порушує припущення про випадкову
вибірку; висока локальна оцінка не доводить, що наступні матеріали не мають нових типів.

Після першої класифікації асистент продовжує читати потік колектора до `end_of_stream`, окремо
класифікує раніше не представлені форми URL, а потім добирає приклади з уже відомих форм лише до
порога впевненості. Збір має налаштовану межу `max_onboarding_samples × fetch_ratio`, число
класифікованих матеріалів — `max_onboarding_samples`, очікування порожнього потоку обмежують
`max_empty_polls` і `collection_poll_wait_ms` для окремого запиту; жодної фіксованої кількості
сторінок у коді не додано.
Якщо потік не завершується до межі очікування, повертається `insufficient_sample`, навіть за
високого Good–Turing. Пізній тип у тій самій формі URL теоретично може лишитися невиявленим;
повної гарантії без класифікації всіх матеріалів немає. Для великих джерел колектор може дійти до
налаштованої межі раніше, ніж вибірка стане достатньою — це свідомий компроміс для ТЗ §8.

Контрактні регресії: довгий початковий ряд товарів зі статтею, потім категорії, список новин і
«інше»; потік одного типу, що впирається у бюджет; потік із високою впевненістю, який не завершується.
В усіх сусіди замінені тільки контрактними фейками; реальний асистент працює без мока.

активації та сутностей. Локальні контрактні тести самі по собі критерій WP-13 не закривають.
