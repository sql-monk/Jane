# L2: ліміти хоста між Docker-репліками

`test_shared_host_replicas.py` піднімає окремий compose-проєкт із двома справжніми Web Collector та testsite.
`compose.host-limits.yaml` монтує той самий проєктний том до `STATE_DIR` обох реплік; тест перевіряє імена
контейнерів, різні Docker PID, спільний том і фактичні `collector.shared_host_*` у середовищі контейнерів.
Оркестратор і зовнішні сервіси для цього сценарію не потрібні.

Обгортка `jane_e2e/host_probe.py` викликає справжній `TestSiteHandler`, записуючи час початку/завершення
позначених запитів. Health-check та керування пробою не рахуються; `robots.txt` колекторів рахується.
Всі запити й відповіді колектора перевіряє контрактний клієнт `collector.v1`.

1. Паралельність: дві колекції по 8 товарів, `max_parallel_fetches_per_host=1`; testsite тримає товарні
   відповіді 0,4 с. Початки обох колекцій перекриваються в часі, найбільша сукупна кількість відкритих
   запитів дорівнює 1.
2. Інтервал: дві колекції на тому самому хості з миттєвими відповідями й `min_delay_ms_per_host=250`.
   Перевіряються кожен інтервал між стартами і повна тривалість послідовності; допуск 50 мс враховує
   доставку від дозволу лімітера до потоку testsite. Тривалість усієї послідовності допускає лише один такий
   зсув, тому допуск не накопичується для кожного запиту.
3. TTL: одна репліка утримує товарний HTTP-запит довше TTL (8 × 4/3 с), друга чекає вільного хоста.
   Поки власник живий, його поновлення тримає слот; після `docker kill` його від'єднаний запит testsite
   відпускається, а слот у мертвому процесі ніхто не звільняє. Наступний запит живої репліки стартує не
   пізніше TTL + `shared_host_poll_ms` + 0,5 с після завершення kill. Початки запитів і маркери kill
   вимірюються одним монотонним годинником testsite; допуск враховує HTTP-доставку й планування, а не
   очікування TTL повторно. Виміряні значення друкуються в stdout.

Ліміти сценарію конфігуруються через середовище (нижче типові значення):

| Змінна | Значення | Призначення |
|---|---:|---|
| `JANE_E2E_SHARED_HOST_TTL_SECONDS` | 8 | `collector.shared_host_ttl_seconds` |
| `JANE_E2E_SHARED_HOST_POLL_MS` | 50 | `collector.shared_host_poll_ms` |
| `JANE_E2E_SHARED_HOST_BUSY_TIMEOUT_MS` | 500 | Очікування SQLite; має виконуватись правило TTL × 2/3 > busy timeout |
| `JANE_E2E_SHARED_HOST_WAIT_S` | 90 | Бюджет опитування / HTTP-запиту |
| `JANE_E2E_SHARED_HOST_PROBE_POLL_S` | 0,05 | Частота опитування testsite |
| `JANE_E2E_SHARED_HOST_TIMING_SLACK_S` | 0,05 | Допуск вимірювання інтервалу |
| `JANE_E2E_SHARED_HOST_TTL_SLACK_S` | 0,5 | Допуск доставки після TTL |
| `JANE_E2E_SHARED_HOST_INTERVAL_MS` | 250 | Інтервал другої фази |
| `JANE_E2E_SHARED_HOST_HOLD_S` | 0,4 | Утримання товарних відповідей першої фази |
| `JANE_E2E_SHARED_HOST_PAGES` | 8 | Кількість товарів на колекцію, щонайменше 3 |
| `JANE_E2E_SHARED_HOST_PACE_PARALLEL` | 4 | Пул збору й паралельність фази інтервалу |
| `JANE_E2E_SHARED_HOST_FAST_RPS` | 1000 | Темп, який не обмежує фазу паралельності |

Паралельність 1 і 4 — точки випробування, які передаються контрактним `limits` запиту; темп 1000 запитів/с
вимикає вплив сервісного типового темпу в фазі паралельності. Політика `respect_crawl_delay=false` потрібна,
щоб окремо перевіряти налаштований інтервал. Ці значення не змінюють типові ліміти production.

Один локальний прогін (PowerShell; власний проєкт, обов'язкове автоматичне `down -v` навіть після падіння):

```powershell
$env:JANE_E2E_PROJECT = 'jane-wp22c-local'
$env:JANE_E2E_REQUIRED = '1'
uv run --all-packages pytest tests/e2e/test_shared_host_replicas.py -m e2e -v -s
```

Після локального прогону решту повних перевірок виконує CI.
