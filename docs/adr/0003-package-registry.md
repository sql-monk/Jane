# ADR-0003. Репозиторій пакетів обробників

- **Статус:** прийнято, діє. Відповідає на відкрите питання ТЗ §13.2.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

ТЗ §13.2 залишає відкритим вибір технології зберігання й розповсюдження пакетів обробників і правил колекторів. Вимоги: версії, незмінні артефакти, залежності, тести, походження, форки, контроль доступу й автономне використання пакета без Orchestrator (ТЗ §7, §13.2). Етап завдання має посилатися на конкретну версію (ТЗ §7), а форк не має змінюватися після оновлення батька (ТЗ §7, критерій 7).

## Варіанти

1. **Окремий сервіс Registry: метадані в PostgreSQL, архіви версій в S3-сумісному або файловому сховищі за SHA-256.**
2. OCI-реєстр (артефакти OCI) — готове розповсюдження й підписи, але статуси, звіти тестів, форки й перенесення змін довелося б будувати поруч.
3. Git-репозиторій на пакет — історія й diff «безкоштовно», але незмінність версій, контроль доступу й автономне завантаження одного архіву складніші.
4. PyPI-сумісний індекс — підходить лише для Python-коду, не для правил колекторів і LLM-пакетів.
5. Таблиця в базі Orchestrator — порушує автономність ([ADR-0002](0002-autonomy-and-data-ownership.md)).

## Рішення

Обрано варіант 1 — сервіс Registry з API `registry.v1` ([registry.v1.yaml](../../contracts/openapi/registry.v1.yaml)).

- **Пакет** — zip-архів із маніфестом `jane-package.json`, схемами й тестами. Формат — [handler-packages.md](../../contracts/docs/handler-packages.md). Типи: екстрактор, збереження, LLM, перетворення, правила колектора.
- **Канонічний архів і дайджест.** Registry перепаковує архів канонічно (відсортовані шляхи, фіксовані час і права) і рахує SHA-256. Етап завдання закріплює `package_id`, `version` і `digest`; виконавець перевіряє дайджест завантаженого архіву (`digest_mismatch`).
- **Зберігання.** Метадані — власна база PostgreSQL (`jane_registry`); архіви — S3/MinIO або файлова система за ключем `sha256/<hex>` (content-addressed), бакет `jane-registry`.
- **Незмінні версії.** Повторна публікація версії — `409 version_exists`. Статуси: `draft`, `approved`, `rejected`, `deprecated`, `yanked`.
- **Форк** — новий пакет із `fork_of` (батько й вихідна версія). Зміни батька форк не отримує; є порівняння (`/diff`), перегляд оновлень батька (`/upstream`) і перенесення змін лише явною командою (`/upstream-ports`, трибічне злиття, `upstream_conflict` при конфлікті).
- **Залежності** пакета обмежені профілем виконання Handler Runtime (`python-extractor@1`); Registry перевіряє їх за профілем, опублікованим runtime (`dependency_not_allowed`).
- **Безпека.** Registry сканує файли пакета на секрети (`secret_detected`); scopes `registry:read`, `registry:write`, `registry:approve`.
- **Автономність.** Архів версії завантажується окремо (`GET …/archive`, ETag — дайджест); пакет можна виконати з локального архіву без Registry.

## Наслідки

- Будь-який пакет — екстрактор, збереження, LLM, правила колектора — версіонується, тестується й форкається одним механізмом (ТЗ §7, критерій 9).
- Відтворюваність: завдання виконує саме той архів, дайджест якого закріплено.
- Registry потребує PostgreSQL і S3-сумісного сховища; для локальних дослідів є режими `JANE_REGISTRY_DB=memory` і `JANE_REGISTRY_BLOB=filesystem`.
- Резервування Registry охоплює і базу, і сховище архівів ([резервування](../operations/backup-restore.md)).
- Затвердження версій, створених LLM: ключ Assistant має `registry:approve` з атрибутом `actor: llm`, а Assistant затверджує версії в режимі автоматичної активації після перевірок. Публікацію від імені LLM Registry блокує, якщо в пакеті заборонено автоматичні зміни (`auto_changes_allowed=false`) — [ADR-0010](0010-llm-in-assistant.md).
- Розбіжність із ТЗ: текст ТЗ §13.2 досі описує вибір технології як відкритий, хоча реалізація відповідає на нього цим рішенням.
