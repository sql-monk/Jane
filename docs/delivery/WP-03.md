# WP-03. Web Collector: стратегії пошуку

**Гілка:** `wp/03-web-collector-discovery` · **Ревізія реалізації:** `534bf17` · **База:** `cba8db4` · **Стан:** blocked (потрібні зміни контракту WP-00 і ядра WP-02 для POST/JSON-матеріалів та правдивої валідації)

## Результат

Реалізовано пакет `services/web-collector/strategies/discovery/` з п'ятьма стратегіями: `sitemap` (index, gzip, текстовий sitemap), `feed` (RSS, RDF, Atom, autodiscovery), `listing` (категорії, пагінація, пошук), `url_template` та `api_feed` (JSONPath і чотири режими пагінації). Пакет експортує `STRATEGIES` для реєстру ядра WP-02. Мережеві звернення й кандидати проходять через контракт `DiscoveryContext`; окремої БД або залежності від оркестратора немає. Опис конфігурації, лімітів, прикладу виклику й обмежень — у [README](../../services/web-collector/strategies/discovery/README.md).

Тести використовують справжній testsite WP-01 по HTTP і справжнє ядро WP-02, включно з kill процесу та відновленням на тому самому стані. Тести розбору перевіряють gzip-бомбу, XXE, JSONPath і ворожі/обрізані документи.

## Конфігурація й ліміти

| Параметр | Типове значення | Де задається |
|---|---|---|
| `crawl.max_depth` | 5 | ефективні `ctx.limits` (platform → rules → request → strategy), типовий профіль ядра |
| `crawl.max_links_per_page` | 2000 | `ctx.limits`; обрізає записи sitemap/feed/API |
| `crawl.max_material_bytes` | 10 MiB | `ctx.limits`; розмір навігаційного документа і розпакованого gzip |
| `crawl.max_seed_urls` | 100000 | `ctx.limits`; шаблонні URL |
| `crawl.max_pages_per_run`, `max_bytes_per_run`, `max_frontier_size` | 5000 / 2 GiB / 100000 | `ctx.limits`; бюджети ядра |
| `strategies[].limits` | успадкувати | правила колектора; звужує ліміти окремої стратегії |

## Відомі обмеження

- `api_feed.method=POST` і `emit_items_as_materials=true` дозволені схемою, але нинішній `DiscoveryContext` уміє лише GET і повернення URL. Збір із цими параметрами явно завершується помилкою. `POST /v1/rules/validations` перевіряє лише тип стратегії, тому зараз помилково відповідає `valid: true, supported: true` для обох варіантів. Тест `test_schema_valid_api_feed_options_need_core_support` фіксує цю розбіжність на реальному API й не видає частковий результат за успішний.
- `use_lastmod_for_revisit` передає `lastmod` у кандидата, але ядро WP-02 поки не використовує його для рішення про повторне відвідування.
- `listing` в `incremental`-зборі може не побачити нові елементи вже відомої сторінки, якщо ядро пропускає її за `revisit.mode=never` або повертає 304; також раніше отриману іншою стратегією сторінку ядро не передає повторно `on_fetched`.
- `llm_explore` не виконується колектором згідно з ADR-0010.

## Неперевірені інтеграції

Testsite і ядро колектора перевірені локально як реальні компоненти. Роботу з зовнішніми сайтами/API, Docker-розгортання і PostgreSQL у цьому WP не перевірено на реальному сервісі.

## Виправлення після рев'ю 1

1. Прибрано числові `FALLBACK_LIMITS` із `_common.py`: `limit()` бере значення тільки з ефективних `ctx.limits` і явно відхиляє відсутнє або нечислове. Ядро створює `StrategyContext(..., to_contract(strat_limits))`, тому в нормальному зборі потрібні значення наявні. Unit-тест перевіряє відсутнє й `bool` замість `int`; README більше не обіцяє локальний fallback.
2. Перевірено межу власності для POST і JSON-матеріалів. У `contracts/python/src/jane_contracts/discovery.py` протокол `fetch(url, *, kind, conditional)` не має `method` або `body`; `DiscoveredUrl` не переносить вміст. У `services/web-collector/src/jane_web_collector/crawler.py` ядро реалізує саме цей GET-виклик і самостійно створює Material. У `rules.py` валідація перевіряє лише підтримку типу. Зміна лише в WP-03 не може виконати ці опції, не порушивши правило `ctx.fetch` та власність шляхів WP-00/02. Додано інтеграційний тест обох schema-valid варіантів: він перевіряє `valid: true, supported: true` і явну помилку збору. Конкретні зміни для інших власників перелічено вище.
