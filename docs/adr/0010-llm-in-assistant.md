# ADR-0010. LLM в Assistant і як етап завдання

- **Статус:** прийнято, діє.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

LLM використовується у двох сценаріях: як обробник у ланцюжку й як засіб створення та вдосконалення правил колекторів і екстракторів (ТЗ §8–9). Дослідження нового джерела триває в межах бюджету до достатньої впевненості (ТЗ §8). Невідомі сторінки передаються LLM лише за явним налаштуванням (ТЗ §8, §13.1 п. 3). Вміст сайтів — дані, а не інструкції (ТЗ §11). Готові екстрактори мають працювати без LLM (ТЗ §8). Колектор має лишатися автономним і детермінованим.

## Варіанти

1. **Окремі ролі: LLM gateway — єдина точка викликів моделей з бюджетами (і обробник етапу); Assistant — координатор підключення джерел і вдосконалення, який використовує колектор, Handler Runtime і Registry через їхні API.**
2. Стратегія `llm_explore` усередині колектора — колектор залежав би від LLM і Assistant, а його поведінка стала б недетермінованою.
3. Прямі виклики провайдера з кожного сервісу — розпорошені ключі, немає спільного обліку витрат і бюджетів.

## Рішення

Обрано варіант 1.

- **LLM gateway** (`llm.v1`, а також `handler.v1` для LLM-пакетів як етапів) — провайдери (`anthropic`, детермінований `fake`), псевдоніми моделей, бюджети ієрархії платформа → джерело → завдання з резервуванням перед викликом (`429 budget_exhausted`), облік витрат, ідемпотентність без повторного списання. Ключі провайдерів — лише через `secret_refs` ([ADR-0007](0007-secrets-and-connections.md)).
- **Assistant** (`assistant.v1`):
  - сесії підключення джерела: пошук кандидатів за назвою, адаптивна вибірка сторінок через `collector.v1`, кілька варіантів правил збору з охопленням, вартістю й ризиками, генерація або підбір екстрактора, тести в Handler Runtime, публікація в Registry, створення джерела й завдання в Orchestrator;
  - запуски вдосконалення: проблемні приклади → нова версія → тести на старих і нових прикладах для кожної прив'язки → активація за політикою;
  - обробка невідомих матеріалів, якщо в джерелі ввімкнено `forward_unknown_to_llm`; інакше — відмова `access_denied_by_policy` без виклику LLM.
- **Політика активації** — `change_policy.llm_versions` джерела: `manual_approval` (типово), `auto_after_checks`, `forbidden`; пакет може заборонити автоматичні зміни (`auto_changes_allowed=false`) — тоді Registry не приймає публікацію від імені LLM.
- **Стратегія `llm_explore`** лишається в схемі правил колектора як зарезервована: Web Collector її не виконує й відхиляє збір з `unsupported_strategy`. Дослідження джерела — частина підключення в Assistant, результат — детерміновані стратегії.
- **Вміст як дані.** LLM gateway передає інструкції лише в системному каналі, а дані — між розмежувачами з випадковим nonce; Assistant додає до кожного промпту інструкцію про недовірені дані й перевіряє вихід моделі перед застосуванням: правила (`robots` лише `respect`, без `llm_explore`, хости лише джерела, валідація схемою), код (перевірка імпортів AST), маніфести (схема).
- **Бюджет Assistant** на запуск — типово 2 USD; кожен виклик несе бюджет і `run_id`, запуск зупиняється при вичерпанні.

## Наслідки

- Колектори й готові екстрактори працюють без LLM; LLM потрібен лише Assistant і LLM-етапам.
- Assistant залежить від LLM gateway, Registry, колектора й Handler Runtime; без них відповідні функції повертають `upstream_unavailable`. Orchestrator потрібен лише для створення джерел і завдань та автоматичної активації.
- Ключ Assistant має `registry:approve` з `actor: llm`: у режимі `auto_after_checks` Assistant затверджує перевірені версії сам; захист від небажаних змін — політика джерела й прапорець пакета.
- Наскрізні сценарії використовують провайдера `fake` як замінника зовнішньої LLM; з реальним провайдером Anthropic сценарії приймання не виконувалися ([приймання](../acceptance/README.md)).
