# Документація Jane

Створюй документацію, з якої читач може зрозуміти модуль, запустити його та знайти потрібний контракт або публічний член.

## Джерела та межі роботи

- [DOCUMENTATION_REQUIREMENTS.md](../../../DOCUMENTATION_REQUIREMENTS.md) — вимоги до змісту та стилю.
- [TECHNICAL_SPECIFICATION.md](../../../TECHNICAL_SPECIFICATION.md) — джерело вимог до системи; код, контракти й конфігурація — джерела фактів про реалізацію.

Прочитай відповідні джерела перед роботою. Для конкретного WP застосовуй також `jane-wp`. Працюй у доручених шляхах; редагування документа не запускає весь план, архівування або зміну сервісів. Вимоги та цей skill зберігаються як нормативні артефакти. Старі тексти й діаграми не використовуй як основу нового змісту.

## Структура сторінки

- Один заголовок першого рівня. Починай із призначення й практичного результату, далі використовуй послідовні рівні заголовків другого та третього рівня.
- Для довгої сторінки додай зміст зі звичайними Markdown-посиланнями на заголовки. Не вставляй HTML-якорі; перевір утворення якорів, особливо після перейменування або дублювання заголовків.
- Пиши короткими розділами українською, з єдиними назвами понять. Давай посилання на потрібний модуль, сценарій, тип або код у місці використання.
- Для каталогів і порівнянь використовуй компактні таблиці: назва, тип, коротке призначення, залежності або посилання — за потребою сторінки. Не розтягуй таблицю великими абзацами.
- Для інструкції покажи передумови, кроки, команди, очікуваний результат і діагностику. Для довідника спочатку покажи сигнатуру й призначення, потім деталі. Не копіюй усі розділи README на кожну сторінку.
- Залишай порожні рядки перед списками, таблицями й блоками коду. Використовуй чистий Markdown без сирого HTML, декоративних бейджів і службових пояснень про те, чим документ «не є».

## Код і приклади

Кожен fenced block має мову, що відповідає його вмісту:

| Вміст | Мова блоку |
|---|---|
| Прості команди uv, just, Docker у середовищі Jane | `powershell` |
| Команди зі специфічним синтаксисом Bash | `bash`; явно зазнач Linux/Bash |
| Код | `python`, `typescript`, `javascript`, `sql` або відповідна мова |
| Дані та конфігурація | `json`, `yaml`, `toml`, `ini` або відповідний формат |
| XML джерела Draw.io, якщо потрібен уривок | `xml`; сама схема — PNG з посиланням на `.drawio` |
| Дерево каталогів або буквальний вивід | `text` |

Не залишай блоки без мови й не позначай виконуваний код як `text`. Підсвічування не робить платформоспецифічну команду кросплатформною: спільні команди мають справді працювати на Windows і Linux, а відмінності описуються окремо.

Приклади мають містити актуальні аргументи, робочу директорію, необхідну конфігурацію та очікуваний результат. Не вигадуй API-поля, значення за замовчуванням чи вивід запуску. Позначай уривок відповіді як уривок. Перед командою очищення прямо зазначай, які дані вона видаляє. Для одного сценарію використовуй ту саму назву тестового проєкту в усіх командах.

## Діаграми

- Використовуй Draw.io. Обирай тип за питанням: компоненти, залежності, потоки, послідовності, стани, класи, ER або процес; кількість визначається змістом.
- Кожна схема пояснює одну тему й має коротке пояснення поряд. Підписи вузлів мають бути короткими, без HTML або HTML-переносів рядка. Колір може підкреслювати ролі, але зміст має читатися з підписів.
- Розрізняй логічний рух даних і реальні виклики API. У типовому завданні Orchestrator отримує матеріали та викликає обробники; стрілка потоку між колектором і екстрактором сама по собі не означає прямого HTTP-виклику.
- Зіставляй схему з кодом і контрактами. Не вигадуй стани, залежності або гарантії заради графіки.
- Зберігай єдине редаговане `.drawio` та обов’язкові `.light.png` і `.dark.png` у `docs/diagrams/`. Обидва PNG мають прозорий фон і створюються з того самого джерела.
- Перевір парсинг і відображення в цільовому переглядачі або доступному рендерері: читабельність підписів, напрямки, обрізання, обов’язково світлу й темну тему. Статична перевірка або рев’ю джерела не підтверджує фактичний рендер. Якщо рендер недоступний, чесно зазнач межу перевірки у звіті про роботу.

## Зміст для модулів і довідників

Документація модуля має пояснювати призначення, межі, самостійний запуск, обов’язкові й опційні залежності, конфігурацію та ліміти, входи й виходи, помилки, сторонню інтеграцію, композицію, власність даних та експлуатацію. Для бібліотеки опиши встановлення й мінімальний застосунок.

Зберігай відмінність між екстрактором-пакетом і Handler Runtime, який виконує його код. Не представляй Orchestrator обов’язковим для прямого використання колектора або обробника. Локальний пакет може усувати залежність від Registry; власні сховища та інші фактичні залежності сервісу все одно потрібно описати.

Довідник у стилі MSDN охоплює всі публічні типи й члени: призначення, модуль, успадкування, інтерфейси, сигнатури, параметри, результати, винятки, обмеження, приклади й посилання на код. Познач доступність читання/запису властивостей. Генеруй фактичні декларації з коду та контрактів, доповнюй поясненнями; спільні відомості зв’язуй посиланнями без дублювання.

## Перевірка перед завершенням

1. Звір факти з поточною ревізією, збережи автономність і явно вкажи реальні обмеження в доречному розділі.
2. Перевір локальні шляхи, посилання на заголовки, рівні заголовків, закриття блоків і мову кожного блоку. Для прикладів перевір формат даних та актуальні аргументи команд.
3. Перевір діаграми й вигляд сторінки, наскільки дозволяє середовище. Використовуй наявні перевірки документації; повні тести платформи запускай лише за потреби зміни.
4. Для WP додай реальні докази та висновок незалежного рев’ю за правилами Jane. Відрізняй перевірку посилань, парсинг, рендер і фактичне виконання сценарію; не називай невиконану перевірку успішною.

Якщо документація розходиться з вимогами, узгодь її в межах дорученої роботи. Не переносись на застарілий стиль і не додавай вигаданих можливостей.

## Формат діаграм: Draw.io

Для кожної діаграми обов’язкові три файли в `docs/diagrams/<розділ>/`: `<назва>.drawio`, `<назва>.light.png`, `<назва>.dark.png`. Єдине редаговане джерело — `.drawio` зі справжніми вузлами, ребрами та текстом; вкладене плоске зображення не замінює джерело. Обидва PNG експортуються з того самого джерела з прозорим фоном; кольори тексту, стрілок і вузлів відповідають світлій або темній темі.

У Markdown показуй світлу версію й давай поруч посилання на темну та `.drawio`. У переглядачі, який підтримує тему, автоматично вибирай відповідний PNG; сирий HTML для перемикання в Markdown не використовуй. PNG не редагуються вручну. Зміна джерела вимагає повторного експорту обох PNG й оновлення контрольних сум.

Перевіряй XML-модель і зв’язки, однаковий зміст обох експортів, RGBA-прозорість, наявність непорожніх пікселів, читабельність підписів та напрямків, відсутність обрізання на світлому й темному тлі. Візуальний перегляд і статична перевірка записуються як окремі докази. Механізм експорту обирається під час виконання робіт; PNG і джерела зберігаються в репозиторії.
