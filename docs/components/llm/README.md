# LLM gateway

LLM gateway — сервіс `services/llm`, через який платформа звертається до мовних моделей. Він веде провайдерів, моделі й псевдоніми, тримає бюджети витрат на рівнях платформи, джерела й завдання, рахує витрати та виконує пакети обробників `kind: llm` як етап ланцюжка. Тип модуля — обробник; працює окремо, без Orchestrator і Registry.

Сервіс реалізує два API: власний `llm.v1` (провайдери, псевдоніми, запити до моделі, бюджети, облік) і спільний протокол обробників `handler.v1` (виклик LLM-пакета, тест-прогони, підключення).

## Призначення й межі

| Відповідає за | Не відповідає за |
|---|---|
| виклик моделі з розділенням довірених інструкцій і недовірених даних | вибір моделі для конкретної задачі — це робить клієнт або пакет через псевдонім |
| бюджети `platform` → `source` → `task`, ліміт запитів на хвилину, облік токенів і вартості | зберігання сутностей, отриманих від моделі, — це етап Storage |
| перевірку відповіді моделі за JSON Schema з повторною спробою | дослідження джерел і генерацію екстракторів — це Assistant |
| виконання пакетів `kind: llm` за `handler.v1` | зберігання й версіонування пакетів — це Registry |
| керовані підключення до провайдерів: посилання на секрети замість значень | розклади, ланцюжки етапів і повтори доставки — це Orchestrator |

Власні дані сервісу — конфігурація (провайдери, псевдоніми, бюджети, підключення), лічильники бюджетів, журнал витрат, результати викликів обробника, ключі ідемпотентності та job. Їх будову описано в [internals.md](internals.md#власні-дані).

## Можливості

- **Запит до моделі** — `POST /v1/completions`: інструкції, дані, опційна `output_schema`; синхронно (200) або як job (`mode: async`, 202).
- **Структурований вихід** — відповідь перевіряється за `output_schema`; за невідповідності шлюз повторює запит із підказкою (`gateway.max_schema_retries`).
- **Бюджети** — `PUT /v1/budgets/{scope_type}/{scope_id}`; перед кожним викликом провайдера шлюз атомарно резервує найгіршу оцінку вартості. Вичерпаний бюджет — 429 `budget_exhausted` без звернення до провайдера.
- **Ідемпотентність** — повтор запиту з тим самим `Idempotency-Key` повертає збережену відповідь і не витрачає бюджет удруге.
- **Облік** — `GET /v1/usage` групує запити, токени й вартість за днем, моделлю, метою або рівнем; виклики в тестовому режимі позначено `test_mode`.
- **Провайдери** — `anthropic` (Messages API) і детермінований `fake` для тестів; моделі викликаються через псевдоніми (`default`, `cheap`, `strong` тощо).
- **LLM-обробник** — `POST /v1/invocations` і `POST /v1/test-runs` для пакетів `kind: llm`; вбудований приклад — `jane.llm-event-extractor`.
- **Сховище стану** — PostgreSQL (кілька екземплярів) або пам'ять процесу (`JANE_LLM_STORE=memory`).

## Автономність

LLM gateway працює без інших модулів Jane. Для першого запуску не потрібні ні база, ні ключ провайдера: режим `JANE_LLM_STORE=memory` і вбудований провайдер `fake` дають детерміновані відповіді. PostgreSQL потрібен для кількох екземплярів і збереження стану між перезапусками; Registry — лише щоб брати LLM-пакети за ідентифікатором (пакет можна передати архівом або покласти в локальний каталог). Подробиці — [dependencies.md](dependencies.md).

## Обмеження

- **Провайдерів два:** `anthropic` і `fake`. Інші провайдери потребують нового адаптера в коді (`jane_llm/providers`).
- **Реальний Anthropic у цій документації не перевірено:** усі приклади виконано з провайдером `fake`. Підключення описано за кодом і `scripts/llm_anthropic.py`.
- **Оцінка токенів наближена:** резерв бюджету рахується як кількість символів, поділена на `gateway.chars_per_token_estimate` (типово 2), тому резерв зазвичай більший за фактичну вартість.
- **Ціни моделей задає адміністратор** у визначенні провайдера; модель без `pricing` не викликається (422).
- **`memory` лише для одного процесу:** бюджети, облік і ключі ідемпотентності зникають після перезапуску й не діляться між екземплярами.
- **Псевдонім видалити через API не можна:** є лише `GET` і `PUT` `/v1/model-aliases`.
