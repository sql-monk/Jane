## Моніторинг

| Що | Як |
|---|---|
| Процес живий | `GET /v1/health` → `{"status":"ok","checks":{}}`. Цільові сховища тут **не** перевіряються |
| Підключення працює | `POST /v1/connections/{id}/test` → `ok`, `secrets_resolved` за іменами (без значень), `latency_ms`, `message` при помилці |
| Що встановлено | `GET /v1/info`: адаптери, пакети з digest, контрактні ліміти, режим автентифікації |
| Стан і обсяг сховища | `POST /v1/storage-status/checks` (job) перевіряє підключення й рахує об'єкти та сутності за типами; `GET /v1/storage-status` віддає останній результат. Статистику мають `filesystem`, `postgresql`, `mongodb` |
| Ефективні ліміти | Рядок журналу `configured limits` під час старту |

Метрики Prometheus (`/metrics`, без токена, якщо `metrics_public` не вимкнено):

| Метрика | Мітки | Значення |
|---|---|---|
| `jane_storage_writes_total` | `adapter`, `status` | Підтвердження записів: `written`, `partially_stale`, `stale`, `duplicate`, `simulated` |
| `jane_storage_failed_invocations_total` | `kind` | Невдалі виклики за `failure.kind` (`connection_error`, `execution_error`…) |
| `jane_http_requests_total`, `jane_http_request_duration_seconds`, `jane_http_requests_in_flight` | `method`, `route`, `status` | Спільні HTTP-метрики jane-kit |
| `jane_service_info` | `service` | Завжди `1` |

Корисні сигнали: зростання `failed_invocations_total{kind="connection_error"}` — недоступне сховище або вичерпані повтори `CONFLICT`; висока частка `status="stale"` — запізнілі спостереження від джерела; `duplicate` — повтори Orchestrator після збоїв.

Журнали — JSON у stdout (`JANE_STORAGE_LOG_FORMAT=console` для людини). Повідомлення Storage:

| Повідомлення | Рівень | Значення |
|---|---|---|
| `storage ready` | info | Адаптери, пакети, Registry, підключення під час старту |
| `configured limits` | info | Ефективні ліміти |
| `storage adapter failed` | warning | Помилка сховища під час виклику; `retryable` у полях |
| `connection violates the secret policy: …` | warning | Підключення з файлу порушує політику; воно відхилятиметься |
| `contracts not found: …` | warning | Немає `contracts/`; запити перевіряє лише ядро |
| `transit blobs removed` | info | Прибирання прострочених транзитних blob |
| `deprecated limits group 'retries' …` | warning | Застаріла змінна `JANE_STORAGE_LIMITS__RETRIES__*` |

Значення секретів не потрапляють у журнали й відповіді: повідомлення драйверів редагуються (`***`).

## Розгортання

Образ збирається з кореня репозиторію ([Dockerfile](../../../services/storage/Dockerfile)) і містить ядро та всі адаптери з `services/storage/adapters/*`:

```powershell
docker build -f services/storage/Dockerfile -t jane-storage .
```

| Властивість | Значення |
|---|---|
| База | `python:3.12-slim`, uv `0.12.13` |
| Користувач | `jane` (uid 10001) |
| Порт | `8000` (`JANE_STORAGE_HOST=0.0.0.0`) |
| Том | `/var/lib/jane/storage` — каталог файлового адаптера й транзитних blob |
| Контракти | `/app/contracts` (`JANE_CONTRACTS_DIR`) |
| Healthcheck | `GET /v1/health` кожні 10 с |

У dev-стеку сервіс піднімає `just up storage`; конфігурація — [infra/compose.yaml](../../../infra/compose.yaml), огляд стеку — [розгортання](../../architecture/deployment.md). Для продуктивного середовища: `AUTH_MODE=api_key` або `jwt`, секрети — змінними `JANE_SECRET_*` або файлами в `/run/secrets`, явний `CONNECTION_HOST_ALLOWLIST`.

## Оновлення й міграції

- **Власної бази немає** — міграцій сервісу немає. Оновлення: новий образ і перезапуск; виклики в роботі перериваються, Orchestrator повторює їх тим самим ключем.
- **Схеми в цільових сховищах** адаптери створюють під час першого відкриття (`ensure_schema`: `CREATE … IF NOT EXISTS`, індекси, бакет). Механізму міграцій для зміни вже створених таблиць немає: `ensure_schema` лише додає відсутнє. Зміна структури адаптера потребує ручної міграції.
- **`jane.storage-mongodb@2.0.0`** змінила розкладку: колекція на тип сутності замість спільних колекцій 1.x (`jane_entities`, `jane_entity_history`, `jane_deliveries`, …). Версія 2 колекцій 1.x не читає й не переносить: дані 1.x лишаються в базі, а завдання, переведені на 2.0.0, пишуть у нові колекції. Перенесення не передбачено ([ADR-0011](../../adr/0011-data-placement.md)).
- **Пакети збереження** незмінні за версією: новий маніфест — нова версія `jane.storage-*`. Етапи завдань посилаються на `package_id@version`, тож оновлення адаптера не змінює вже налаштованих завдань.
- **Підключення** після перезапуску: з файлу читаються знову, а створені через `PUT` — втрачаються. Orchestrator надсилає підключення під час зміни свого реєстру, тому після перезапуску Storage їх треба надіслати знову (повторно зберегти в Orchestrator) або тримати у файлі.

## Резервування й відновлення

Storage даних не тримає — резервуються цільові сховища їхніми засобами (`pg_dump`, резервні копії SQL Server, `mongodump`, версіонування бакета, копія каталогу).

- Записи доставок, знімки й історія мають бути в **одній узгодженій** копії: таблиці `<prefix>deliveries`, `<prefix>entities`, `<prefix>entity_history`, `<prefix>objects` у PostgreSQL і SQL Server; колекції `<prefix>_deliveries`, `<prefix><тип>`, `<prefix><тип>.history`, `<prefix>_objects`, `<prefix>_object_chunks` у MongoDB; ключі бакета й підкаталоги в S3 і файлах. Копія без записів доставок втратить дедуплікацію: повторна доставка старого ключа запише дані вдруге.
- MongoDB: `mongodump` без реплікасету не дає знімка всієї бази, тому копіюйте її, коли Storage не пише. Команди для бази `jane_results` dev-стеку — [резервування платформи](../../operations/backup-restore.md#mongodb-сутності-з-пакетів).
- Файловий адаптер: копіюйте каталог `base_path` при зупиненому Storage або знімком файлової системи; тимчасові `*.tmp` і `locks/` не потрібні.
- Після відновлення зі старішої копії ключі доставок, записані пізніше, сховище «не пам'ятає»: їх повторна доставка запише дані знову, а порядок спостережень не дасть старішим значенням перезаписати новіші.
- Власні транзитні blob (`JANE_STORAGE_TRANSIT_DIR`) резервувати не потрібно: вони тимчасові й створюються знову під час читання.

Відновлення після збою під час запису вбудоване в адаптери: незавершений коміт або доповнюється наступним читачем (`pending` у MongoDB і S3), або виконується знову (запис доставки без знімка у файловому адаптері). Перевірено для PostgreSQL: зупинка бази посеред роботи → `connection_error`; після старту бази повтор тим самим ключем завершився успішно.

## Масштабування

Записи можна виконувати кількома екземплярами з одним сховищем: дедуплікація й CAS версій — у сховищі, тож дублів і втрачених оновлень немає (сценарії C-02, C-09). Паралельність одного екземпляра — `jobs.max_concurrent_jobs`, пул з'єднань — `adapters.pool_max_size`.

Обмеження кількох екземплярів:

- підключення з `PUT /v1/connections/{id}` живуть у пам'яті екземпляра, що прийняв запит; за балансувальником використовуйте файл підключень, однаковий для всіх екземплярів;
- `GET /v1/invocations/{id}` і `GET /v1/jobs/{job_id}` відповідають лише на екземплярі, що виконав виклик;
- ключі `Idempotency-Key` у пам'яті кожного екземпляра; паралельний дубль на іншому екземплярі не отримає `409`, але й не запише дані вдруге — його зупинить запис доставки в сховищі;
- файловий адаптер для кількох екземплярів потребує спільного каталогу з коректними `O_EXCL` і атомарним `os.replace`; на мережевих файлових системах не перевірявся.

Розбіжність із ТЗ §4 («Компоненти повинні підтримувати незалежне масштабування кількома екземплярами»): запис масштабується, але керовані підключення, job і результати викликів не спільні між екземплярами.

## Власність даних

- Storage не має власної бази. Дані, які він пише, належать користувачу й лежать у цільових сховищах; Storage створює в них лише свої таблиці, колекції чи ключі з префіксом (`jane_`, `prefix`).
- Інші сервіси Jane читають результати лише через `storage.v1`, а не з таблиць напряму ([власність даних](../../architecture/data-ownership.md)). Сторонній застосунок користувача може читати власну базу SQL-запитами ([приклад](integration.md#самостійне-використання)).
- API видалення немає: записи доставок і історія зберігаються безстроково й ростуть з кожним викликом. Прибирання — вручну засобами сховища; видалений запис доставки знімає захист від дубля для свого ключа.

## Типові проблеми

| Симптом | Причина | Що зробити |
|---|---|---|
| `422`, `host_not_allowed` | Хост підключення не в allowlist | Додати `hostname:port` у `JANE_STORAGE_CONNECTION_HOST_ALLOWLIST`, перезапустити |
| `422`, `secret_ref_not_allowed` | `env:` без префікса `JANE_SECRET_`, `file:` поза каталогом секретів, `vault:` | Перейменувати змінну або перенести файл |
| `422 secret_detected` | Секрет у `params` | Перенести в `secret_refs` |
| `502 upstream_unavailable`: `secret(s) … cannot be resolved` | Змінна чи файл секрету відсутні в середовищі Storage | Задати змінну або змонтувати файл; перевірити `POST /v1/connections/{id}/test` |
| `404` на підключення, що раніше працювало | Storage перезапущено, підключення було з `PUT` | Надіслати підключення знову або описати у файлі |
| `HandlerResult.failed`, `connection_error`, `retryable: true` | Сховище недоступне або паралельні записи вичерпали `conflict_retries` | Перевірити сховище; за частих конфліктів збільшити `conflict_retries.max_attempts` |
| `execution_error`: `already stored with sha256 …` | Той самий ключ об'єкта з іншим вмістом: збіглися `source_id`, дата, `material_id` і `observation_id` | Колектор має давати новий `observation_id` кожному спостереженню |
| `failed`: `local blob reading is disabled` | Вхідний `file:///` без `JANE_STORAGE_CONTENT_FILES_DIR` | Задати каталог RAW-об'єктів файлового адаптера |
| У `GET /v1/objects/{id}` немає `material` | RAW більший за `inline_max_bytes`, немає постійного URI й не задано `JANE_STORAGE_TRANSIT_DIR` | Задати транзитний каталог або читати `/content` |
| `413 payload_too_large` | Тіло більше `transfer.max_request_body_bytes` | Передавати вміст blob-посиланням |
| `lock … held longer than lock_timeout_ms` | Файловий адаптер: довге блокування ключа | Перевірити залишки `locks/` після аварії (старші за `lock_stale_ms` ламаються самі), швидкість диска |
| `bucket … does not exist (params.create_bucket is false)` | S3: бакет не створено | Створити бакет або задати `create_bucket: true` |
| Сутності не видно через `storage.v1` | Етап писав у простір `prefix` / `schema`, а підключення читання — без нього | Окреме підключення з тими самими `params` |
