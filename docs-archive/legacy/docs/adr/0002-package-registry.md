# ADR-0002. Технологія репозиторію пакетів обробників

**Статус:** прийнято (WP-00, 2026-09-27) · закриває відкрите рішення ТЗ §13.2

## Контекст
ТЗ §7, §13.2: потрібне зберігання й розповсюдження пакетів обробників усіх типів (екстрактор,
збереження, LLM, перетворення) і правил колекторів. Вимоги: версії, незмінні артефакти,
залежності, тести, походження (людина чи LLM), форки з посиланням на батька й незмінністю
після оновлення батька, diff, явне перенесення змін, контроль доступу, заборона автозмін
пакета, пошук за типом сутності/доменом, автономне використання пакета без оркестратора й без
репозиторію. Пакети не містять секретів (відхиляти). Одна з ключових робіт — WP-05; споживачі —
runtime, storage, llm, колектори, асистент, адмінка.

## Рішення
**Власний сервіс `registry` (WP-05) з API `registry.v1`**:

1. **Метадані** (пакети, версії, статуси, історія статусів, звіти тестів, форки, налаштування
   `auto_changes_allowed`) — у власній БД PostgreSQL `jane_registry`.
2. **Артефакт версії** — zip-архів із `jane-package.json` у корені
   (`schemas/package-manifest.schema.json`), зберігається **content-addressed** у blob-сховищі
   (`jane-registry/sha256/<hex>`; MinIO/S3 або файлова система). Дайджест `sha256:` канонічного
   архіву (відсортовані шляхи, фіксовані mtime/права) обчислює registry; версія незмінна
   (`version_exists`), ідентичний вміст дедуплікується за дайджестом.
3. **Форк** — новий пакет із копією вмісту й `fork_of` (батько, версія, дайджест). Батько не має
   посилань на форк у вмісті, тож його оновлення форк не змінюють. `GET /upstream` показує нові
   версії батька, `GET /diff?from=parent:<v>` — відмінності, `POST /upstream-ports` — трьохстороннє
   злиття лише за явною командою, результат — нова версія форку зі `provenance.upstream_port`.
4. **Залежності**: екстрактори залежать лише від бібліотек **профілю runtime**
   (`dependencies.runtime_profile`, наприклад `python-extractor@1`); registry перевіряє вимоги
   PEP 508 проти опису профілю (його публікує WP-06) і відхиляє `dependency_not_allowed`.
   Залежність між пакетами — `dependencies.packages` з точними версіями.
5. **Секрети**: при публікації — сканування вмісту (шаблони ключів, високоентропійні рядки,
   `.env`, приватні ключі) → 422 `secret_detected`. Підключення описуються лише як
   `required_connections`.
6. **Статуси версії**: `draft → approved | rejected`, далі `deprecated`/`yanked`. Активація в етапі
   завдання — справа оркестратора; registry лише каже, чи версія дозволена (`approved`).
7. **Контроль доступу**: scopes `registry:read`, `registry:write`, `registry:approve` (ADR-0005);
   LLM-асистент публікує лише `draft` і не може публікувати в пакет з `auto_changes_allowed=false`.
8. **Автономність**: `GET …/archive` (ETag = дайджест) — самодостатній архів для handler-runtime
   CLI або `HandlerInvocation.package_archive`. Сам registry не залежить від інших сервісів
   (прогін тестів при публікації — опційно через handler-runtime).

## Наслідки
- Один механізм версіонування для всіх типів пакетів і правил колекторів (критерій 9).
- Незмінність і дайджест дають відтворюваність етапів (`package_id@version#digest`).
- Власний сервіс — більше коду в WP-05 порівняно з готовим реєстром, але всі доменні вимоги (форк,
  upstream, статуси, заборона автозмін, пошук за сутностями) реалізуються прямо.
- Можливий наступний крок без зміни контракту — дзеркалювання архівів в OCI-реєстр (ORAS).

## Альтернативи
| Варіант | Чому ні |
|---|---|
| **OCI-реєстр (ORAS, Harbor, distribution)** | Незмінні content-addressed артефакти й доступ «з коробки», але форки, upstream-diff, статуси погодження, пошук за типом сутності й заборону автозмін усе одно треба будувати поруч; для Windows-розробки додає ще один сервіс. Залишено як можливий бекенд зберігання |
| **Git-репозиторій (гілка/тег на версію, форк = fork репо)** | Diff і історія безкоштовно, але незмінність тегів не гарантована, контроль доступу й пошук — зовнішні, LLM-публікація через git складніша; конфлікти злиття в рантаймі |
| **PyPI-сумісний індекс (devpi, pypiserver)** | Лише Python-пакети; storage/LLM-пакети й правила колекторів не лягають; немає форків і походження |
| **Таблиця в БД оркестратора** | Порушує автономність (ТЗ §4, §13.2 «без оркестратора») і спільну БД |
