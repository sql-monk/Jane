## Компоненти

| Модуль | Відповідальність |
|---|---|
| `__main__.py` | точка входу `python -m jane_llm` (також команда `jane-llm`) |
| `app.py` | FastAPI-застосунок: маршрути `llm.v1` і `handler.v1`, seed під час старту, оренди спільного стану |
| `gateway.py` | `Gateway`: розв'язання моделі, план бюджетів і лімітів частоти, резерв, виклик провайдера, перевірка виходу, облік |
| `prompt.py` | збирання промпту: преамбула, інструкції, дані в розмежувачах з nonce, підказка для повтору |
| `handler.py` | `LlmHandler`: виконання пакета `kind: llm`, відображення виходу в `HandlerResult` |
| `packages.py` | `PackageLoader`: архів запиту → локальний каталог → Registry; канонічний архів і дайджест; CLI `digest`/`publish` |
| `testing.py` | `run_tests`: тест-прогін пакета (`POST /v1/test-runs`) |
| `connections.py` | політика секретів і `api_base`, розв'язання `secret_refs`, пошук секретоподібних значень |
| `providers/` | адаптери `anthropic` і `fake`, протокол `ProviderAdapter` |
| `store.py` | `Store`: `PostgresStore` і `MemoryStore` з однаковою семантикою |
| `models.py` | Pydantic-моделі документів `llm.v1` і `Connection` |
| `settings.py` | налаштування процесу й групи лімітів |

Спільне з jane-kit: створення застосунку, автентифікація, `/v1/health`, `/v1/info`, `/metrics`, job (`/v1/jobs/*`), ідемпотентність, курсорна пагінація, читання `ContentRef`.

## Запит до моделі

![Послідовність completion: ідемпотентність, бюджет, повтор за схемою](../../diagrams/llm/completion-sequence.light.png#gh-light-mode-only)
![Послідовність completion: ідемпотентність, бюджет, повтор за схемою](../../diagrams/llm/completion-sequence.dark.png#gh-dark-mode-only)

Зображення для теми: [світле](../../diagrams/llm/completion-sequence.light.png), [темне](../../diagrams/llm/completion-sequence.dark.png); джерело — [completion-sequence.drawio](../../diagrams/llm/completion-sequence.drawio).

`Gateway.complete` виконує:

1. Перевіряє `output_schema` (JSON Schema 2020-12) і розв'язує ефективні ліміти: шар запиту поверх платформних.
2. Розв'язує модель: псевдонім або `provider_id/model_id` → провайдер (має бути `enabled`) → модель → адаптер за `kind` → підключення з секретами. Модель без `pricing` відхиляється: без ціни бюджет неможливо застосувати.
3. Збирає промпт (див. [нижче](#розділення-інструкцій-і-даних)) і визначає `max_output_tokens` = значення запиту або `gateway.default_max_output_tokens`, але не більше `llm.max_output_tokens_per_request`.
4. Для кожної спроби (1 + `max_schema_retries`):
   - оцінює вхідні токени як `ceil(символи промпту / gateway.chars_per_token_estimate)`; перевищення `max_input_tokens_per_request` або контексту моделі — 422 `limit_exceeded`;
   - рахує найгіршу оцінку вартості: оцінка входу й `max_output_tokens` за цінами моделі;
   - атомарно резервує оцінку в усіх застосовних бюджетах і збільшує лічильники частоти; відмова на першій спробі — 429, на повторній — спроби зупиняються, а відповідь отримує позначку `schema retries stopped`;
   - викликає провайдера; помилка провайдера знімає резерв — 502 `upstream_unavailable`;
   - замінює резерв фактичною вартістю й додає запис у журнал `usage` (`outcome`: `ok` або `invalid_output`);
   - перевіряє вихід за схемою; невалідний вихід і наявна спроба — у системний канал додається підказка, побудована **лише зі схеми** (шлях у схемі й порушене ключове слово), без значень з відповіді моделі.
5. Повертає `CompletionResult` із сумою токенів і вартості всіх спроб і станом бюджетів.

Якщо модель обгорнула JSON у Markdown-блок коду (з позначкою `json` або без неї), обгортка знімається перед розбором.

## Бюджети

Бюджет — пара `(рівень, Budget)`; `Budget` = `amount`, `currency`, `period`.

| Рівень | Звідки | Коли застосовується |
|---|---|---|
| `platform` | збережене визначення `platform/platform` або `limits.llm.budget` конфігурації | завжди |
| `source` | `PUT /v1/budgets/source/{id}` | якщо задано `scope.source_id` |
| `task` | `PUT /v1/budgets/task/{id}` | якщо задано `scope.task_id` |
| запит | `limits.llm.budget` запиту | додатковий бюджет найконкретнішого рівня запиту |

Правила (`gateway.py`):

- **Лічильник** — `(рівень, ідентифікатор, валюта:вікно)`. Вікна `day`, `week`, `month` — календарні періоди UTC; `total` — одне вікно; `run` — за `scope.run_id`, а без нього — сам запит з усіма повторами за схемою.
- **Бюджет запиту лише звужує.** З тією самою валютою й періодом, що в збереженого бюджету того самого рівня, обидва використовують один лічильник, і діє менша сума; інакше перевіряються обидва.
- **Перевірка перед кожним викликом провайдера:** виклик дозволено, лише якщо для кожного бюджету `spent < amount` і `spent + reserved + оцінка ≤ amount`. Тому `amount: 0` забороняє будь-який виклик, навіть моделі з нульовою ціною.
- **Атомарність:** у PostgreSQL рядки лічильників блокуються `SELECT … FOR UPDATE` в одному глобальному порядку ключів — кілька екземплярів разом не перевищують бюджет і не потрапляють у взаємне блокування.
- **Застарілий резерв** (екземпляр упав під час виклику) через `gateway.reservation_ttl_seconds` списується за оцінкою.
- **Частота:** `max_requests_per_minute` рахується за хвилину для рівнів `platform`, `source`, `task` (із збережених визначень і запиту) і для провайдера (`provider.limits.max_requests_per_minute`). Перевищення — 429 `rate_limited` з `Retry-After` до кінця хвилини.
- **Стан бюджету** (`status` у відповідях): `spent` — уже списана вартість без резервів; `exhausted` = `spent ≥ amount`.

## Розділення інструкцій і даних

Вміст сайтів і повідомлень — дані, не інструкції (ТЗ §11). `prompt.py`:

- Довірений текст — платформна преамбула й `instructions` клієнта чи пакета — іде лише в системний канал провайдера.
- Кожна частина даних іде в канал користувача між рядками `<<<JANE-DATA <nonce> name=… media_type=…>>>` і `<<<JANE-END <nonce>>>`. `nonce` — 128 випадкових біт на кожен запит, оголошується лише в системному каналі.
- Будь-яке `<<<` у даних замінюється схожими символами `‹‹‹`, тому дані не можуть підробити розмежувач, навіть знаючи nonce.
- Преамбула прямо каже моделі не виконувати вказівок усередині блоків.
- Підказка для повторної спроби будується лише зі схеми, бо шляхи в даних і відповіді можуть містити текст джерела.

Тести ін'єкцій (`services/llm/tests/test_injection.py`, `test_content_policy.py`) використовують провайдер `fake`, який виконує вказівки з каналу інструкцій, — так перевіряється, що дані справді не потрапляють у цей канал.

## Ідемпотентність

- `POST /v1/completions` і `POST /v1/test-runs`: ключ `Idempotency-Key` обов'язковий. Перший запит займає ключ; повтор з тим самим тілом повертає збережену відповідь з `Idempotency-Replayed: true` — провайдер не викликається, бюджет не списується. Інше тіло — 422 `idempotency_key_reused`; запит, що ще виконується, — 409 `idempotency_in_progress`.
- `POST /v1/invocations`: ключ — заголовок або `delivery.delivery_key`. Повтор повертає збережений `HandlerResult` з `duplicate: true`. Результат `failed` через `budget_exhausted` не зберігається.
- Ключі живуть `idempotency.idempotency_ttl_seconds` (типово добу). У PostgreSQL ключ, зайнятий екземпляром, що зупинився, звільняється після `state.in_progress_lease_ms`.
- Асинхронний запит з тим самим ключем повертає той самий job.

## LLM-обробник

`LlmHandler.invoke` для кожного входу робить один структурований запит до шлюзу:

1. Завантажує пакет (`PackageLoader`: архів запиту → локальний каталог → Registry), перевіряє `kind: llm`, `entry.executor: llm`, збіг `package_id`/`version` і `digest`.
2. Перевіряє `params` за `params_schema` пакета і тип входу за `input.accepts`.
3. Вхід `material` дає два блоки даних — метадані й вміст; `entities` і `data` — по одному. Якщо пакет має `entry.input_template`, шаблон з `{{шлях.до.значення}}` заповнюється й теж передається як дані.
4. Інструкції — файл `entry.instructions`, схема — `entry.output_schema`, модель — `entry.model` (псевдонім), `scope.purpose: handler`, рівні бюджету — з `context.trace`.
5. Вихід стає `output.data` (кілька входів — `{"results": [...]}`); для кожного `output.entities[]` маніфесту елементи масиву `<entity_type>s` (або `<entity_type>`) стають `EntityRecord`. Ключові поля `message`, `material`, `material_id` без значення беруть ідентифікатор матеріалу; `observation` — з матеріалу.
6. Статус: `success`, `empty` або `failed` (`schema_mismatch`, `budget_exhausted`, `invalid_params`).

## Стани job

Асинхронні запити (`llm_completion`), виклики обробника (`llm_invocation`) і тест-прогони (`llm_test_run`) виконуються як job jane-kit.

![Стани job](../../diagrams/llm/job-states.light.png#gh-light-mode-only)
![Стани job](../../diagrams/llm/job-states.dark.png#gh-dark-mode-only)

Зображення для теми: [світле](../../diagrams/llm/job-states.light.png), [темне](../../diagrams/llm/job-states.dark.png); джерело — [job-states.drawio](../../diagrams/llm/job-states.drawio).

- Одночасно виконується не більше `jobs.max_concurrent_jobs` job на екземпляр, решта чекає в `queued`; понад `jobs.max_queued_jobs` — 503 `service_unavailable`.
- Job довший за `jobs.job_timeout_ms` завершується `failed` з кодом `timeout`.
- У PostgreSQL job належить екземпляру, що його виконує, і тримає оренду, яку оновлює heartbeat (`state.heartbeat_interval_ms`). Якщо оренда не оновлювалася `state.job_lease_ms`, job стає `failed` з `service_unavailable` (`retryable: true`); під час старту екземпляр завершує job зупинених екземплярів.

| Таблиця | Зміст |
|---|---|
| `config` | документи конфігурації: `kind` = `provider`, `alias`, `budget`, `connection`; ключ — ідентифікатор (для бюджету `<scope_type>:<scope_id>`) |
| `counters` | лічильники бюджетів і частоти: `spent`, `reserved`, `requests` за `(scope_type, scope_id, window_key)`; рівень `provider` — лише для частоти |
| `reservations` | резерви викликів у процесі: сума й ключі лічильників |
| `usage` | журнал витрат: по запису на кожен виклик провайдера (зокрема кожну спробу за схемою) |
| `invocations` | `HandlerResult` викликів обробника для `GET /v1/invocations/{id}` |
| `idempotency` | ключі `Idempotency-Key` зі збереженою відповіддю й орендою |
| `jobs` | документи job з власником і орендою |

Секретів у сховищі немає: підключення зберігає лише посилання `secret_refs`, значення розв'язуються в середовищі процесу під час виклику. Схема створюється й доповнюється під час старту під advisory-блокуванням (`CREATE … IF NOT EXISTS`). Власність даних платформи — [архітектура](../../architecture/data-ownership.md).

## Гарантії

- Запит, відхилений бюджетом або частотою, не доходить до провайдера.
- Повтор з тим самим `Idempotency-Key` не викликає провайдера й не списує бюджет.
- Кілька екземплярів зі спільним PostgreSQL не перевищують бюджет разом: перевірка й резерв атомарні.
- Дані не потрапляють у системний канал моделі ні під час першої спроби, ні в підказці для повтору.
- Секрети не повертаються API, не пишуться в базу й журнал; підключенню з недозволеним `api_base` секрети не видаються.
- Відповідь за `output_schema` перевіряється шлюзом незалежно від того, чи провайдер підтримує структурований вихід.
