**Точка підключення стратегій WP-03** (README, розділ «Підключення стратегій»): WP-03 кладе пакет у
`services/web-collector/strategies/discovery/` з `STRATEGIES: list[type[DiscoveryStrategy]]` у `__init__.py`.
Ядро імпортує каталог як пакет `jane_web_collector_discovery` (відносні імпорти працюють; шлях перевизначає
`JANE_WEB_COLLECTOR_DISCOVERY_PATH`, Docker копіює його в `/app/strategies`). Додатково — entry points групи
`jane.web_collector.strategies`. Помилка імпорту пакета не валить сервіс (`/v1/info` → `capabilities.strategy_load_errors`).
Каталог `strategies/discovery/` не створювався. Механізм перевірено плагіном-замінником у тимчасовому каталозі
(`test_discovery_package_is_loaded_and_combines_with_recursion`: sitemap-стратегія через `ctx.fetch` + рекурсія).

Не зроблено / свідомо:
- Спільне сховище стану для кількох **вузлів** (PostgreSQL `jane_web_collector` з карти власності даних) — лише SQLite:
  кілька екземплярів на одному вузлі зі спільним каталогом (lease) або незалежні екземпляри. Див. «Відомі обмеження».
- Blob у MinIO/S3 — лише транзитний каталог (`file://`); без нього великі матеріали → `limit_exceeded` (ADR-0004 п.7).
- Автентифікація запитів до API не перевіряється (`auth_mode=none`, як у шаблоні jane-kit).

## Відомі обмеження
- **Кілька вузлів.** Стан — SQLite; кілька екземплярів коректні на одному вузлі зі спільним каталогом (lease +
  fencing, див. «Виправлення після рев'ю 1») або як незалежні колектори. Спільного сховища для кількох вузлів немає
  (v1 одновузловий, прийнято на рев'ю 1).
- **Blob** — лише `file://` транзит; MinIO/S3 не підключено.
- **Повторні відвідування**: у `incremental` URL, що минулого разу впали (4xx/5xx), пробуються знову; для 304 і
  пропущених URL обхід продовжується за збереженими посиланнями лише для стратегій `recursive`.
- **Семантика для WP-03** (задокументовано в README): `on_fetched` отримує відповіді з будь-яким статусом;
  ресурс із `ctx.fetch` іде в `on_fetched` інших стратегій; навігаційний документ після рестарту можна
  отримати знову, тож стан стратегії має бути в `snapshot()`.
- Метрики — лише HTTP-метрики jane-kit; лічильники обходу — у `stats` збору та `progress.counters` Job.
- Graceful-зупинка скасовує локальні job-задачі jane-kit (Job на мить `cancelled`), але збір лишається
  незавершеним і відновлюється при старті (статус Job перезаписується).
- Перевірено лише на Windows 11; Linux — у CI (`just check`), локально не запускалось.

## Неперевірені інтеграції
- registry.v1 — лише мок сусіда за контрактом (`tests/test_rules_sources.py`, відповіді валідуються за `registry.v1.yaml`); не перевірено на реальному сервісі (WP-05 ще не готовий).

- Реальні сайти в інтернеті — не перевірено (лише testsite).
- Стратегії WP-03 — лише плагін-замінник у тесті; реальний пакет `strategies/discovery/` ще не існує.

## WP-02b: точна межа буфера backpressure (2026-09-30)

**Гілка:** `wp/02b-backpressure` від локального `main` `38766a7`.
**Причина:** WP-13 R-08 на реальному Docker-стеку відтворив
`queue.max_unacked_materials=2` і `unacked=5` за
`concurrency.max_parallel_fetches=4`. Кілька fetch одночасно проходили
`_wait_backpressure()` перед завантаженням і кожен записував матеріал.

У `CrawlRun` перевірка місткості й коміт матеріалу тепер серіалізовані для
одного збору. HTTP-запити можуть завершитися паралельно, але наступний матеріал

### Виправлення після незалежного рев'ю політики секретів

Рев'юер відтворив два витоки. По-перше, `httpx.LocalProtocolError` для
`Authorization` зі значенням із CRLF включав саме значення секрету; код
`Fetcher._with_retries` копіював текст винятку у відповідь одноразового fetch

### Правило для різних значень

Користувач (збір або fetch) **активний на хості** від свого першого запиту до нього й до закриття сесії
(збір завершився, впав, скасований або передав lease; fetch повернув відповідь). Для кожного запиту до хоста
діє **найсуворіше** значення серед активних користувачів: найбільший інтервал
`max(1 / requests_per_second_per_host, min_delay_ms_per_host / 1000, Crawl-delay за respect_crawl_delay)` і найменша
`max_parallel_fetches_per_host`. `Crawl-delay`, побачений сесією, діє до її закриття (запит самого `robots.txt` без
Crawl-delay його не знижує). `Retry-After` від джерела відкладає запити всіх користувачів хоста. Значення беруться
лише з ефективних лімітів сесій (платформа → `rules.limits` → `limits` запиту, `hard_caps`); чисел у коді немає.

### Між екземплярами (ТЗ)

ТЗ прямо не вимагає узгоджувати ліміти на хост між екземплярами: §4 вимагає масштабування кількома екземплярами,
§13.1 п.5 — щоб типові значення «не скасовували окремих обмежень конкретного сайту»; `limits.schema.json` позначає
«на екземпляр» лише `max_parallel_fetches`, для полів `*_per_host` область дії не вказано. За змістом ліміт на хост —
це ввічливість до сайту, тож N екземплярів, що одночасно збирають один хост, разом дають до N× ліміту. Це **не
реалізовано**: потрібна спільна координація (для одного вузла — розклад хоста в спільному SQLite із записом на
кожен старт запиту, для кількох вузлів — зовнішнє сховище, якого у v1 немає); це не дрібна зміна в межах WP-02c.
Межу задокументовано в README («Ліміти»); L2 harness вимірює один екземпляр. Див. «Запити до інших власників» нижче.

### Регресії, які перевірено

- Скасування збору не чекає на лімітер: очікування слоту й черги старту переривається; запит, скасований під час
  очікування, нічого не лишає в розкладі (старт позначається лише після сну, наперед нічого не резервується).
  Перша версія з резервуванням наперед лишала «дірку» після скасування двох запитів не в порядку LIFO — це
  спіймав інтеграційний тест скасування, тому модель змінено.
- Звільнення: `in_flight` повертається у `finally` синхронно (без `await`), тож повторне скасування його не
  перериває; після закриття сесії її (суворі) значення перестають діяти.
- Пам'ять: стан хоста видаляється, коли ним ніхто не користується, нічого не виконується й не чекає, а останній
  інтервал минув — під час закриття сесії та не рідше ніж раз на `collector.host_state_prune_interval_seconds`
  (і в `gc()`); сесії зареєстровані зі слабкими ключами, тож незакрита сесія перестає діяти після збирання сміття.

**3. Очікування синхронного fetch поруч із повільним збором — ризик, не змінювалося.** За правилом «найсуворіше»
`POST /v1/fetches` чекає на свою чергу до хоста стільки, скільки диктує найповільніший активний на хості збір

`collector.max_retry_after_seconds` (той обмежує лише `Retry-After` і `Crawl-delay`). Для harness WP-14 ризик
такий: якщо сценарій із синхронними fetch (або оркестратор у L8) іде одночасно з повільним збором того самого хоста,
fetch відповідає через кілька інтервалів того збору й може перевищити тайм-аут клієнта. Сценарії L1–L8 зараз
виконуються послідовно й кожен дочитує свої збори, тож на них це не впливає. Обмеження не додавав: контрактно
сумісний варіант — 429 `rate_limited` з `retry_after_seconds` після налаштовуваної межі очікування — це нова
поведінка API й новий параметр, а наявний `max_retry_after_seconds` (300 с) клієнтам із коротшим тайм-аутом не
допоміг би. README доповнено реченням про це (розділ «Ліміти»). Якщо WP-14/WP-09 потрібна межа — окрема задача.
