# WP-26. Візуальний редактор ланцюжків

**Гілка:** `wp/26-visual-chain-editor` · **База:** `9936d65` · **Стан:** review

## Результат

Ланцюжок редагується через вибір етапів на схемі та панелі. Додавання handler/collect, видалення етапу з його ребрами, безпечне перейменування з переписуванням `inputs[].from`, вибір пакета та точної версії з реєстру з курсорною пагінацією. Окремі елементи керування створюють і видаляють спрямовані ребра, розгалуження, `select` та рекурсивні умови `when`.

Грід має рівно три колонки: Назва, Тип, Значення. Object/array розгортаються без обмеження штучною глибиною; поля можна додати, видалити й перейменувати без перезапису іншого поля; елементи масиву можна додати, видалити та перемістити. Number/boolean/null/string та вкладені сторонні параметри зберігають типи. Власні ключі `__proto__`/`constructor` обробляються як JSON-дані. Некоректна чернетка числа чи назви блокує глобальне збереження і перевірку, поки поле не виправлено або не видалено.

Текст етапів лишається єдиним джерелом даних: візуальні зміни серіалізують весь набір етапів, JSON-режим читає цей самий текст; некоректний JSON залишається доступним для виправлення. Наявні поля завдання, розклад, ліміти, optimistic concurrency та POST idempotency збережені. Схема TaskConfig перевіряється наявним статично скомпільованим валідатором; DAG-помилки (цикли, невідомі посилання, дублікати, відсутні входи, кілька collect) блокують збереження.

Основні файли: `web/admin/src/components/ChainEditor.tsx`, `PropertyGrid.tsx`, `DagView.tsx`, `web/admin/src/lib/property.ts`, `dag.ts`, `web/admin/src/pages/TasksPage.tsx`, окремий `chain-editor.css`.

Перша спроба browser мала strict-mode помилку неоднозначного test locator `Додати $` (два гріди); уточнено scope і exact match, компоненти не підмінялися. Числа мають точність JavaScript Number, як у наявному JSON-редакторі. Після R1 незавершені поля зберігаються при згортанні; зміна етапу/режиму/вкладки та структурні зміни блокуються до виправлення або явної дії «Відкинути незбережені поля».

Stored-material tasks також потребують collect за чинним контрактом і `orchestrator.dag`; RAW інжектуються через collect. UI зберігає це правило.

## Виправлення після рев’ю R1

1. Невалідне число більше не зникає при згортанні object/array: дочірні рядки лишаються змонтованими і лише приховуються. Незавершені поля блокують raw JSON, вибір етапу/вкладки, перейменування чи видалення етапу, package picker та структурні операції grid/link (зміна типу, перейменування/видалення батька, додавання/видалення/перестановка елементів). Поля можна виправити або явно відкинути кнопкою «Відкинути незбережені поля». Чернетка не дозволяє зберегти старе значення непомітно. Issue registry використовує незалежні React IDs, тому довільні JSON ключі з крапками не колізують із вкладеними шляхами.
2. Виходи залежать від kind джерела ребра: collect — output/unmatched_materials; handler — output/input_material/problems. Невалідний завантажений select не змінюється автоматично, відображається окремою опцією «Недопустимий»; buildDag блокує save також для raw JSON. Правила відповідають `services/orchestrator/src/jane_orchestrator/dag.py`.
3. Новий browser сценарій branching використовує допустимий unmatched_materials із collect. Raw JSON регресія перевіряє collect→problems та handler→unmatched_materials і виправлення без втрат. Array regression перевіряє guard reorder/sibling delete/parent rename/type, explicit discard, correction 9.5 та перестановку зі збереженням `[1,9.5]`. Collapse/raw/stage/tab regression зберігає порожню числову чернетку й після виправлення зберігає 7.25.
4. Під час R1 browser виявив колізію React keys у сусідніх ChainLinks/PropertyGrid при зміні етапу; ключі розділені за типом компонента. Фінальний запуск після виправлення — без retries.
