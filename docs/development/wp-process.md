## Старт

1. Прочитати [ТЗ](../../TECHNICAL_SPECIFICATION.md), `plan.md` §2–§4 і свій WP у §5, `AGENTS.md`, звіти залежностей `docs/delivery/WP-NN.md` і `contracts/`.
2. Створити гілку `wp/NN-<назва>` (назва — з карти шляхів).
3. Створити в корені checkout файл `.jane-wp` з одним рядком `WP-NN`. Файл у `.gitignore`, змінювати його після створення не можна.

## Власність шляхів

Карта [.claude/wp-paths.json](../../.claude/wp-paths.json) задає для кожного WP шаблони `allow`/`deny` (`deny` має пріоритет) і спільні шляхи `common_allow`: звіт `docs/delivery/WP-{wp}.md`, каталог `docs/delivery/WP-{wp}/` і `uv.lock`. Карту змінює лише координатор.

- Хук Claude Code `guard_paths.py` блокує Edit/Write поза шляхами WP, якщо в checkout є `.jane-wp`; checkout без `.jane-wp` вважається checkout координатора й не обмежується.
- Хук `guard_bash.py` у checkout виконавця забороняє push у `main`, `git merge`, перемикання на `main`, видалення чи перезапис `.jane-wp` і карти шляхів; force push заборонено завжди.
- Обхід через команди оболонки знаходить перевірка:

  ```powershell
  python .claude/hooks/jane_wp.py check-diff main
  ```

  Вона перелічує змінені відносно `main` файли поза власністю WP; очікувано — `0`.

Потрібна зміна в чужій області — запис у звіт («Запити до інших власників»), а не правка.

Розбіжність: скіл `jane-wp` у `.agents/skills` згадує шляхи `.Codex/wp-paths.json` і `.Codex/hooks/jane_wp.py`; карта шляхів у репозиторії лежить у `.claude/wp-paths.json` (каталог `.codex/` містить лише хуки й агентів Codex), а `CLAUDE.md` і `AGENTS.md` посилаються на `.claude/hooks/jane_wp.py`.

## Definition of Done

Для сервісного WP (`plan.md` §4):

- API за контрактом, контрактні тести зелені;
- unit- та інтеграційні тести, одна команда запуску в README сервісу;
- README: незалежний запуск, конфігурація, ліміти з типовими значеннями, приклад виклику зі стороннього застосунку;
- Dockerfile, health-check, структуровані журнали, базові метрики, можливість кількох екземплярів;
- `CLAUDE.md`/`AGENTS.md` сервісу з трьох рядків: запуск, тести, контракт;
- критерій «Готово, коли» перевірено тестом або командою;
- `check-diff main` — нуль файлів поза власністю.

Для несервісних WP застосовуються пункти, що мають сенс.

## Звіт і завершення

1. Звіт `docs/delivery/WP-NN.md` за шаблоном `report-template.md` скілу: справжній вивід команд (середину можна скоротити, підсумок — ні); що не запускалося — сказати прямо. Вивід команд зберігати в `.jane/wpNN-*.txt` свого checkout.
2. Часті дрібні коміти англійською у свою гілку; без push у `main`, без merge.
3. Статус у `docs/delivery/status.md` змінює лише координатор. Виконавець повідомляє гілку, останній SHA, шлях до звіту й стан (`review` або `blocked` з причиною).
4. Після рев'ю — кожне зауваження виправлено або обґрунтовано, у звіті розділ «Виправлення після рев'ю N» з новим виводом команд. Рев'ю виконує субагент `wp-reviewer`, який сам запускає команди зі звіту.

## Синхронізація з main

- Конфлікт із `main` перевіряє `git merge-tree --write-tree main HEAD`.
- Розв'язання — `git rebase main` у своїй гілці (`git merge` у checkout виконавця заборонено).
- Конфлікт `uv.lock`: взяти версію з `main`, виконати `uv lock`, потім `uv lock --check`.
- Після rebase — повний `just check`. Злиття в `main` і переписування історії робить лише координатор.
