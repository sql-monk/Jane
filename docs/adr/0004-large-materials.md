# ADR-0004. Передавання великих матеріалів і час їхнього життя

**Статус:** прийнято (WP-00, 2026-09-27)

## Контекст
ТЗ §4: для великих матеріалів — потокове передавання або посилання. plan.md §2: посилання на
blob-сховище (MinIO/S3/файли), не в тілі запиту. Сторінки бувають від кількох КБ до десятків МБ,
вкладення Telegram — більші. Колектор, runtime і storage мають працювати й автономно, без
blob-сховища, для невеликих даних. Потрібно визначити, хто створює й видаляє об'єкти.

## Рішення
1. **Єдиний тип `ContentRef`** (`schemas/common/content-ref.schema.json`), який кожен споживач
   зобов'язаний підтримувати в обох варіантах:
   - `inline` — `data` (utf-8 або base64), якщо розмір ≤ `limits.transfer.inline_max_bytes`;
   - `blob` — `uri` (`s3://bucket/key` або `file:///…` лише для одновузлового розгортання зі
     спільним томом), `sha256`, `size_bytes`, `media_type`, `store`, `expires_at`, опційно
     попередньо підписаний `download_url`.
   Споживач перевіряє `sha256` після читання.
2. **Транзитні об'єкти** (`store: transit`) — бакет `jane-transit`, префікс = сервіс-виробник
   (`web-collector/…`, `telegram-collector/…`, `assistant/…`). Час життя —
   `limits.transfer.transit_ttl_seconds` (довідкове типове значення — 7 діб), реалізується
   lifecycle-правилом бакета (MinIO/S3) або прибиральником виробника (файли). Виробник ставить
   `expires_at`. Транзитний об'єкт — лише для передавання між етапами; довше він не потрібен,
   бо для повторної обробки використовуються **збережені** RAW.
3. **Постійні об'єкти** (`store: persistent`) створює лише обробник збереження за підключенням
   користувача (файли, MinIO, S3, або BLOB-колонка в БД). Вони живуть, доки їх не видалить
   власник сховища; storage повертає `StoredObjectRef` з `content` (persistent `ContentRef`).
   Повторна обробка (`/v1/reprocessing`) читає Material через `storage.v1 GET /v1/objects/{id}`.
4. **Попередньо підписані посилання** (`download_url`) живуть `download_url_ttl_seconds`
   (довідково 1 год); сервіс-споживач з обліковими даними до сховища може читати за `uri`.
   Для споживачів без доступу до сховища (сторонні застосунки) виробник видає `download_url`.
5. **Запити з тілом** понад `limits.transfer.max_request_body_bytes` відхиляються 413
   `payload_too_large` — клієнт має передати blob.
6. Оркестратор ніколи не копіює вміст: між етапами передає `ContentRef` як є. Якщо транзитний
   об'єкт прострочено до обробки (довгий простій) — етап отримує помилку `not_found` і матеріал
   перезбирається або читається зі збереженого RAW.
7. Автономний режим без blob-сховища: `content_delivery: inline` у колекторі; більший матеріал —
   помилка `limit_exceeded` з підказкою налаштувати blob-сховище.

## Наслідки
- Невеликі матеріали не потребують інфраструктури; великі не проходять через JSON-тіла.
- TTL обмежує зростання транзитного сховища; довгострокове зберігання — явний етап збереження
  (узгоджено з ТЗ §2: «Збереження RAW є окремим етапом»).
- Усі реалізації мають однаковий helper читання/запису ContentRef — його дає `jane-kit` (WP-01).

## Альтернативи
- **Потокове передавання (chunked/multipart) між сервісами** — складніше для повторів і
  ідемпотентності, не переживає рестарт; залишено для майбутнього `/v2` за потреби.
- **Завжди inline (base64)** — роздуває тіла на 33 %, пам'ять і ліміти проксі.
- **Спільна файлова система для всіх** — не працює для кількох вузлів і кількох екземплярів.
- **Безстроковий транзит** — неконтрольоване зростання; дублює функцію обробника збереження.
