## Рішення

| Питання | Рішення | Обґрунтування |
|---|---|---|
| Де тримати відкриту сесію / job | URL (`?session=`, `?tab=improvement&job=`) | Відновлюється після перезавантаження, ділиться посиланням; це ідентифікатори, не секрети; браузерне сховище не потрібне |
| Типовий вибір «Повторно обробити» на рядку об'єкта | `material_ids` (як було), `object_ids`/`observation_ids` — явним вибором | Не змінює поведінку й наявний real-тест дефекту WP-09 (він перевіряє саме фільтр `material_ids` за джерелом); точний вибір доступний одним кліком і перевірений real |
| Публікація пропозиції `proposal_only` з UI | лише перегляд (файли, маніфест, diff) | Пункт WP-20 — показ; публікація потребує злиття файлів `based_on` з архіву registry — окрема функція |
| Правила етапу `collect` без власних rules | показати `Source.collector_rules` як поточні («правила джерела») | Так визначає `previous` оркестратор (orchestrator.v1 `activateStageVersion`) |
| Оновлення списків | опитування з `config.polling`, лише поки є активні елементи | Без зашитих інтервалів; неактивні списки не опитуються |

## Відомі обмеження

- Публікації пропозиції `proposal_only` з адмінки немає — лише перегляд (див. «Рішення»).
- Поле порогу впевненості в UI не обмежене стелею `hard_caps` (вона показується поруч); значення понад стелю
  обмежує сам асистент (`min(запит, hard_caps)`).
- У mock-режимі `GET /v1/info` асистента не має `limits` (приклад контракту — загальний `ServiceInfo`), тому mock-тест
  підставляє контрактний профіль `limits@PlatformLimits/ci.json`.
- Повторне відкриття тієї самої групи не перечитує її стан окремим запитом (як і раніше): актуальний стан дає список
  груп; примітка й запуски групи оновлюються (поле примітки синхронізується, список запусків опитується).
