# ADR-0007. Цільові середовища для профілів лімітів

**Статус:** прийнято як типове рішення (WP-00, 2026-09-27); реальні середовища підтверджує людина

## Контекст
ТЗ §13.1 п.5 і критерій 13: ліміти не зашиваються, змінюються без зміни коду; мають бути
перевірені початкові профілі для підтримуваних середовищ розгортання. WP-14 вимірює середовища,
обрані в WP-00, і готує профілі (`deploy/profiles/`). Реальних цільових середовищ замовник не
назвав, тому потрібне розумне типове рішення.

## Рішення
1. **Модель лімітів** — `schemas/common/limits.schema.json`: групи `concurrency`, `rate`, `crawl`,
   `timeouts`, `retries`, `queue`, `sandbox`, `llm`, `transfer`, `telegram`; рівні
   platform → source → task → stage (нижчий перекриває, відсутнє успадковується, `null`
   заборонено); `PlatformLimits.hard_caps` обмежують усе згори; обмеження сайту/провайдера
   (robots Crawl-delay, Retry-After, flood-wait, ліміти LLM) лише звужують; ефективні значення з
   походженням — `GET /v1/limits/effective`. Автономний сервіс застосовує
   `min(limits із запиту, власні hard_caps)`.
2. **Підтримувані середовища v1** (профіль = ім'я в `PlatformLimits.profile`):

| Профіль | Середовище | Орієнтовні ресурси | Призначення |
|---|---|---|---|
| `dev-laptop` | Docker Desktop на Windows 11 / Docker на Linux, увесь стек в одному compose | 4 vCPU, 8–16 ГБ RAM, SSD | розробка, демонстрації |
| `ci` | GitHub Actions `ubuntu-latest` (або еквівалент GitLab) | 4 vCPU, 16 ГБ RAM, без зовнішньої мережі до реальних сайтів | автоматичні тести, testsite |
| `single-node` | Одна Linux VM, Docker Compose, кілька екземплярів сервісів | 8 vCPU, 32 ГБ RAM | перше робоче розгортання |

   Kubernetes/кілька вузлів — поза v1; модель лімітів це підтримує без змін.
3. **Довідкові стартові значення** — `contracts/examples/schemas/common/limits@PlatformLimits/{dev-laptop,single-node,ci}.json`
   і `limits/defaults-dev-laptop.json`. Це **не виміряні** значення: WP-14 має їх перевірити
   навантажувальними прогонами й винести в `deploy/profiles/<profile>.json`; сервіси беруть
   типові значення з конфігурації (не з коду) і документують їх у README.
4. Критерій 13 перевіряється так: зміна `PUT /v1/limits/platform` або `limits` джерела/завдання →
   наступний запуск працює з новими значеннями без перезбирання; профілі проходять smoke-тест на
   своєму середовищі.

## Наслідки
- WP-02…WP-11 отримують ліміти з конфігурації за єдиною схемою; WP-01 (`jane-kit`) реалізує
  злиття й походження один раз.
- Якщо людина назве інші середовища, змінюються лише профілі (WP-14), не схема й не код.

## Альтернативи
- **Одні типові значення на всі середовища** — не виконує критерій 13 («профілі для підтримуваних середовищ»).
- **Ліміти лише в змінних середовища сервісів** — немає рівнів source/task і походження.
- **Автоматичне визначення лімітів за ресурсами хоста** — можна додати в WP-14 як підказку, але
  не замість явних профілів.
