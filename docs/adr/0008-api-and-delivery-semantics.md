# ADR-0008. Конвенції API й семантика доставки

**Статус:** прийнято (WP-00, 2026-09-27)

## Контекст
ТЗ §4, §11, §13.1 п.6: версіоновані документовані API, асинхронні тривалі операції, ідемпотентність,
діагностика, передавання великих матеріалів; повторне отримання — нове спостереження, повторна
технічна доставка — дубль без повторних ефектів; запізнілий результат не замінює новіший;
підтвердження приймання, повтори, відновлення після збоїв, простежуваність. Контракти писатимуть
і споживатимуть 11 агентів паралельно.

## Рішення
1. **Версія в шляху** `/v1`; зворотно сумісні зміни — у `/v1`, несумісні — `/v2` паралельно.
   Відповіді й дані — толерантний читач; документи конфігурації — строгі (`additionalProperties: false`).
2. **Помилки** — RFC 9457 `application/problem+json` + `code`, `retryable`, `errors[]`, `trace_id`
   (`schemas/common/problem.schema.json`, каталог — `contracts/docs/errors.md`). Помилка коду
   обробника — не HTTP-помилка, а `HandlerResult.status = failed` з `failure.kind`.
3. **Чотири стани результату** (ТЗ §9): `success`, `empty`, `unrecognized` (з `partial`),
   `failed` (з `failure.kind`: execution_error, schema_mismatch, timeout, resource_exceeded,
   sandbox_violation, …). Групування проблем — за `unrecognized.signature`/`failure.kind`.
4. **Тривалі операції** — `202` + `Job` + `Location: /v1/jobs/{id}`; стани `queued → running →
   succeeded|failed`, `cancelling → cancelled`; скасування `POST /v1/jobs/{id}/cancel`
   (ідемпотентне). Синхронна операція, що не вклалась у `sync_response_max_ms`, теж переходить у 202.
5. **Ідемпотентність** — заголовок `Idempotency-Key` на кожному POST з ефектом; повтор — збережена
   відповідь і `Idempotency-Replayed: true`; інше тіло — 422; в процесі — 409 retryable.
   Для обробників ключ = `delivery_key`, детермінований:
   `sha256(run_id | stage_id | item_key)`, де `item_key` = `observation_id` або
   `<upstream invocation_id>/<index>`. Storage зберігає `delivery_key` атомарно з даними
   **безстроково**; інші — щонайменше `idempotency_ttl_seconds`.
6. **Спостереження й порядок:** кожне отримання — новий `observation_id`; `material_id` стабільний;
   порядок — `observed_at` → `revision.sequence` → `observation_id`. Часткове оновлення:
   відсутнє поле не змінюється, очищення — лише `cleared`, `null` у `fields` заборонено.
7. **Потік матеріалів колектора — pull із курсором:** `GET /v1/collections/{id}/materials?after=`
   підтверджує все до курсора; непідтверджене видається повторно (at-least-once);
   переповнення буфера (`max_unacked_materials`) призупиняє обхід — це і є backpressure
   оркестратора (черга оркестратора `max_queue_depth` → він перестає забирати матеріали).
8. **Оркестратор:** елемент етапу = (run, stage, item_key); воркер бере елемент з lease
   (`SKIP LOCKED`), викликає обробник із `delivery_key`, фіксує результат і лише потім створює
   елементи наступних етапів (в одній транзакції з позначкою завершення). Після падіння lease
   спливає — повтор із тим самим ключем, обробник не дублює ефект (критерій 8).
9. **Пагінація** — курсорна `{items, next_cursor}`. **Простежуваність** — W3C `traceparent`,
   `trace_id` у журналах і Problem; оркестратор зберігає зв'язки матеріал → етап → результат → версія.
10. **Вміст як дані для LLM:** довірені `instructions` і недовірені `data` розділені в `llm.v1`;
    LLM ніколи не отримує секретів.

## Наслідки
- Повтори будь-де безпечні; дублікати відсікаються на рівні, що має ефект (storage, llm).
- Колектор не потребує знати про оркестратор: той самий pull-API придатний для сторонніх застосунків.
- Pull замість push додає затримку опитування (long-poll `wait_ms` її зменшує).

## Альтернативи
- **Push колектора в оркестратор (callback)** — колектор залежав би від адреси оркестратора;
  складніший backpressure.
- **Вебхуки для job** — корисні, але додають вимоги до мережевої досяжності; відкладено (додаються
  сумісно як необов'язкове поле).
- **Ідемпотентність лише в оркестраторі** — не захищає від повторного запису після падіння між
  записом і фіксацією результату.
- **Offset-пагінація** — нестабільна на змінних наборах.
