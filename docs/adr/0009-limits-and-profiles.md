# ADR-0009. Ліміти з успадкуванням і профілі середовищ

- **Статус:** прийнято, діє.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

ТЗ забороняє зашивати числові ліміти в архітектуру: паралельність, частота запитів, глибина й обсяг обходу, тайм-аути, повтори, розміри черг і матеріалів, бюджети LLM конфігуруються на рівні платформи, джерела й завдання; початкові значення мають бути безпечними й перевіреними для цільового середовища (ТЗ §13.1, п. 5; критерій 13). Сервіси мають застосовувати ліміти й без Orchestrator.

## Варіанти

1. **Одна схема лімітів для всіх рівнів із глибоким злиттям, жорсткими стелями й походженням значень; профілі `PlatformLimits` для середовищ; безпечні типові значення в коді кожного сервісу.**
2. Один набір типових значень для всіх середовищ — або занадто обережний для сервера, або небезпечний для ноутбука.
3. Ліміти лише в змінних середовища — немає рівнів джерела й завдання і немає змін без перезапуску.
4. Автовизначення лімітів за ресурсами хоста — непередбачувано й не враховує обмежень сайтів.

## Рішення

Обрано варіант 1.

- **Схема** — [limits.schema.json](../../contracts/schemas/common/limits.schema.json): групи `concurrency`, `rate`, `crawl`, `timeouts`, `retries`, `queue`, `sandbox`, `llm`, `transfer`, `telegram`.
- **Рівні** — `platform` → `source` → `task` → `stage` → `request`; глибоке злиття, `null` заборонено; `hard_caps` обмежують результат (`min`); результат зберігає походження кожного значення (`GET /v1/limits/effective` в Orchestrator).
- **Сервіси** — модель `Limits` у `jane_kit.config` вимагає типового значення для кожного поля; шари сервісу — файл `JANE_<СЕРВІС>_LIMITS_FILE` і змінні `JANE_<СЕРВІС>_LIMITS__…`; спільний профіль застосовується частково, а невідомі шляхи — помилка старту.
- **Orchestrator** зберігає ліміти платформи в базі (`GET/PUT /v1/limits/platform`) і передає ефективні ліміти етапу виконавцю; виконавець застосовує `min(ліміти запиту, власні стелі)`.
- **Профілі** — `deploy/profiles/dev-laptop.json`, `ci.json`, `single-node.json`; harness `deploy/profiles/harness/limits_harness.py` вимірює дотримання профілю.
- Під час виконання значення лише звужуються обмеженнями джерела чи сервісу (`Crawl-delay`, `Retry-After`, flood-wait Telegram, ліміти провайдера LLM).

## Наслідки

- Ліміти змінюються без зміни коду: перезапуском сервісу з іншим профілем, через API Orchestrator або в документі джерела чи завдання ([ліміти](../operations/limits.md)).
- Кожна відмова через ліміт має стабільний код `limit_exceeded` і шлях ліміту в `details`.
- Значення, які сервіс не моделює, з профілю ігноруються й пишуться в журнал — опечатку в назві відрізняє помилка старту.
- Профіль `ci` виміряно в CI (вердикт `pass`, прогін 37953732904) — [перевірка профілів](../operations/limits-validation.md#результати-приймання).
- Документ платформи Orchestrator створюється з файлу лише на першому старті; зміна файлу на робочу базу не впливає.
