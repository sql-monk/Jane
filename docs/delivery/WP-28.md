## Результат

Реалізовано WP-28 із [плану візуального рев’ю](admin-visual-review-plan.md): початковий перегляд результатів показує каталог фактично збережених типів з читабельними назвами й кількостями. Для єдиного фактичного типу перегляд відкривається автоматично; для кількох типів користувач вибирає картку. Каталог не виводиться з конфігурації джерел, назва `offer` не потрібна для початкового перегляду. Порожнє сховище, відсутня можливість і помилка бекенда мають різні стани.

[API storage](../../contracts/openapi/storage.v1.yaml) доповнено `GET /v1/entity-types` із курсором і необов’язковою областю ключа та параметром `search` існуючого `GET /v1/entities`. Пошук буквального підрядка виконується на сервері по ключах і полях вибраного типу перед пагінацією; клієнт не завантажує попередні сторінки заради пошуку. `%` та `_` не стають шаблонами. URL з `connection_id`, `entity_type`, `scope`, `key` зберігають чинну семантику.

[Обов’язковий StorageAdapter](../../contracts/python/src/jane_contracts/storage_adapter.py) не змінено: додані окремі необов’язкові Protocol-и discovery/search та statistics. Файловий і PostgreSQL адаптери підтримують нові можливості. MinIO, S3, MongoDB та SQL Server повертають `501 not_implemented` для каталогу/пошуку; старий перегляд за відомим типом працює. Приклади, документацію, контрактні споживачі й згенерований `storage.ts` оновлено.

[Статистика сховищ](../../web/admin/src/pages/StoragesPage.tsx) окремо показує RAW/документи результатів та актуальні сутності. PostgreSQL рахує об’єкти за власною таблицею objects, сутності за власною entities, її фізичний обсяг з індексами через `pg_total_relation_size`; кількості типів і загальна кількість отримуються в одній read-only repeatable-read транзакції. Файловий адаптер рахує байти документів актуальних станів. Історія й доставки не включені в обсяг сутностей. Неперевірені або недоступні показники — `null` із причиною, без вигаданого нуля. Чужі таблиці не читаються.

[results-context](../../web/admin/src/lib/results-context.ts) містить `resultsHref({ connectionId, entityType, scope, key })` та `entityTypeLabel`. Helper має лише реальні storage-фільтри, не підміняє область ключа `source_id` і не удає фільтрування за запуском або завданням. Його окремий commit — `f547cc49c515a922bf3731dde067f2d47afaffe9`; інтерфейс передано WP-29 і WP-30.

## Відомі обмеження

Каталог і серверний пошук наразі доступні лише в PostgreSQL/files; решта адаптерів чесно повертає capability unavailable. Пошук обмежений вибраним `entity_type` та заданими scope/key; текстовий індекс не додавався, тому підрядковий пошук може вимагати серверного сканування. Курсор забезпечує сторінки результату, а не постійний snapshot між запитами: паралельні записи можуть змінювати каталог, як і існуючий entity list. Файлова статистика рахує доступні snapshot files під час проходу, без глобального блокування запису.

Показник `statistics` за чинним контрактом означає всі connection objects (RAW та result documents); він не удає фізичного обсягу всього PostgreSQL/диска. `entity_statistics` не є кількістю сутностей конкретного запуску. Helper не додає неіснуючих run/task/source фільтрів.

## Неперевірені інтеграції

UI unit/Chromium використовують сусідні API-моки на базі контрактних прикладів; самі ResultsPage/StoragesPage не мокаються. Файловий API та PostgreSQL integration працювали з реальними власними сховищами. MinIO/S3/MongoDB/SQL Server нову capability не реалізують і на реальному сервісі в межах WP-28 не перевірялися. Повний інтегрований CI, незалежні wp-reviewer/contract-guardian та живий робочий стек очікують WP-32.
