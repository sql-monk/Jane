# Карта власності даних

Правило (ТЗ §4, plan.md §3.7): **кожен сервіс володіє своїми даними й власним сховищем; інші
сервіси отримують їх лише через версіонований API.** Спільної БД немає. У dev-стеку один сервер
PostgreSQL може містити кілька баз, але кожна база має окрему роль, і роль сервісу не має прав на
чужі бази (це налаштовує WP-01).

## Хто чим володіє

| Сервіс (WP) | Володіє даними | Де зберігає | API доступу |
|---|---|---|---|
| web-collector (02/03) | Черга обходу, множина відомих URL, стан стратегій, курсори повторних відвідувань, запуски збору, буфер непідтверджених матеріалів, помилки URL | Власне сховище стану (SQLite для одного екземпляра або власна БД PostgreSQL `jane_web_collector` для кількох) + транзитні blob `jane-transit/web-collector/…` | `collector.v1` |
| telegram-collector (04) | Курсори каналів (останній message_id, водяний знак редагувань), запуски, буфер, сесія облікового запису (як секрет за `secret_refs`) | Власне сховище стану + транзитні blob | `collector.v1` |
| handler-runtime (06) | Кеш ідемпотентності (delivery_key → HandlerResult, TTL), кеш пакетів (перевірених за дайджестом), прогони тестів. **Бізнес-даних немає** | Власне сховище (SQLite/PostgreSQL `jane_handler_runtime`) + локальний кеш | `handler.v1` |
| storage (07/08) | Бізнес-результати в цільових сховищах користувача: актуальний стан сутностей, історія, записи доставок, RAW-об'єкти. Власний кеш ідемпотентності | Цільові сховища за підключеннями (PostgreSQL, SQL Server, MongoDB, MinIO, S3, файли) | `handler.v1` (запис), `storage.v1` (читання) |
| registry (05) | Пакети, версії (метадані, статуси, історія статусів), звіти тестів, форки й походження, налаштування пакетів; архіви версій | Власна БД PostgreSQL `jane_registry` + blob `jane-registry/…` (content-addressed) | `registry.v1` |
| llm (10) | Провайдери, псевдоніми моделей, бюджети рівнів, журнал витрат, кеш ідемпотентності (щоб не платити двічі), підключення провайдерів | Власна БД PostgreSQL `jane_llm` | `llm.v1`, `handler.v1` |
| assistant (11) | Сесії підключення, запуски вдосконалення, проміжні вибірки й оцінки. Створені пакети належать registry | Власна БД PostgreSQL `jane_assistant` + транзитні blob | `assistant.v1` |
| orchestrator (09) | Джерела, завдання, розклади, запуски, елементи етапів (черга з lease), активації й аудит, реєстр підключень (лише `secret_refs`), ліміти платформи, групи проблем, реєстр невідомих матеріалів, простежуваність (лише ідентифікатори й посилання) | Власна БД PostgreSQL `jane_orchestrator` (черга — `SELECT … FOR UPDATE SKIP LOCKED`) | `orchestrator.v1` |
| admin (12) | Нічого, крім стану браузера | — | споживач API |
| blob-сховище (інфраструктура) | Бакет `jane-transit` (префікс = сервіс-виробник, lifecycle TTL), бакет `jane-registry` (registry) | MinIO / S3 / файлова система | посилання `ContentRef` |

Оркестратор не зберігає вміст матеріалів чи результатів — лише ідентифікатори (`material_id`,
`observation_id`, `invocation_id`, `object_id`, `canonical_key`) для простежуваності; вміст читається
через API storage.

## Хто відповідає за дедуплікацію й повтори

| Ситуація | Відповідальний | Механізм |
|---|---|---|
| Той самий URL знайдено кількома стратегіями або кілька разів | Колектор | Черга з дедуплікацією за канонічним URL у межах `state_key` |
| Незмінена сторінка при повторному відвідуванні | Колектор | Умовні запити (ETag/Last-Modified) або `dedup.key = canonical_url_and_content` |
| Колектор повторно видав матеріал, бо споживач не підтвердив курсор | Оркестратор | Той самий `observation_id` → той самий елемент етапу (`run_id, stage_id, item_key`) і той самий `delivery_key` |
| Воркер оркестратора впав під час виклику обробника | Оркестратор + обробник | Lease закінчується → повтор із тим самим `delivery_key`; обробник повертає збережений результат (`duplicate: true`) |
| Повторна технічна доставка результату в сховище | storage | Постійний запис `delivery_key` у цільовому сховищі разом із даними (атомарно) |
| Повтор LLM-запиту | llm | Кеш за `Idempotency-Key`; бюджет не списується вдруге |
| Повторне отримання матеріалу з джерела (новий запуск) | — (це не дубль) | Нове спостереження (`observation_id`) → новий запис історії; актуальний стан — за порядком спостережень |
| Запізнілий результат | storage | Порядок `observed_at → sequence → observation_id`; старіше потрапляє лише в історію (`stale`) |
| Редагування Telegram | telegram-collector | Той самий `material_id`, нове `observation_id`, більший `revision.sequence`, `is_edit: true` |
| Повторна публікація тієї самої версії пакета | registry | Версії незмінні: `version_exists`; той самий `Idempotency-Key` → повтор відповіді |
| Повторний запуск за розкладом під час активного запуску | Оркестратор | `schedule.overlap` (skip/queue/allow) і `max_parallel_runs_per_task` |

Повтори (retry) на помилках: ініціює **викликач** за `retryable` і `limits.retries`
(оркестратор — для етапів; колектор — для HTTP-запитів до джерела; storage — для `CONFLICT`
адаптера). Обробник не повторює сам детерміновані помилки коду екстрактора.

## Автономність: залежності під час роботи

| Сервіс | Обов'язкові залежності | Необов'язкові | Від оркестратора |
|---|---|---|---|
| web-collector | мережа до джерел, власне сховище стану | blob-сховище (без нього — лише inline), registry (правила можна передати inline або з файла) | **ні** |
| telegram-collector | Telegram API, сховище стану | blob-сховище, registry | **ні** |
| handler-runtime | контейнерний рушій (docker/podman) | registry (пакет можна передати архівом), blob-сховище | **ні** |
| storage | цільові сховища | registry (стандартні пакети `jane.storage-*` вбудовані в сервіс), blob-сховище | **ні** |
| registry | власна БД, blob-сховище | handler-runtime (прогін тестів при публікації) | **ні** |
| llm | провайдери LLM | registry (LLM-пакет можна передати архівом) | **ні** |
| assistant | llm, registry, collector, handler-runtime | orchestrator (лише для автоактивації) | опційно |
| orchestrator | власна БД; усі виконавці за конфігурацією | — | — |
