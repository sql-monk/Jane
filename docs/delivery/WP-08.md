# WP-08. Адаптери збереження

**Гілка:** `wp/08-storage-adapters` · **Ревізія:** останній коміт гілки (звіт комітиться останнім; перевірки — на `ed4043f`) · **База:** `0db9aeb` (перевірено злиття з актуальним `main` `894cbf0`) · **Стан:** review

## Результат

Чотири адаптери за інтерфейсом `jane_contracts.storage_adapter.StorageAdapter`, кожен — окремий uv-пакет
`jane-storage-<name>` з entry points `jane.storage.adapters` і `jane.storage.packages`, пакетом збереження в дистрибутиві
(`package/jane-package.json`, `schemas/params.schema.json`, тести пакета) і джерелом `jane-storage = { path = "../..", editable = true }`.
Ядро WP-07 не змінювалося: адаптери з'являються в реєстрі, `/v1/info` і Docker-образі самі.

| Адаптер | Де | Як забезпечено атомарність `commit_entity` |
|---|---|---|
| `sqlserver` (pymssql / FreeTDS, без ODBC) | [adapters/sqlserver](../../services/storage/adapters/sqlserver/README.md) | один T-SQL-пакет в одній транзакції (`XACT_ABORT ON`): вставка доставки → CAS `UPDATE … WHERE version = @expected` / `INSERT` → вставка історії; 2627/2601 на доставці → `DUPLICATE`, інакше/50001/1205 → `CONFLICT` |
| `mongodb` (PyMongo `AsyncMongoClient`) | [adapters/mongodb](../../services/storage/adapters/mongodb/README.md) | без транзакцій (працює на окремому `mongod`): CAS одного документа знімка (`replace_one({_id, version})` / `insert_one`), який несе подію історії й підтвердження доставки в `pending`; ідемпотентне перенесення в `entity_history`/`deliveries`; `get_delivery` бачить ключі в `pending` (індекс) |
| `s3` (boto3) | [adapters/s3](../../services/storage/adapters/s3/README.md) | лише умовні `PutObject`: заявка доставки `If-None-Match: *` → CAS знімка `If-Match: <ETag>` (знімок несе подію в `pending`) → перенесення історії; компенсація заявки при `CONFLICT`; «мертві» заявки (програли гонку — одразу, впали — після `lock_stale_ms`) прибираються |
| `minio` | [adapters/minio](../../services/storage/adapters/minio/README.md) | `MinioAdapter(S3Adapter)` — той самий протокол, інший профіль |

Спільне — з ядра: JSON-документи й `entity_ack` — `jane_storage.codec`, `object_id` — `jane_storage.keys.object_id_for`,
хеші ключів — `key_digest`. Типовий формат RAW — з ядра (адаптери зберігають байти як є; C-12 перевіряє HTML-сторінку
через обробник). Для `s3`/`minio` адаптер має `content_uri()` → `s3://<bucket>/<key>` (читальний API віддає blob).

**MinIO і S3 — спільна основа з різними профілями (обґрунтування).** MinIO реалізує S3 API, тож протокол (розкладка ключів,
умовні записи, алгоритм коміту, відновлення) однаковий; окрема реалізація дублювала б найризиковіший код без різниці в
поведінці. Натомість спільний код перевірено на **двох незалежних** реалізаціях S3 — MinIO і SeaweedFS. Відмінності
(профіль `S3Profile`): `endpoint` обов'язковий для MinIO; `addressing_style` `path` проти `auto`; `create_bucket` типово
`true` проти `false`; SSE-S3/SSE-KMS (`sse`, `sse_kms_key_id`) лише для `s3`. Окремий дистрибутив дає власні `kind`,
пакет `jane.storage-minio` і `required_connections.kind: minio`. Відмінність серверів, помічена в тестах: на `If-Match`
для відсутнього ключа MinIO відповідає `NoSuchKey`, SeaweedFS — 412 (обидва обробляються як невдала умова);
умовний `DeleteObject` MinIO ігнорує — протокол на нього не спирається.

**Відхилення від порядку в contracts/docs/storage-adapter.md для об'єктних сховищ.** Документ пропонує
«доставка → історія (`If-None-Match`) → знімок (`If-Match`)», а осиротілу подію історії — «перезаписувати при повторі».
Осиротілу подію (після збою) не відрізнити від коміту, що ще триває: перезапис ламає чужий коміт, а без перезапису
сутність блокується назавжди (кожен повтор — `CONFLICT`). Тому подія пишеться **в сам знімок** (`pending`) тим самим
умовним записом, а файл історії — після CAS. Умовні записи `If-None-Match`/`If-Match` і всі гарантії контракту
(атомарність, C-01…C-16) збережено; запит до WP-00 на уточнення документа — нижче. Той самий прийом використано в MongoDB.

Додатково до набору сумісності: тести відновлення після збою (`s3/tests/test_recovery.py` — свіжа заявка → `CONFLICT`,
застаріла → прибрано, програна → одразу мертва, непереміщений `pending` → переноситься читачем;
`mongodb/tests/test_recovery.py` — повтор доставки, чий `pending` не перенесено, → `duplicate` і перенесення) і
unit-тести конфігурації кожного адаптера (у `just check`, без сервісів).

Не зроблено з plan.md §5: нічого. Реальний AWS S3 — не перевірено (див. «Неперевірені інтеграції»).

## Конфігурація й ліміти

Усі — з `params` підключення або з опцій адаптера, які ядро бере з `JANE_STORAGE_LIMITS__ADAPTERS__…` (опції мають
пріоритет над `params`); без них — безпечні типові значення (`DEFAULT_OPTIONS` кожного адаптера).

| Параметр | Типове значення | Адаптери | Де задається |
|---|---|---|---|
| `connect_timeout_ms` / `command_timeout_ms` | 10000 / 30000 | усі | `JANE_STORAGE_LIMITS__ADAPTERS__CONNECT_TIMEOUT_MS` / `…COMMAND_TIMEOUT_MS` або `params` |
| `pool_max_size` | 10 | усі (s3/minio — пул HTTP boto3) | `…__POOL_MAX_SIZE` або `params` |
| `pool_min_size` | 1 (sqlserver) / 0 (mongodb) | sqlserver, mongodb | `…__POOL_MIN_SIZE` (у сервісі типово 1) або `params` |
| `lock_timeout_ms` | 30000 | sqlserver (`sp_getapplock` в `ensure_schema`) | `…__LOCK_TIMEOUT_MS` або `params` |
| `lock_stale_ms` | 120000 | s3, minio (вік заявки доставки без знімка) | `…__LOCK_STALE_MS` або `params` |
| `retry_max_attempts` | 3 | s3, minio (спроб одного запиту botocore, `standard`) | `params` підключення |
| `chunk_bytes` | 4194304 (≤ 15 МіБ) | mongodb | `params` підключення |
| найбільший об'єкт | 104857600 | усі | ядро: `JANE_STORAGE_LIMITS__OBJECTS__MAX_OBJECT_BYTES` |

## Відомі обмеження

- `s3`/`minio`: `list_entities` і `list_objects` читають документи за префіксом (O(n) GET на сторінку, фільтри — на
  клієнті); порядок — за хешем канонічного ключа / `object_id`. Заявка доставки коміту, що «завис» довше за
  `lock_stale_ms`, вважається мертвою (як і блокування файлового адаптера).
- Порядок `list_entities` у sqlserver/mongodb/s3/minio — за хешем ключа (індексований keyset), у files/postgres — за
  канонічним ключем; контракт порядок не фіксує, повний обхід без пропусків і дублів перевіряє C-15.
- `sqlserver`: pymssql підставляє параметри на клієнті, тож RAW передається hex-рядком у `CONVERT(varbinary(max), …, 2)`
  (запит удвічі більший за об'єкт); тайм-аути pymssql — цілі секунди.
- `mongodb`: `pending` одного знімка — лише одна подія; коміт спершу переносить попередню (додатковий запис при
  частих оновленнях однієї сутності).
- botocore може брати власні змінні оточення / `~/.aws/config` для незаданих параметрів (endpoint, профіль) — у
  контейнері сервісу їх не задавати; облікові дані адаптер вимагає явно.

## Неперевірені інтеграції

- **AWS S3 — не перевірено на реальному сервісі** (немає тестового доступу). Адаптер `s3` перевірено на SeaweedFS 4.47,
  спільний протокол — також на MinIO. AWS підтримує `If-None-Match`/`If-Match` на `PutObject`; відповідь
  409 `ConditionalRequestConflict` обробляється як невдала умова (`CONFLICT`), але на AWS не перевірялася. SSE-KMS
  і virtual-hosted адресація — лише конфігурація клієнта, без перевірки на AWS.
- MongoDB з набором реплік, SQL Server з `encryption=require` / Azure SQL — не перевірялися (dev-стек: окремий `mongod`,
  SQL Server без примусового шифрування).
- Читання `s3://`-посилань (`content_uri`) сервісом через транзитне підключення — код ядра WP-07, наскрізно не перевірявся.
