# ADR-0004. Пісочниця для Python-екстракторів

- **Статус:** прийнято, діє.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

Екстрактори — Python-код із репозиторію пакетів, зокрема створений LLM (ТЗ §7–9). Його виконання треба обмежити за часом, ресурсами й доступами (ТЗ §11). Код обробляє вміст чужих сайтів, тож має розглядатися як недовірений. Пісочниця має працювати на Windows (Docker Desktop) і Linux.

## Варіанти

1. **Новий контейнер на кожен виклик через API Docker або Podman із жорсткими обмеженнями.**
2. Обмеження процесу засобами ОС (`setrlimit`, seccomp, nsjail, bubblewrap) — лише Linux і слабша ізоляція файлової системи.
3. Обмежений інтерпретатор (RestrictedPython) — ламає звичайні бібліотеки парсингу й не захищає від споживання ресурсів.
4. WebAssembly (Pyodide) — немає частини нативних бібліотек (lxml).
5. MicroVM (Firecracker, Kata) — сильніша ізоляція, але не працює на Windows і ускладнює розгортання.
6. Довгоживучий робочий процес для багатьох викликів — швидше, але стан одного виклику може вплинути на наступний.

## Рішення

Обрано варіант 1, реалізований Handler Runtime (`services/handler-runtime/src/jane_handler_runtime/docker_sandbox.py`).

- **Один виклик — один контейнер** `jane-sbx-<hex>` з образу профілю виконання (`python-extractor@1`, образ задає `JANE_HANDLER_RUNTIME_PROFILE_IMAGES`; будується командою `jane-handler-runtime build-image`). Після виклику контейнер видаляється.
- **Обмеження контейнера:** мережа вимкнена (`network_mode=none`), коренева файлова система лише для читання, `tmpfs` для `/tmp` з `noexec`, ліміти пам'яті (без swap), CPU і кількості процесів, `cap_drop=ALL`, `no-new-privileges`, користувач `65534:65534`, обмежений обсяг виводу. Межа часу — `sandbox.wall_time_ms` і примусове завершення.
- **Ліміти** — група `sandbox` моделі лімітів: `cpu_cores`, `memory_mb`, `wall_time_ms`, `max_output_bytes`, `max_processes`, `tmpfs_mb` ([ADR-0009](0009-limits-and-profiles.md)).
- **Рушій** — Docker або Podman (`JANE_HANDLER_RUNTIME_DOCKER_HOST`); OCI-runtime можна замінити, наприклад на gVisor (`JANE_HANDLER_RUNTIME_DOCKER_RUNTIME=runsc`).
- **Бекенд `subprocess`** без ізоляції — лише для довірених локальних пакетів і тестів; не стартує без `JANE_HANDLER_RUNTIME_ALLOW_UNSAFE_SUBPROCESS=true`.
- **Залежності пакета** обмежені набором бібліотек профілю; Registry перевіряє їх під час публікації ([ADR-0003](0003-package-registry.md)).

## Наслідки

- Код екстрактора не має мережі й не бачить файлів хоста; результат перевіряється за схемою пакета.
- Холодний старт контейнера додає затримку кожному виклику; вимірювання профілю `ci` перевіряє її проти частки `wall_time_ms` (сценарій L6 — [перевірка профілів](../operations/limits-validation.md)).
- Handler Runtime потребує доступу до API контейнерного рушія. У dev-стеку він монтує Docker-сокет хоста; це дає сервісу керування Docker хоста, тому поза розробкою потрібен окремий або rootless-рушій.
- Мережевий доступ пакета за allowlist (`access.network=allowlist`) не реалізовано: такі пакети відхиляються.
- Тести ізоляції виконуються лише на Linux (`just isolation`, job `isolation` у CI).
- Контейнери пісочниць, що лишилися після аварійної зупинки сервісу, автоматично під час старту не прибираються ([типові проблеми](../operations/troubleshooting.md#health-і-залежності)).
