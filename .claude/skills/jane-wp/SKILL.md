# Виконання WP проєкту Jane

Це plan.md §8, перетворений на чекліст. Йди по кроках і не пропускай.

## 1. Старт
1. Прочитай `TECHNICAL_SPECIFICATION.md`, `plan.md` §2–§4 і свій WP у §5, `CLAUDE.md`.
2. Прочитай звіти `docs/delivery/WP-NN.md` своїх залежностей (якщо вони є в твоїй ревізії) і `contracts/`.
3. Створи гілку: `git checkout -b wp/NN-<назва>` (назва — з `.claude/wp-paths.json`).
4. Створи в корені checkout файл `.jane-wp` з одним рядком `WP-NN`. Після цього хук пускає запис лише у твої шляхи.
   Файл у `.gitignore`, не комітиться. Змінювати його після створення не можна.
5. Переглянь свої шляхи: `.claude/wp-paths.json` → `packages.NN` + `common_allow`.

## 2. Робота
- Лише свої шляхи. Потрібна зміна в чужій області → запиши в звіт («Запити до інших власників»), не роби сам.
- Контракти лише з `contracts/`. Бракує поля чи ендпоінта → опиши потребу у звіті, не вигадуй.
- Сусіди — моки, згенеровані з контрактів. Сам компонент не мокати.
- Ліміти — з конфігурації (платформа → джерело → завдання), типові значення задокументувати в README.
- Тестові стеки: `docker compose -p jane-wpNN-<щось>`, власні порти й томи.
- Комітити часто, англійською, дрібними логічними кроками. Коміти лише у свою гілку, без push у `main`, без merge.
- Кросплатформність: Windows і Linux, `pathlib`, без bash-only скриптів у ключових командах.

## 3. DoD сервісного WP (plan.md §4)
- [ ] API за контрактом із `contracts/`, контрактні тести зелені.
- [ ] Unit- та інтеграційні тести; одна команда запуску, описана в README сервісу.
- [ ] README: незалежний запуск, конфігурація, ліміти з типовими значеннями, приклад виклику зі стороннього застосунку.
- [ ] Dockerfile, health-check, структуровані журнали, базові метрики; кілька екземплярів можливі.
- [ ] `CLAUDE.md` сервісу з трьох рядків: як запустити, як протестувати, де контракт.
- [ ] Критерій «Готово, коли» свого WP з plan.md §5 перевірено тестом або командою.
- [ ] `python .claude/hooks/jane_wp.py check-diff main` → 0 файлів поза власністю.

Для несервісних WP (00, 01, 13, 14) застосовуй пункти, що мають сенс, і критерій «Готово, коли» з §5.

## 4. Звіт
Заповни `docs/delivery/WP-NN.md` за шаблоном [report-template.md](report-template.md).
Вивід команд — справжній, скопійований із запуску (можна скоротити середину, але не підсумок).
Якщо щось не запускалося або перевірено лише на замінниках — напиши це прямо.

## Синхронізація з main
`main` рухається, поки ти працюєш (інші WP зливаються). Перевіряй `git merge-tree --write-tree main HEAD`.
Якщо є конфлікт (найчастіше `uv.lock`): `git rebase main` у своїй гілці (`git merge` у checkout виконавця заборонено).
Для `uv.lock` бери версію з `main` і перегенеруй `uv lock`, потім `uv lock --check`. Інші конфлікти — лише у своїх
шляхах; чуже не правиш. Після rebase — повний `just check`. Push і переписування `main` заборонені.

## 5. Завершення
1. Закоміть усе у свою гілку (включно зі звітом).
2. Статус у `docs/delivery/status.md` не змінюй — це робить координатор. У фінальному повідомленні вкажи:
   гілку, останній SHA, шлях до звіту, стан (`review` або `blocked` із причиною).

## Після рев'ю
Виправ кожне зауваження або обґрунтуй у звіті, чому ні. Додай у звіт розділ «Виправлення після рев'ю N»
з новим виводом команд. Не послаблюй тести, щоб закрити зауваження.
