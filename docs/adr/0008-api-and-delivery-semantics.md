# ADR-0008. Семантика API й надійна доставка

- **Статус:** прийнято, діє.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

ТЗ вимагає версіонованих API, асинхронних тривалих операцій зі станом і прогресом (ТЗ §4), підтвердження приймання результатів, повторних спроб, відновлення після збоїв і простежуваності (ТЗ §11). Повторна технічна доставка не має створювати повторних записів, а повторне отримання матеріалу з джерела — нове спостереження (ТЗ §11). Запізнілий результат не має замінювати новіший. Механізм має працювати й між автономними сервісами без Orchestrator.

## Варіанти

1. **HTTP API `/v1` з `Idempotency-Key` у кожного виконавця, `delivery_key` для етапів, job для тривалих операцій, витягування матеріалів колектора курсором.**
2. Ідемпотентність лише в Orchestrator — сторонній застосунок без Orchestrator не мав би захисту від дублів.
3. Push-доставка результатів (callback, webhook) від виконавця — потребує доступності викликача й власних повторів у кожного виконавця.
4. Пагінація зсувом (`offset`) — нестабільна при вставках.

## Рішення

Обрано варіант 1. Конвенції — [common.yaml](../../contracts/openapi/common.yaml), [errors.md](../../contracts/docs/errors.md), [data-ownership.md](../../contracts/docs/data-ownership.md).

- **Версіонування шляхом** — `/v1`; зворотна сумісність контрактів перевіряється в CI (`just contracts-compat`).
- **Помилки** — RFC 9457 `application/problem+json` з розширеннями `code`, `retryable`, `errors`, `trace_id`. Клієнт вирішує за `code` і `retryable`.
- **Асинхронні операції** — `202` з `Job`; стани `queued`, `running`, `cancelling`, `succeeded`, `failed`, `cancelled`; опитування `GET /v1/jobs/{job_id}`, скасування `POST /v1/jobs/{job_id}/cancel`. Строк зберігання — `transfer.job_retention_seconds`.
- **Ідемпотентність** — заголовок `Idempotency-Key` для змінних операцій: повтор із тим самим ключем повертає збережену відповідь із `Idempotency-Replayed: true`; поки перший запит виконується — `409 idempotency_in_progress`; той самий ключ з іншим тілом — `422 idempotency_key_reused`. Строк — `transfer.idempotency_ttl_seconds` (типово 86400 с). Заявки на ключ у спільних сховищах мають оренду, тому працюють між екземплярами.
- **Доставка етапів** — Orchestrator обчислює `delivery_key = sha256(run_id | stage_id | item_key)` і передає його як `Idempotency-Key`. Обробник на повтор повертає збережений `HandlerResult` з `duplicate: true`; Storage зберігає запис `delivery_key` у цільовому сховищі разом із даними.
- **Черга Orchestrator** — елементи етапів з орендою (`SELECT … FOR UPDATE SKIP LOCKED`); після закінчення оренди елемент бере інший воркер і повторює виклик із тим самим `delivery_key`.
- **Матеріали колектора** — витягування курсором із підтвердженням (at-least-once); непідтверджений матеріал видається повторно з тим самим `observation_id`. Буфер обмежено `queue.max_unacked_materials`: колектор призупиняє збір (backpressure).
- **Спостереження й порядок** — повторне отримання з джерела дає новий `observation_id` і новий запис історії. Storage упорядковує спостереження за `observed_at → sequence → observation_id`; старіше потрапляє лише в історію.
- **Пагінація** — курсорна.
- **Трасування** — W3C `traceparent` і `X-Request-ID` між сервісами ([моніторинг](../operations/monitoring.md#трасування)).

## Наслідки

- Повтори безпечні на всіх рівнях: клієнт, воркер Orchestrator, інший екземпляр виконавця. Наскрізні сценарії R-01…R-08 перевіряють це перезапусками, `docker kill`, розривом мережі й репліками ([приймання](../acceptance/README.md)).
- Виконавці зберігають відповіді за ключами протягом TTL — це місце в їхніх сховищах і причина, чому стан ідемпотентності має бути спільним для реплік ([масштабування](../operations/scaling.md)).
- Доставка «рівно один раз» досягається як «принаймні один раз» плюс дедуплікація за ключем; ключ має бути стабільним для одного логічного повтору.
