# Щогодинний моніторинг новин

Цей комплект налаштовує збір новин із восьми сайтів і чотирьох публічних Telegram-каналів у чинному стеку Jane. Кожен матеріал отримує джерело, заголовок, опис інфоприводу, тон авторського викладу, названі сутності та ставлення автора до кожної з них. Результати зберігаються як `news_article`; підтверджена повна ідентичність події також створює спільну `news_event`.

## Джерела та межі збору

Актуальні URL, ідентифікатори, мови та пакети правил зберігаються в [каталозі сайтів](sources.web.json) і [каталозі Telegram](sources.telegram.json). Регіон означає походження редакції; він не визначає мову чи місце описаної події.

| Регіон | Сайти | Telegram |
|---|---|---|
| Україна (`ukraine`) | Українська правда, Укрінформ | [Суспільне Новини](https://t.me/s/suspilnenews) |
| Європа (`europe`) | BBC News, The Guardian | [DW Главное](https://t.me/s/dwglavnoe) |
| США (`usa`) | NPR, ABC News | [Голос Америки](https://t.me/s/golosameriki) |
| Росія (`russia`) | РИА Новости, RT на русском | [ТАСС](https://t.me/s/tass_agency) |

Типовий розклад — інтервал `3600` секунд, `Europe/Kyiv`, `overlap: skip`: якщо попередній запуск триває, наступний пропускається. Кожний запуск сайту обмежено трьома статтями з RSS, кожний запуск Telegram — трьома найновішими текстовими повідомленнями з поточної відкритої сторінки. Бюджет вебобходу додатково враховує один навігаційний RSS-документ: за типових параметрів `max_pages_per_run` дорівнює `4`. Це обмежена вибірка, тому за інтенсивного потоку частина публікацій може залишитися поза аналізом. Параметри `--max-articles` і `--max-posts` змінюють ці межі.

Telegram читається через `https://t.me/s/<channel>` штатним Web Collector. Обліковий запис, Telethon і його секрети цьому сценарію не потрібні; доступна лише публічна вебсторінка з недавніми дописами, без повного архіву. Закриті канали й повідомлення без тексту не входять до цієї конфігурації.

Правила дотримуються `robots.txt`. Швидкість — не більше одного запиту за секунду на хост, із паузою щонайменше `1000` мс та одним паралельним завантаженням на хост. Інкрементальний збір і перевірка зміни вмісту зменшують повторні завантаження. Невідомі сторінки автоматично не передаються LLM.

## Налаштування та запуск

Потрібні Python/`uv`, запущений стек із Registry, Orchestrator, Web Collector, Handler Runtime, LLM і Storage, налаштований провайдер LLM та керовані підключення `raw-files` і `results-mongo` (MongoDB, [../documents/connections.json](../documents/connections.json)). Сценарій використовує ці підключення і перевіряє їхню наявність. Ключ API береться з локального файла стану стека; секрети не входять до пакетів чи каталогів.

Команди виконуються з кореня checkout. Для поточного проєкту `jane-demo` файл стану — `.jane/stack-jane-demo.json`. Якщо код запускається з іншого checkout, передайте фактичний шлях до цього файла через `--stack-file`; синтаксис Python/`uv` однаковий на Windows і Linux.

### Перевірка й експорт конфігурації

```powershell
uv run --all-packages python examples/news/setup_news.py check
uv run --all-packages python examples/news/setup_news.py export --output .jane/news-monitoring/config.json
```

`check` валідує маніфести, правила, джерела й завдання без звернення до запущених сервісів. `export` додатково записує конфігурацію з точними версіями та digest пакетів. Обидві команди друкують кількість валідованих пакетів і джерел; експорт не містить облікових даних підключень.

### Публікація й налаштування

```powershell
uv run --all-packages python examples/news/setup_news.py apply --stack-file .jane/stack-jane-demo.json --interval 3600 --max-articles 3 --max-posts 3
```

`apply` публікує та схвалює пакети, створює або оновлює джерела й завдання групи `news-analysis`. Чужий ресурс із тим самим ідентифікатором і іншою групою не перезаписується. Пакети мають незмінні версії: зміна архіву вже опублікованої версії вимагає нової версії. Оновлення ресурсів використовує ETag/`If-Match`.

Необов'язковий `--first-run-at` приймає час першого scheduled запуску у RFC 3339 UTC. Він задає початок розкладу; подальший інтервал залишається `3600` секунд. Без цього параметра конфігурація не містить фіксованої абсолютної дати першого запуску.

### Перший і звичайний запуск

```powershell
uv run --all-packages python examples/news/setup_news.py run --stack-file .jane/stack-jane-demo.json --exact --output .jane/news-monitoring/first-runs.json
uv run --all-packages python examples/news/setup_news.py run --stack-file .jane/stack-jane-demo.json --output .jane/news-monitoring/rss-runs.json
```

`--exact` підставляє одну попередньо перевірену `article_url` для кожного сайту; Telegram читає його поточну публічну стрічку. Звичайний запуск використовує RSS і недавні дописи. Команда записує ідентифікатори асинхронних запусків та завершується після їх створення; стан `succeeded` перевіряється окремо. Для вибіркового запуску додайте, наприклад, `--only news-web-bbc news-tg-suspilnenews`.

### Перевірка збережених результатів

```powershell
uv run --all-packages python examples/news/setup_news.py verify --stack-file .jane/stack-jane-demo.json --output .jane/news-monitoring/verification.json
```

`verify` читає сутності через Storage API, налаштування завдань і три останні запуски. Для кожного джерела потрібні хоча б одна збережена `news_article` з `evidence_validation: verified`, увімкнене завдання та інтервал `3600`. За невиконання критерію команда повертає код `1`. Наявність раніше збереженої сутності сама по собі не підтверджує успіх останнього запуску: дивіться `latest_runs` і час результатів у звіті.

## Поля результату

Повний формат визначають [схема news_article](packages/news.article-normalize/schemas/news_article.schema.json) і [схема news_event](packages/news.article-normalize/schemas/news_event.schema.json). Відсутні необов'язкові дані пропускаються.

| Поля | Значення |
|---|---|
| `source_id`, `source_name`, `source_kind`, `region`, `transport` | Джерело та спосіб отримання; `rss_article` або `telegram_public_web` |
| `url`, `material_id`, `content_sha256` | Точна стаття/допис, матеріал і digest вмісту, коли він наданий |
| `headline`, `headline_ukrainian`, `summary` | Оригінальний заголовок, український переклад і стислий виклад |
| `source_language`, `analysis_language` | Мова джерела; пояснення аналізу — українською (`uk`) |
| `published_at`, `fetched_at`, `edited_at` | Публікація, завантаження та редагування, якщо відомі |
| `reporting_kind`, `topics`, `locations` | Новина/думка/аналіз/пресреліз, теми й названі місця |
| `sentiment` | `positive`/`neutral`/`negative`, впевненість, пояснення та цитати |
| `entities[]` | Назва, стала назва, тип, роль, ставлення, впевненість і цитати щодо сутності |
| `event`, `event_grouping`, `event_id` | Інфопривід, рішення про групування та спільний ID за достатніх даних |
| `evidence_validation` | Результат буквальної перевірки цитат за оригіналом |

## Тональність і докази

`sentiment.label` описує тон автора. Нейтральне повідомлення про напад чи загибель залишається `neutral`, якщо автор не додає власної оцінки. `entities[].attitude` так само оцінює авторське ставлення до конкретної сутності. Наслідок події зберігається окремо як необов'язковий `factual_impact`: `beneficial`, `harmful`, `neutral` або `unknown`.

Кожна цитата має `attribution: author` або `quoted_source`. Чужа негативна заява не стає негативним ставленням автора. Для ненейтральної авторської оцінки потрібен доказ авторського формулювання. Перевіряльник звіряє дослівні цитати з відповідною статтею або конкретним Telegram-повідомленням; вигадана цитата завершує етап помилкою і не записується як перевірений результат.

`evidence_validation: verified` означає, що цитати знайдено в оригінальному тексті та пройдено перевірки формату й атрибуції. Це не незалежна перевірка правдивості повідомлених фактів. Семантичні оцінки, переклад, роль сутності та ідентичність події формує LLM; значення впевненості не є виміряною точністю моделі.

## Групування подій

Метод `exact_canonical_identity` для `actor_action` використовує п'ять полів `event.canonical`: `date`, `primary_actor`, `action`, `object`, `location`. Для конкретного `incident` ключ складається з дати, дії, названого об'єкта, міста та країни: невстановлений нападник не заважає зіставити ту саму подію. Явний час інциденту також входить до ключа та потребує цитати; пропущений моделлю відомий час блокує групування. Назви нормалізуються для точного порівняння; модель має давати сталі англомовні значення незалежно від мови статті.

Групування вимагає повного конкретного ключа, `identity_specificity: specific` та перевірених доказів. Для інциденту додатково перевіряється походження дати: явна дата або однозначне відносне посилання з підтвердженою датою публікації основної статті. Дати оновлення, футера чи пов'язаних матеріалів не використовуються. Невідома дата не замінюється датою публікації, невідома локація — столицею чи `global`; загальні об'єкти на кшталт «склад» не утворюють конкретної ідентичності.

Пакет має типовий поріг `min_grouping_confidence=0.9`. Цей новинний комплект явно налаштовує `0.75` через `--min-grouping-confidence`; початкова оцінка моделі зберігається без підвищення. Це евристичний параметр конфігурації: оцінки моделі не калібровані та не означають виміряну точність. Повний конкретний ключ, буквальні цитати, підтверджена дата й перевірка часу обов'язкові незалежно від порога. Схема вимагає підтвердження дати й часу; за обмежень зовнішньої структурованої відповіді адаптер передає цю схему в інструкціях і Jane суворо перевіряє отриманий JSON локально.

За браку даних стаття зберігається з `event_grouping.status: ungrouped` і причиною; `event_id` та спільна `news_event` не створюються. Це консервативне точне групування: різні канонічні формулювання того самого інфоприводу можуть залишитися окремими. Приблизний семантичний пошук чи злиття схожих подій цей комплект не виконує.

Для одного загального інциденту канонічний об'єкт — головний названий об'єкт, наприклад аеропорт; згадані термінали залишаються в описі та доказах. Коли текст описує окремі інциденти з різними компонентами, їхня відмінність зберігається; неоднозначна ідентичність не групується. Повторний аналіз із результатом `ungrouped` явно очищує попередній `event_id` у сховищі.

## Пакети та API

Orchestrator керує логічним потоком `collect → prepare → analyse → verify → store-news`; окремий `store-raw` зберігає оригінал відразу після збору. Екстрактори й трансформація виконуються у Handler Runtime, а сховища використовують адаптери Storage. Бізнес-результати не записуються колекторами напряму.

| Пакет | Призначення |
|---|---|
| `news.web-rules-*` | RSS discovery й межі дозволених доменів |
| `news.telegram-public-*-rules` | Поточна публічна сторінка каналу |
| [news.web-article](packages/news.web-article/jane-package.json) | Читабельна стаття та підтверджені метадані; paywall пропускається |
| [news.telegram-public-posts](packages/news.telegram-public-posts/jane-package.json) | Окремі текстові дописи зі своїми URL |
| [news.article-analysis](packages/news.article-analysis/jane-package.json) | Багатомовний аналіз за JSON Schema |
| [news.article-normalize](packages/news.article-normalize/jane-package.json) | Перевірка цитат, URL, атрибуції й точної ідентичності події |
| `jane.storage-files`, `jane.storage-mongodb` | RAW у `raw-files`; структуровані результати у `results-mongo` — колекції `news_article` і `news_event` |

API визначені контрактами [Orchestrator](../../contracts/openapi/orchestrator.v1.yaml), [Registry](../../contracts/openapi/registry.v1.yaml), [Handler](../../contracts/openapi/handler.v1.yaml), [LLM](../../contracts/openapi/llm.v1.yaml) і [Storage](../../contracts/openapi/storage.v1.yaml). Основні операції: `/v1/sources`, `/v1/tasks`, `/v1/tasks/{task_id}/runs`, `/v1/runs/{run_id}`, `/v1/entities`. POST із побічним ефектом використовують `Idempotency-Key`; доступ — Bearer token. Джерела та завдання належать Orchestrator, пакети — Registry, збережені сутності — Storage.

## Оновлення запущених сервісів

[deploy_llm.py](deploy_llm.py) розгортає виправлення LLM/Handler Runtime або параметри черги Orchestrator у наявному Compose-проєкті. Команди змінюють запущений сервіс; застосовуйте їх після перевірки відповідного коду.

```powershell
uv run --all-packages python examples/news/deploy_llm.py --stack-file .jane/stack-jane-demo.json --service llm
uv run --all-packages python examples/news/deploy_llm.py --stack-file .jane/stack-jane-demo.json --service handler-runtime
uv run --all-packages python examples/news/deploy_llm.py --stack-file .jane/stack-jane-demo.json --service orchestrator
```

Helper створює похідний образ на основі поточного образу сервісу й перевіряє SHA-256 кожного зміненого модуля. Для Orchestrator копіюються `engine.py` і `settings.py`, вмикається `engine.item_queue_ordering=run_round_robin`, а очікування/повтор ідемпотентної доставки задаються як `1000`/`5000` мс. Поточні налаштування `JANE_*` і опублікований порт зберігаються та перевіряються. Receipt записується поряд із файлом стека в `news-deploy/<service>/receipt.json`; Compose-дані з секретами не друкуються.

Почерговий режим обирає доступний запуск за його останньою активністю. Усередині запуску зберігається FIFO; ліміти паралельності, leases і delivery keys діють як раніше. Це дозволяє новим малим запускам отримувати чергу поряд зі старими великими. За типової конфігурації сервісу залишається `fifo`; параметр нового режиму вмикає саме deployment helper. Збір і зміни статусу також оновлюють час активності запуску.

Для спільного запущеного стека узгоджено місткість черг: Handler Runtime — 8 jobs; Web Collector — 32 jobs і тайм-аут job 4 години. `--service web-collector` змінює лише ці налаштування поверх поточного образу, зберігаючи код колектора. Паралельність HTTP на хост і ліміти новинного завдання залишаються окремими обмеженнями.

## Перевірка і діагностика

Докази перевірок і межі підтвердженого результату — у [VERIFICATION.md](VERIFICATION.md). Їх зібрано, коли результати зберігалися в PostgreSQL (`jane.storage-postgresql`, `results-pg`); [config.lock.json](config.lock.json) — знімок тієї розгорнутої конфігурації. Ці результати в `results-mongo` не переносяться, тож `validate_live.py --report-only` для старих квитанцій їх не знайде. Для локальної перевірки пакетів:

```powershell
uv run --all-packages pytest examples/news/test_analysis.py examples/news/test_web_article.py examples/news/test_telegram_sources.py examples/news/test_web_sources.py -q
```

| Симптом | Перевірка |
|---|---|
| Немає нових матеріалів | RSS/публічна сторінка, robots, scope, стан incremental; у Telegram можуть бути лише медіадописи |
| `unrecognized` на prepare | Читабельний текст, article containers, paywall; оригінал доступний у RAW |
| Помилка цитати/URL на verify | Діагностика запуску; доказ має належати саме цьому матеріалу чи допису |
| Усі статті `ungrouped` | П'ять полів canonical, конкретність, дата, докази й поріг confidence |
| Запуск queued/running надовго | Останні run/stage statuses, backlog, доступність LLM і ліміти; наявність старих сутностей не підтверджує цей запуск |
| Помилка незмінної версії пакета | Підвищити версію зміненого пакета, перевірити та повторити `apply` |

Прямий API-прогін ланцюжка на реальних матеріалах перевіряє аналіз і збереження; повний запуск через Orchestrator додатково перевіряє його чергу й доставку. Виконаний щогодинний тригер є окремим доказом роботи розкладу. Ці рівні перевірки наведено окремо у звіті.
