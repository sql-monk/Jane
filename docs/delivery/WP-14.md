## Результат

- У [`deploy/profiles/`](../../deploy/profiles/README.md) розміщено три schema-valid документи
  `PlatformLimits` (`dev-laptop`, `ci`, `single-node`) і кросплатформний валідатор. Числа без

  конфігурацію лімітів та оновлення/міграції. Окремо описано
  [резервування й відновлення](../operations/backup-restore.md) та

  перевірки цін і подій Telegram на основі контрактних JSON-зразків, із чітким переліком
  потрібних пакетів, підключень і зовнішнього доступу.

Три пропуски контрактних тестів: два тести LLM потребують PostgreSQL dev-стеку,
один тест шаблону сервісу ще не має OpenAPI-контракту. У цьому checkout не запускалися
`just up`, навантаження, повний процес, резервне відновлення або справжній Telegram.

## Конфігурація й ліміти

| Параметр | Джерело | Статус |
|---|---|---|
| `JANE_ORCHESTRATOR_LIMITS_FILE` | `deploy/profiles/<profile>.json` лише для першого заповнення БД | інтерфейс підтверджений кодом, застосування профілю на стеку не тестовано |
| `PUT /v1/limits/platform` | чинний документ + `If-Match` ETag | шлях для зміни без перезбирання; WP-14 не виконував його на реальному API |
| Ліміти source/task/stage | документи джерел/завдань, `GET /v1/limits/effective` | успадкування й hard caps за контрактом; профілі не виміряно |

## Відомі обмеження та неперевірені інтеграції

ADR-0007 залишає людині підтвердження реальних цільових середовищ. `infra/compose.yaml`
містить dev-залежності й testsite, а не всі застосунки. Наведені в контрактах product/price
package digest є демонстраційними. Сценарії з реальними сайтами, LLM-провайдером, Telegram,
SQL Server/MongoDB/S3 і відновленням backup **не перевірено на реальному сервісі**.

### Знахідки (для фази 2 і власників)

1. **Повний профіль як `LIMITS_FILE`.** storage, handler-runtime, registry, llm і assistant падають на старті:
   `jane_kit.config.LimitError: platform:/cfg/limits/platform.json: unknown limit(s) [...] for ServiceLimits`
   (перша спроба стеку з профілем у storage; для кожного сервісу перевірено в процесі). Приймають профіль лише
   orchestrator, web-collector і telegram-collector. Наслідок: іншим сервісам профіль доходить тільки в
   запитах оркестратора; для автономного використання — їхні типові значення. Зафіксовано xfail-тестом.
2. **Дайджест SDK ≠ дайджест registry.** `jane_extractor_sdk.package.build_archive` стискає deflate: для
   пакета каталогу `sha256:0ecb213c…` проти канонічного `sha256:5d5df843…`. Приклади закріплені на алгоритм
   registry (`jane_registry.archive`); він збігається з `jane_storage.packages`.
3. **Ліміт частоти на рівні збору (індикація, не вимірювання).** `HostLimiter` web-collector створюється на
   кожен збір (`crawler.py`), тож два одночасні збори одного хоста можуть разом перевищити
   `requests_per_second_per_host`: самоперевірка harness на локальному процесі один раз показала 20 запитів/с
   при ліміті 10. Також лімітер резервує час старту, а не момент відправлення: окремі запити одного збору
   інколи надходять парою з проміжком 1–15 мс при інтервалі 100 мс (середній темп нижчий за ліміт). На
   навантаженій машині ефекти відтворюються не щоразу; висновок дадуть L1/L2 фази 2.
4. **testsite не змінює ціну.** Часткове оновлення доведено історією (`completeness: partial`,
   `applied_fields`) і `field_orders` (ціна — від спостереження перевірки, назва — від каталогу), а не новим
   значенням ціни.

## WP-14c: локальний сплеск проти джитеру probe-site (2026-10-02)

**Гілка:** `wp/14c-rate-jitter-check`, база `e83de37`. CI
[36949099065](https://github.com/sql-monk/Jane/actions/runs/36949099065) на чистому
`e83de37` дав **fail** у `limits`: L1 і L2 мали по 200 запитів, по 47 стартів у
будь-якому вікні 1 с (межа 51) і найменше середнє п'яти проміжків 21,07/21,11 мс
(межа 15 мс). Але мінімальні окремі проміжки 2,13/2,71 мс не пройшли блокер
«жоден < 10 мс». У сирих подіях навколо них: L1 — 41,34 / 2,13 / 40,52 мс;
L2 — 42,09 / 2,71 / 40,61 мс. Це компенсований зсув доставки на сервері,
а не виявлений надлишок запитів за секунду. Інші L3–L8 пройшли.

У `metrics.rate_checks` блокер одного найкоротшого проміжку замінено перевіркою:
для **кожного** проміжку хоча б одна пара з сусіднім має середнє не нижче
`інтервал − допуск`. П'ятипроміжкове середнє й межа будь-якого вікна 1 с
лишаються блокерами; короткий одиничний проміжок лишається попередженням.
Контрприклади в адресних тестах: запізнілий старт із коротким наступним
проміжком дає `warn`; доданий близький запит і два незалежні потоки до одного
хоста дають `fail`.
