# ADR-0010. LLM-дослідження джерела виконує асистент, а не колектор

**Статус:** прийнято (WP-00, рев'ю 1, 2026-09-27)

## Контекст
ТЗ §6 і §13.1 п.1 перелічують «автоматичне дослідження джерела за допомогою LLM» серед способів
пошуку матеріалів. У `collector-rules.schema.json` є стратегія `llm_explore`. Якщо колектор
виконуватиме її сам, він залежатиме від асистента/LLM. Тоді колектор перестане бути автономним
(ТЗ §4), і з'явиться другий шлях витрат LLM поза бюджетами асистента.

## Рішення
1. У v1 **колектор не виконує `llm_explore`**. Реєстр стратегій Web Collector повертає
   `supported: false` у `POST /v1/rules/validations`. Збір із такою стратегією відхиляється з
   `validation_failed`. Нового API немає.
2. LLM-дослідження джерела — частина **onboarding асистента** (`assistant.v1`, WP-11). Асистент
   отримує вибірку через `collector.v1` (`/v1/fetches`, `/v1/collections`), аналізує її через
   `llm.v1` у межах бюджету й перетворює знахідки на звичайні стратегії (`seed_list`, `sitemap`,
   `feed`, `listing`, `url_template`, `api_feed`, `recursive`) у запропонованих правилах.
3. Стратегія `llm_explore` лишається в схемі як зарезервована. Її реалізацію в колекторі можна
   додати пізніше зворотно сумісно.

## Наслідки
- Колектор не має залежностей від LLM і асистента.
- Критерій 10 закривається рекурсивним обходом, Sitemap і детермінованими стратегіями. Критерій 4
  («підготовка екстрактора через LLM») закриває асистент.

## Альтернативи
- **Колектор викликає асистента для `llm_explore`.** Відхилено: це циклічна залежність і
  порушення автономності.
- **Видалити `llm_explore` зі схеми.** Відхилено: ТЗ згадує цей спосіб, тож варто зберегти місце
  для майбутньої реалізації.
