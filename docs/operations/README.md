# Експлуатація Jane v1

Ці інструкції описують наявний dev-стек та автономні сервіси на поточній ревізії. Сценарій
`single-node` є планом розгортання, **не підтвердженим робочим середовищем**. Перед робочим
використанням потрібні вимірювання з [валідації профілів](limits-validation.md), перевірка
резервного відновлення й погодження цільової машини.

## Незалежний запуск

1. Із чистого checkout установіть `uv`, Docker Compose і `just` за [DEVELOPMENT.md](../../DEVELOPMENT.md).
2. Виконайте `uv sync --all-packages`, потім `just up postgres testsite` (або `just up` для всіх
   dev-залежностей). `just env` показує фактичні адреси та згенеровані облікові дані. Не копіюйте
   цей вивід у звіти чи журнал команд.
3. Запускайте потрібний компонент за **його** README. Наприклад, Web Collector:
   `uv run --package jane-web-collector python -m jane_web_collector`; Orchestrator потребує власної
   PostgreSQL і `JANE_ORCHESTRATOR_DATABASE_URL` та запускається
   `uv run --package jane-orchestrator python -m jane_orchestrator`.
4. Перевірте `/v1/health`, `/v1/info` та `/metrics` кожного запущеного компонента. Для інтеграційних
   тестів використовуйте `just integration` у стеку цього checkout.

`infra/compose.yaml` зараз піднімає PostgreSQL, SQL Server, MongoDB, MinIO, S3-замінник, testsite і
proxy. Він **не піднімає автоматично всі застосунки Jane**. `just up` сам по собі не доводить
готовності наскрізного процесу.

## Спільний запуск

1. Кожен застосунок запускайте за його README з окремим портом і постійним сховищем. Передайте
   оркестратору `JANE_ORCHESTRATOR_EXECUTORS` або `..._EXECUTORS_FILE`: колектори, runtime,
   сховище RAW, registry, LLM мають коректні `base_url`, `role` і `capabilities`.
2. Для нової БД перед першим запуском оркестратора задайте
   `JANE_ORCHESTRATOR_LIMITS_FILE` на один із [профілів](../../deploy/profiles/README.md). Файл
   не змінює вже збережені платформні ліміти; для цього застосуйте `PUT /v1/limits/platform`
   з ETag. Для кожного сервісу перевірте його власні hard caps через `/v1/info`.
3. У робочому середовищі налаштуйте автентифікацію, TLS/reverse proxy, `secret_refs` і окремі
   облікові записи. Не зберігайте паролі в JSON профілю, прикладах чи Git. Адреси dev-стеку
   зв'язані з `127.0.0.1`; зовнішню доступність налаштовуйте свідомо.
4. Після запуску перевірте health усіх компонентів, `GET /v1/executors` оркестратора та один
   малий контрольований запуск з урахуванням `robots.txt` і зовнішніх обмежень.

Для паралельних перевірок задавайте різні compose-проєкти (`just up --project <унікальна-назва>`)
і використовуйте відповідне `just env --project <назва>`. Не запускайте `just down -v` для
стеку з даними, які потрібно зберегти: `-v` видаляє томи.

## Оновлення, міграції та відкат

1. Зафіксуйте ревізії коду, образів, контрактів, пакетів, активних версій етапів і ETag
   платформних лімітів. Заплануйте паузу нових запусків і дочекайтеся завершення активних або
   зупиніть їх через API скасування. У багатопроцесному стеку зупиніть планувальник і воркери.
2. Зробіть узгоджений backup за [резервуванням і відновленням](backup-restore.md) та перевірте
   його відновлення в ізольованому середовищі.
3. Перевірте release notes і міграційний шлях кожного сервісу. Зараз Orchestrator викликає
   `Database.migrate()` під час старту, LLM створює власну схему при старті, Web Collector має
   локальну схему стану; це **не гарантує** автоматичної сумісності довільного відкату.
4. Оновлюйте по одному компоненту, перевіряючи health, журнали міграції та контрактні smoke-тести.
   При помилці зупиніть нові записи. Відкат коду після зміни схеми можливий лише за
   документованої сумісності; інакше відновіть узгоджену копію даних і попередню ревізію разом.

Приклади джерела/завдань наведено в [examples](../../examples/README.md); статус їхньої
наскрізної перевірки там позначено окремо.
