# ADR-0006. Автентифікація й scopes

- **Статус:** прийнято, діє.
- **Звірено з кодом:** ревізія `48389a3`, 2026-10-11.

## Контекст і проблема

Сервіси викликають одне одного, їх викликають адмінка й сторонні застосунки (ТЗ §4, §10). Кожен сервіс має працювати окремо, тому автентифікація не може залежати від Orchestrator. Локальні тести мають запускатися без налаштування ідентичностей, а dev-стек і production — з ними.

## Варіанти

1. **Bearer-токен у кожному сервісі з трьома режимами: `none`, `api_key`, `jwt`; дозволи — scopes на операцію.**
2. Лише mTLS між сервісами — немає ідентичності користувача й складна видача сертифікатів стороннім застосункам.
3. Сесії Orchestrator — автономні сервіси залежали б від Orchestrator.
4. Власний сервер ідентичностей — поза обсягом платформи.

## Рішення

Обрано варіант 1. Реалізація — `libs/jane-kit/src/jane_kit/auth.py`, таблиці scopes — `libs/jane-kit/src/jane_kit/auth_scopes.py`; у контрактах scope кожної операції — розширення `x-jane-scope`.

- **`none`** — лише локальні тести: усі запити від `anonymous`; сервіс не стартує на не-loopback адресі без явного дозволу.
- **`api_key`** — статичні ключі в конфігурації сервісу: назва, scopes і SHA-256 ключа або `secret_ref`. Режим dev-стеку.
- **`jwt`** — токени зовнішнього IdP за JWKS: обов'язкові `iss`, `aud`, `exp`; лише асиметричні алгоритми; scopes з claim `scope`. Рекомендований для середовищ поза розробкою.
- **Scopes** — `<сервіс>:<дія>`: `collector:read`, `collector:run`, `handler:invoke`, `handler:test`, `connections:write`, `storage:read`, `llm:invoke`, `llm:admin`, `registry:read`, `registry:write`, `registry:approve`, `orchestrator:read`, `orchestrator:write`, `orchestrator:admin`, `assistant:use`.
- **Відмова закрита:** неповна конфігурація зупиняє старт; маршрут без scope у таблиці — помилка старту.
- **Без токена** — лише `GET /v1/health` і, типово, `GET /metrics`.
- **Міжсервісні виклики** — власний ключ сервісу з середовища (`*_TOKEN_REF`, `*_TOKEN`, `*_TOKEN_ENV`).
- **Адмінка** підтримує OIDC з PKCE; у dev-стеку оператор вводить ключ API, який зберігається лише в сесії вкладки.

## Наслідки

- Однакова модель у всіх сервісах; сторонній застосунок отримує окремий ключ із мінімальними scopes.
- Ключі `api_key` зберігаються лише як хеші; у dev-стеку `just up` генерує ключ для кожної ідентичності ([infra/README.md](../../infra/README.md#облікові-дані)).
- Режим `jwt` покритий unit-тестами `jane-kit`; у dev-стеку з реальним IdP не перевірявся.
- Ключ Assistant у Registry має `registry:approve` з атрибутом `actor: llm`, тому автоматична активація версій, створених LLM, можлива без людини, якщо політика пакета дозволяє ([ADR-0010](0010-llm-in-assistant.md)).
- Налаштування для оператора — [безпека експлуатації](../operations/security.md).
