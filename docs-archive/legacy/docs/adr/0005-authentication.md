# ADR-0005. Автентифікація сервісів і адмінки

**Статус:** прийнято (WP-00, 2026-09-27)

## Контекст
Сервіси викликають один одного (оркестратор → колектори/обробники/registry/llm, асистент →
llm/registry/колектор/runtime) і використовуються сторонніми застосунками автономно (ТЗ §4).
Адмінка — браузерний застосунок (WP-12) з керуванням підключеннями, кодом і лімітами. Потрібна
проста для dev і Windows схема, яку можна посилити в прод без зміни контрактів.

## Рішення
1. **Контракт один для всіх режимів:** `Authorization: Bearer <token>` (`bearerAuth` у кожному
   OpenAPI). `/v1/health` — без автентифікації. `/v1/info` повертає `auth_mode`.
2. **Режими сервісу** (конфігурація `auth.mode`, реалізує `jane-kit`):
   - `none` — лише для локальних тестів; сервіс слухає `127.0.0.1` і пише попередження в журнал;
   - `api_key` — статичні ключі з конфігурації (зберігаються хешем; значення — через `secret_refs`),
     кожному ключу призначено scopes; **типовий режим dev-стеку**;
   - `jwt` — JWT (RS256/ES256), перевірка за JWKS URL, `iss`/`aud`/`exp`, scopes у claim `scope`;
     **рекомендований для прод**. Сервісні облікові записи отримують токени через OAuth2
     client credentials у зовнішнього IdP (Keycloak, Entra ID тощо).
3. **Scopes** (перевіряє кожен сервіс для своїх операцій): `collector:read`, `collector:run`,
   `handler:invoke`, `handler:test`, `connections:write`, `storage:read`, `registry:read`,
   `registry:write`, `registry:approve`, `orchestrator:read`, `orchestrator:write`,
   `orchestrator:admin` (ліміти платформи, підключення), `llm:invoke`, `llm:admin`,
   `assistant:use`. Брак scope — 403 `forbidden`.
4. **Адмінка:** OIDC Authorization Code + PKCE у зовнішнього IdP; адмінка звертається до API
   сервісів через reverse proxy (WP-01) з префіксами `/api/<service>/v1/...`, передаючи
   access token користувача. Ролі IdP відображаються на scopes (`viewer`, `operator`, `admin`).
   Для dev — режим `api_key` з ключем адміністратора, який вводиться на сторінці входу адмінки й
   зберігається лише в `sessionStorage`.
5. **Делегування:** оркестратор і асистент викликають інші сервіси **власним** сервісним
   токеном; ідентичність користувача передається в `requested_by` (аудит), а не як токен.
6. mTLS між сервісами — опційно на рівні розгортання (service mesh/проксі), контракти не змінює.

### Уточнення реалізації B2 (2026-10-09)

Джерело — [WP-01g/B2](../delivery/M3/01g-auth.md); ці уточнення застосовуються до реалізації після злиття B2.
Таблиці операцій і scopes — [`jane_kit/auth_scopes.py`](../../libs/jane-kit/src/jane_kit/auth_scopes.py),
спільний захист — [`jane_kit/auth.py`](../../libs/jane-kit/src/jane_kit/auth.py).

- **Загальні маршрути.** `/v1/health` завжди відкритий. `/v1/info` вимагає будь-який дійсний токен без
  спеціального scope і повертає фактичний `auth_mode`; `/openapi.json` і `/docs` також вимагають токен.
  `/metrics` типово відкритий для скрейпера; `<PREFIX>METRICS_PUBLIC=false` вимагає дійсний токен.
- **Коди відмов.** Відсутній чи недійсний токен — 401 `unauthenticated` у `problem+json`;
  дійсний токен без потрібного scope — 403 `forbidden`. Недоступний IdP без ключів у JWKS-кеші —
  503 `service_unavailable` з `Retry-After`, оскільки валідність токена не вдалося перевірити.
- **Режим `none`.** Типово дозволений лише на loopback і супроводжується попередженням у журналі.
  За `HOST=0.0.0.0` застосунок не стартує; явне `<PREFIX>AUTH_NONE_ALLOW_REMOTE=true` є винятком із цього
  обмеження. Dev/e2e/профільні стеки використовують `api_key` і цього винятку не потребують.
- **Покриття операцій.** Сервіс передає повну таблицю `auth_scopes` у `create_app`; таблиця звіряється
  з маршрутами на старті. Операція без рядка не отримує дозвіл за замовчуванням. Автентифікація виконується
  до маршрутизації, перевірка scope — залежністю застосунку до обробника, включно з підключеними роутерами.

| Операції | Scopes (перелік означає «будь-який із») |
|---|---|
| Читання підключень виконавця | `connections:write` або базовий `collector:read` / `handler:invoke` |
| Зміна, видалення та перевірка підключень | `connections:write` |
| Читання/скасування job | scopes операцій, що створюють job у цьому сервісі; для колектора читання — `collector:read`, скасування — `collector:run` |
| Валідація правил колектора | `collector:read` або `collector:run` |
| Скидання стану колектора | `collector:run` |
| Читання провайдерів і псевдонімів LLM | `llm:invoke` або `llm:admin` |
| Бюджети й usage LLM | `llm:admin` |
| Оркестратор: читання / запис | відповідний `orchestrator:read` / `orchestrator:write` або `orchestrator:admin` |

Оркестратор використовує `token_ref` конкретного виконавця або власний `SERVICE_TOKEN_REF`;
асистент може задавати окремий `<NEIGHBOUR>_TOKEN_REF` кожному сусіду з власним `SERVICE_TOKEN_REF` як fallback.
Registry читає профілі runtime власним `RUNTIME_PROFILES_TOKEN_REF`. Нерозв'язне посилання не дозволяє старт.
У dev-стеку `just up` генерує ключі дев'яти ідентичностей у ігнорованому `.jane/stack-<project>.json`:
сервіси отримують хеші дозволених ключів, відкритий токен — лише його власник. `just env` показує ключ
адміністратора як `JANE_STACK_AUTH_ADMIN_API_KEY`; real-e2e адмінки читає той самий ключ зі стек-файлу.

JWT перевіряє підпис, `iss`, `aud`, `exp` і `nbf`; `alg=none` та HS* не приймаються.
JWKS оновлюється з TTL і cooldown, що враховує також невдалу спробу; чинний кеш використовується після
невдалого оновлення. `jwt`/OIDC із реальним IdP **не перевірено на реальному сервісі** — перевірки B2
використовували локальний JWKS. OpenAPI цим уточненням не змінюється.

## Наслідки
- Автономний сервіс можна використати з одним ключем API без IdP.
- Прод отримує стандартні JWT/OIDC без змін коду сервісів — лише конфігурація.
- Кожен сервіс сам перевіряє токен (немає централізованого шлюзу як єдиної точки відмови).

## Альтернативи
- **Лише mTLS** — складно для сторонніх застосунків і браузера.
- **Сесії в оркестраторі для адмінки і проксі всіх API через нього** — робить оркестратор
  обов'язковою залежністю й вузьким місцем; суперечить автономності.
- **Власний IdP у складі Jane** — поза обсягом; стандартний OIDC дешевший і безпечніший.
