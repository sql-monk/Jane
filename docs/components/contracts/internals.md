## Зв'язки між файлами

- OpenAPI сервісу посилається на `common.yaml` (параметри, відповіді-помилки, path items `Job`, `JobCancel`, `Health`, `Info`, `Connection*`) і на схеми `../schemas/*.schema.json`; приклади — `../examples/openapi/*.json`.
- Схеми посилаються одна на одну відносними `$ref` (`common/defs.schema.json#/$defs/...`).
- Інструменти розв'язують посилання лише в межах локальних файлів (`file://`), документи кешуються; YAML читається без перетворення дат, як JSON.
- Контракти автономних API (`collector`, `handler`, `storage`, `registry`, `llm`) не мають посилань — прямих чи транзитивних — на `orchestrator.v1.yaml` і `assistant.v1.yaml`.

## Приклади

| Каталог | Перевірка |
|---|---|
| `examples/schemas/<схема>/*.json` | Валідний за `schemas/<схема>.schema.json` |
| `examples/schemas/<схема>@<Def>/*.json` | Валідний за `#/$defs/<Def>` цієї схеми, наприклад `common/limits@PlatformLimits/ci.json` |
| `examples/invalid/schemas/...` | **Має** відхилятися тією самою схемою — перевіряє, що обмеження справді діють |
| `examples/openapi/*.json` | Example Objects (`summary`, `value`); валідуються за схемою місця, де на них посилаються |

Кожна операція має приклад тіла запиту (якщо воно є) і приклад кожної успішної відповіді — інакше лінтер падає. Ці приклади ж повертає мок.

## Перевірки лінтера

`check_contracts.py` виконує кроки по черзі й завершується з кодом `1`, якщо є хоч одна помилка:

1. Кожна JSON Schema валідна за метасхемою 2020-12, має `$schema` 2020-12, усі `$ref` розв'язуються.
2. Кожен OpenAPI-документ валідний як OpenAPI 3.1 (`openapi-spec-validator`).
3. Конвенції Jane:
   - `info.version`, `bearerAuth` і верхньорівневий `security`;
   - шлях починається з `/v1/`; є унікальний `operationId`, `summary`, `tags`, `responses`;
   - POST оголошує `Idempotency-Key` або має розширення `x-jane-no-idempotency-key: <причина>`;
   - захищена операція оголошує `401`;
   - помилки — `application/problem+json` зі спільною схемою `Problem`;
   - `202` повертає спільну схему `Job`;
   - є приклади тіла запиту й успішних відповідей, і вони валідні.
4. Приклади `examples/schemas/**` валідні, `examples/invalid/**` відхиляються.
5. Python-файли `contracts/python` компілюються й імпортуються.
6. Мок може віддати успішну відповідь для кожної операції кожного API; автономні API не залежать від контрактів Orchestrator і Assistant.
7. Redocly lint з правилами `contracts/redocly.yaml` (за наявності Node.js або обов'язково з `--require-redocly`).

## Алгоритм сумісності

`compat.py --base <ref>` бере `contracts/schemas`, `contracts/openapi` і `contracts/examples` на базовій ревізії (`git ls-tree` і `git show`) у тимчасовий каталог і порівнює з робочим деревом.

Напрям має значення:

- **тіла запитів і параметри** не можуть звужуватися — старий клієнт має й далі проходити валідацію;
- **тіла відповідей** не можуть втрачати гарантованих полів чи розширювати тип — старий клієнт має їх розуміти;
- **окремі схеми** (наприклад `Material`, що йде в обидва боки) перевіряються в обох напрямах.

| Рівень | Приклади змін |
|---|---|
| `BREAKING` | Видалено файл, операцію чи успішну відповідь; нове обов'язкове поле або параметр запиту; звужено тип, перелік чи межі запиту; поле відповіді видалено або стало необов'язковим; розширено тип відповіді; закрито `additionalProperties`; змінено `const` |
| `WARNING` | Нове значення переліку у відповіді; видалено необов'язкове поле; змінено `pattern`; змінено кількість альтернатив `oneOf`/`anyOf` (перевірити вручну) |

Код виходу `1`, якщо є хоч одне `BREAKING`. З `--oasdiff` додатково виконується `oasdiff breaking` для кожного OpenAPI-документа (бінарний файл або закріплений Docker-образ); помилка рівня `ERR` чи збій oasdiff теж дають код `1`. `--self-test` перевіряє сам компаратор на вбудованих випадках порушень і на тому, що образ oasdiff закріплено тегом і digest.

## Мок

`mock.py` будує маршрути з шаблонів шляхів і методів OpenAPI-документа (включно з path items через `$ref`). Для запиту:

1. Невідомий шлях — `404`, інший метод — `405` (Problem).
2. Немає обов'язкового заголовка або обов'язкового тіла — `422 validation_failed`.
3. Відповідь — перший приклад найменшого успішного статусу або вибраний `Prefer: code=` / `Prefer: example=`.
4. Для `202` додається `Location: /v1/jobs/<job_id>` з `job_id` прикладу.

Стану мок не має: той самий запит завжди дає ту саму відповідь, `Idempotency-Key` не запам'ятовується.
