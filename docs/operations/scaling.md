# Масштабування

ТЗ вимагає, щоб компоненти масштабувалися кількома екземплярами незалежно (ТЗ §4). У Jane це забезпечують спільне сховище стану сервісу, оренда (lease) з серцебиттям для незавершеної роботи та ідемпотентність за ключем. Сторінка описує, які сервіси можна запускати кількома екземплярами, за яких умов і що для цього перевірено.

## Підсумок за сервісами

| Сервіс | Кілька екземплярів | Умова | Перевірено наскрізно |
|---|---|---|---|
| Orchestrator | так | одна база `jane_orchestrator` | R-01: дві репліки, втрата оренди |
| Registry | так | одна база й одне blob-сховище; не `JANE_REGISTRY_DB=memory` | R-06: дві репліки читають опублікований архів |
| LLM gateway | так | `JANE_LLM_STORE=postgres`, одна база | R-04: повтор не списує бюджет двічі (один екземпляр) |
| Assistant | так | задано `JANE_ASSISTANT_STATE_DSN` | R-06: репліки ділять сесію й повтор |
| Handler Runtime | так | задано `JANE_HANDLER_RUNTIME_STATE_DSN` | R-06: повтор на інший екземпляр — дубль |
| Storage | так | дедуплікація — записом `delivery_key` у цільовому сховищі | R-06: друга репліка визнає доставку дублем |
| Web Collector | лише на одному хості | спільний каталог стану (`state.db`) | L2: дві репліки ділять ліміти хоста |
| Telegram Collector | лише на одному хості | спільний каталог стану | ні |

Сценарії — [тести наскрізні](../../tests/e2e/README.md); результати прогонів — [приймання](../acceptance/README.md).

## Оренда (lease) і повтори

Незавершена робота кожного сервісу з кількома екземплярами належить конкретному процесу через оренду з терміном дії, яку власник поновлює серцебиттям.

- **Ідемпотентність.** Запит з `Idempotency-Key`, який ще виконується на іншому екземплярі, отримує `409 idempotency_in_progress` (повторюваний); після завершення — збережену відповідь із заголовком `Idempotency-Replayed: true`. Заявка (claim) на ключ має оренду `in_progress_lease_ms` (типово 900000 мс) із серцебиттям `heartbeat_interval_ms` (типово 15000 мс); заявку зупиненого екземпляра інший може перехопити після закінчення оренди.
- **Асинхронні job.** Job належить екземпляру з орендою `job_lease_ms` (типово 60000 мс, у Handler Runtime — 30000 мс). Job, оренду якого ніхто не поновив, завершується як `failed`, тож клієнт бачить, що треба почати знову.
- **Доставка результатів.** Orchestrator повторює виклик обробника з тим самим `delivery_key`; обробник повертає збережений результат із `duplicate: true`, Storage не записує дані двічі.

Параметри оренди задаються змінними середовища груп лімітів сервісу: `JANE_<СЕРВІС>_LIMITS__STATE__*` (Handler Runtime, LLM gateway, Assistant), `JANE_REGISTRY_LIMITS__RECOVERY__*`, `JANE_ORCHESTRATOR_LIMITS__CLAIMS__*`. Типові значення кожного сервісу — `configuration.md` модуля.

## Orchestrator

- **Черга** — таблиця елементів етапів у базі Orchestrator. Воркери беруть елементи через `SELECT … FOR UPDATE SKIP LOCKED`; брокера повідомлень немає.
- **Оренда елемента** — `JANE_ORCHESTRATOR_LIMITS__ENGINE__LEASE_MS` (типово 30000) із серцебиттям `…__HEARTBEAT_MS` (типово 10000). Якщо воркер зник, інший перехоплює елемент після закінчення оренди. Перехоплення не витрачає спробу повтору; після `…__MAX_LEASE_RECLAIMS` (типово 5) перехоплень елемент завершується з помилкою як «отруйний».
- **Розклади** спрацьовують один раз на всі екземпляри: прострочені завдання блокуються `FOR UPDATE … SKIP LOCKED`, і `next_run_at` зсувається в тій самій транзакції. Перекриття запусків одного завдання (`schedule.overlap`) додатково захищене advisory lock.
- **Процеси.** Кожен процес API типово запускає `…__WORKERS` потоків воркерів (типово 2). Воркери можна винести в окремі процеси `python -m jane_orchestrator worker` — [запуск](running.md#окремий-процес-воркерів-orchestrator).
- **Міграції** при одночасному старті кількох екземплярів серіалізуються advisory lock.

## Колектори і ліміти хоста

Web Collector і Telegram Collector зберігають стан у SQLite (`<state_dir>/state.db`, режим WAL). Кілька процесів одного колектора працюють лише на одному хості зі спільним каталогом стану (`JANE_WEB_COLLECTOR_STATE_DIR`, `JANE_TELEGRAM_COLLECTOR_STATE_DIR`):

- збір належить екземпляру з орендою `lease_seconds` (типово 30 с) і серцебиттям `heartbeat_interval_ms` (типово 5000 мс); записи екземпляра, що втратив оренду, відкидаються;
- Web Collector узгоджує темп і паралельність запитів до одного хоста джерела між усіма зборами й екземплярами, що ділять каталог стану (`JANE_WEB_COLLECTOR_LIMITS__COLLECTOR__SHARED_HOST_LIMITS`, типово `true`). Слот зупиненого екземпляра звільняється через `shared_host_ttl_seconds` (типово 120 с);
- екземпляри з окремими каталогами стану — незалежні колектори: вони не узгоджують ліміти хоста між собою.

Після оновлення колектора всі екземпляри, що ділять каталог стану, оновлюються разом — [оновлення](upgrades.md#кілька-екземплярів-під-час-оновлення).

## Обмеження

- **Режими в пам'яті** — лише для одного екземпляра: Registry з `JANE_REGISTRY_DB=memory`, LLM gateway з `JANE_LLM_STORE=memory`, Handler Runtime і Assistant без DSN стану. Стан у них втрачається під час перезапуску.
- **Storage** тримає job і результати `GET /v1/invocations/{id}` у пам'яті екземпляра: опитувати job треба той самий екземпляр, що його прийняв. Дедуплікація записів працює між екземплярами.
- **`file://`-посилання й транзитні blob** доступні лише в межах одного вузла зі спільним томом. Обмін великими матеріалами між вузлами через S3-сумісне транзитне сховище не реалізовано — [ADR-0005](../adr/0005-large-materials.md).
- **Пісочниці Handler Runtime** запускаються на Docker-рушії екземпляра; скасування job зупиняє контейнер лише на цьому рушії.
- **Ліміти хоста** (`sandbox`, пам'ять, CPU) обмежують кожну пісочницю, а не сумарне навантаження хоста; сумарне навантаження обмежує `concurrency.max_parallel_invocations` на екземпляр.

## Масштабування в dev-стеку

`just up` не має прапорця `--scale`, а в `infra/compose.yaml` немає балансувальника перед репліками: proxy Caddy звертається до сервісу за його ім'ям у мережі Compose. Наскрізні тести запускають кілька реплік власною фікстурою `scale` (`tests/e2e/conftest.py`, `E2EStack.scale`) і звертаються до кожної репліки за її опублікованим портом. Ручне масштабування dev-стеку в межах документування не перевірялося.
