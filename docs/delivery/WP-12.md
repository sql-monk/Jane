## Результат

`web/admin/` — окремий pnpm-проєкт (TypeScript, React 19, Vite 8, pnpm 11.27.1 через corepack, власний
`pnpm-lock.yaml`, `tsconfig.json` → `../../tsconfig.base.json`), як просив WP-01. Бекенду немає: усі виклики —
`<api_base>/<service>/v1/...` через reverse proxy (ADR-0005).

- **Клієнти з контрактів.** [scripts/gen-api.mjs](../../web/admin/scripts/gen-api.mjs) генерує типи
  (openapi-typescript) для всіх 7 API і бандл JSON Schema з `contracts/schemas` у `src/api/generated/`;
  `pnpm lint` падає, якщо згенероване застаріло. Виклики — openapi-fetch
  ([src/api/client.ts](../../web/admin/src/api/client.ts)); Idempotency-Key на кожен POST з побічним ефектом,
  `If-Match` з ETag на PUT/PATCH, problem+json → `ApiError` за `code`, job — опитування з backoff
  (параметри з `config.json`). Редактори конфігурацій валідуються ajv за схемами контрактів
  ([src/lib/schema.ts](../../web/admin/src/lib/schema.ts)); сервіс лишається авторитетом (422).
- **Екрани ТЗ §10** ([src/pages](../../web/admin/src/pages)):
  - джерела (прапорець «Передавати в LLM невідомі сторінки», політика версій від LLM, ліміти, підключення,
    ефективні ліміти з походженням) і **стратегії обходу**: редактор правил колектора (пакет `collector-rules`) —
    картки 8 стратегій (seed_list, recursive, sitemap, feed, listing, url_template, api_feed, llm_explore),
    комбінування, область/robots/нормалізація, перевірка схемою, публікація нової версії;
  - завдання: форма, **розклади** (manual/once/cron/interval, overlap), **ланцюжок** як DAG (розгалуження,
    `select`, умови `when`), перевірка в оркестраторі (`task-validations`), запуск зараз / у тестовому режимі;
  - **активація й відкат** версій пакета в етапі з обов'язковою причиною (аудит), історія активацій, журнал аудиту;
  - пакети й правила колекторів: версії, статуси (погодити/відхилити/застаріла/yank з причиною), **тести без
    запису** (`handler test-runs` → TestReport), **diff** версій і від батька, **форк**, **оновлення батька**
    (`upstream`) з явним перенесенням (`upstream-ports`), прив'язки пакета до етапів;
  - **редактор коду** (CodeMirror 6, Python/JSON), локальний diff, маніфест зі схемою, публікація як нова
    draft-версія (вихідна незмінна);
  - запуски: **прогрес** етапів, **витрати** LLM, backpressure, **скасування**, елементи й **помилки**, помилки
    колектора, **повторна обробка** збережених RAW (з запуску або з матеріалу);
  - **матеріали** (storage objects, вміст як текст через HTTP Range, простежуваність матеріал → етап → версія),
    **результати** (стан сутностей, історія з запізнілими полями);
  - **групи проблем** (фільтр зокрема `unresolved`), вдосконалення через асистента на всіх прив'язках, результат
    (`unresolved`, пропозиція розширити типи даних), невідомі матеріали;
  - **сесії асистента**: підключення за назвою/посиланням, уточнення кандидата, вибірка, аналіз, **варіанти з
    охопленням, вартістю й ризиками**, прийняття, створення джерела/завдань з чернеток;
  - **підключення** (лише посилання на секрети, стан синхронізації, перевірка у виконавця), **LLM** (провайдери,
    псевдоніми, бюджети, витрати), **ліміти** платформи (defaults/hard_caps) й ефективні.
- **Автентифікація:** `auth.mode` = `api_key` (dev; ключ лише в `sessionStorage`), `oidc` (Authorization Code
  + PKCE, oidc-client-ts, токени в sessionStorage), `none` (локальні тести).
- **Секрети ніде не відображаються:** API несе лише `secret_refs`; додатково `redactSecrets` маскує схоже на
  секрет **у точках показу** — у `JsonView` (усі JSON-фрагменти відповідей) і на екрані «Підключення» (таблиця,
  посилання, завантаження в редактор). Після рев'ю 2 повідомлення помилок додатково обмежені локальним текстом,
  відомим кодом контракту та HTTP-статусом; довільні `title`, `detail`, `errors[].message`, `trace_id` і `details`
  сервісу не показуються. Централізовано в `unwrap` маски не застосовуються, щоб вони не потрапляли у форми
  конфігурацій і не поверталися в сервіс під час збереження. Форма підключення приймає лише `env:/file:/vault:`;
  вміст матеріалів не рендериться як HTML (eslint забороняє `dangerouslySetInnerHTML`).
- **Форки в завданнях:** на вкладці «Версії етапів» можна обрати поточний пакет етапу або будь-який його форк
  (`GET /v1/packages?fork_of=`), погоджену версію й активувати її з причиною (`ActivationRequest.package`).
- **Інтеграція з `just check`:** job `web` (lint, typecheck, test) зелений.
- **E2E:** [playwright.config.ts](../../web/admin/playwright.config.ts) піднімає 7 контрактних моків
  (`uv run contracts/tools/mock.py <api>`) і production-збірку (`vite preview`) як reverse proxy.
  38 сценаріїв у [e2e/](../../web/admin/e2e): 26 на моках (дані — приклади контрактів), 9 гібридних `@hybrid`,
  2 auth і 1 маскування помилки. Гібридні сценарії самі створюють дані через API реальних сервісів
  (orchestrator, registry, storage, handler-runtime, llm, assistant).
  Гібрид — `JANE_ADMIN_TARGET_<API>=<url>` замінює окремий мок реальним сервісом. Реальний стек:
  `pnpm e2e:real <url проксі>` виконує `auth.spec.ts`, регресію маскування та гібридні сценарії;
  сценарії `@mock` там пропускаються (див. «Режими e2e» у README і запит до WP-13).

Не зроблено в межах WP: Dockerfile/образ для статики (розгортання й запис адмінки в Caddy — WP-13); список сесій
асистента з сервера (немає ендпоінта — див. запити).

## Відомі обмеження

- `just web`/CI викликають `corepack pnpm --dir web/admin` з кореня репозиторію, де немає `packageManager`, тож
  corepack бере останній pnpm (зараз 12.8.1), а той відмовляється працювати з `packageManager: pnpm@11.27.1`.
  Обхід у своїх шляхах — `web/admin/pnpm-workspace.yaml` з `pmOnFail: warn` (лок-файл не змінюється, pnpm 12
  його приймає). Правильне виправлення — запуск з `cwd=web/<app>` (запит до WP-01).
- Моки повертають статичні приклади: e2e перевіряють рендер прикладів і точні тіла запитів, а не стан між
  запитами. Job-и мок-сервісу ніколи не завершуються — завершений job підставляється з прикладів контракту
  (TestReport) через `page.route`.
- openapi-typescript некоректно обробляє `$defs` і `discriminator` без `mapping` у JSON Schema контрактів;
  генератор це виправляє постобробкою (`fixGenerated`, покрито тестом).
- OIDC — не перевірено з реальним IdP.
- Список нещодавніх сесій асистента — у `localStorage` браузера (лише ідентифікатори), бо API не має списку.
- Handler-runtime перевірено з реальним registry: сценарій сам публікує SDK-пакет через API, а runtime завантажує
  його архів для тестів у Docker. `e2e/registry-standin.ts` залишено для ізольованого запуску runtime без registry.
- 26 сценаріїв `@mock` прив'язані до конкретних прикладів контрактів і в режимі реального стеку пропускаються.
  Еквівалентні сценарії `@hybrid` покривають частину функцій на реальних API. Неперевіреними залишаються
  наскрізний запуск з реальним колектором, витратами й помилками, групи проблем, активація/відкат в оркестраторі,
  редактор коду з публікацією та явне перенесення змін батька в реальному registry; потрібен інтеграційний стек WP-13.

## Неперевірені інтеграції

- Повний стек через reverse proxy (`pnpm e2e:real`) — **не перевірено**: на цій ревізії Caddy не маршрутизує
  `/api/<service>` і не роздає адмінку; потрібна інтеграція WP-01/WP-13.
- Перевірено гібридно на реальних сервісах з main (решта сусідів — контрактні моки): orchestrator (WP-09),
  registry (WP-05), storage (WP-07/08, files-адаптер), handler-runtime (WP-06, Docker), llm (WP-10), assistant (WP-11).
- web-collector (WP-02) у main є, але екран «Помилки колектора» бере `collection_id` із запуску оркестратора;
  без запуску завдання з реальним колектором він перевірений лише на моках.
- OIDC Authorization Code + PKCE — не перевірено на реальному сервісі (IdP).
