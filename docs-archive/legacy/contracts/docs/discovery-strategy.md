# Стратегія пошуку матеріалів у Web Collector

Інтерфейс: [`python/src/jane_contracts/discovery.py`](../python/src/jane_contracts/discovery.py).
Конфігурація стратегій — `collector-rules.schema.json#/$defs/Strategy` (поле `type` = `type_name`).

## Власність

| WP | Що реалізує |
|---|---|
| WP-02 (ядро) | `DiscoveryContext` (fetch, нормалізація, scope, robots, ліміти на хост, редиректи, умовні запити, розмір), черга з дедуплікацією й пріоритетами, глибина, повторні відвідування, збереження стану, `StrategyRegistry`, стратегії `seed_list` і `recursive`, API `collector.v1` |
| WP-03 | `sitemap` (+index, .gz), `feed` (RSS/Atom), `listing` (категорії, пагінація, пошук), `url_template`, `api_feed`; експортує `STRATEGIES` з `strategies/discovery/__init__.py` |
| — | `llm_explore` у v1 **не реалізується колектором**: реєстр стратегій повертає `supported: false` (`POST /v1/rules/validations`), збір із такою стратегією не стартує (`validation_failed`). LLM-дослідження джерела виконує onboarding асистента (WP-11, `assistant.v1`) і перетворює знахідки на звичайні стратегії в запропонованих правилах |

## Правила

1. Стратегія **не робить HTTP-запитів сама** — лише `ctx.fetch()`. Це гарантує, що robots.txt,
   межі домену, `exclude`, ліміти частоти й розміру діють для всіх стратегій однаково.
2. Стратегія **пропонує** `DiscoveredUrl`; ядро нормалізує, перевіряє scope/exclude/robots,
   дедуплікує (ключ — канонічний URL, `dedup` у правилах), обмежує глибину й розмір черги,
   упорядковує за пріоритетом (`priorities` правил + `priority` стратегії + `priority` кандидата).
3. `kind="navigation"` — сторінка потрібна лише для пошуку (sitemap, стрічка, сторінка списку,
   сторінка API); ядро не видає її як Material. `kind="material"` — кандидат у матеріали.
4. Комбінування: ядро викликає `on_fetched()` **усіх** стратегій для кожного отриманого ресурсу.
   Так `recursive` переходить за посиланнями зі сторінок, знайдених `sitemap`, а `listing` може
   реагувати на сторінки категорій, знайдені рекурсією.
5. Глибина: seeds мають `depth=0`; кандидат із `on_fetched` отримує `depth = resource.depth + 1`.
   `limits.crawl.max_depth` (ефективний, з урахуванням `limits` стратегії) застосовує ядро.
6. Стан: після кожної порції ядро зберігає `snapshot()` усіх стратегій разом із чергою; після
   рестарту викликає `restore()` і продовжує (критерій WP-02 «після kill обхід продовжується»).
7. Помилки мережі й HTTP ядро фіксує в `/v1/collections/{id}/errors`; `FetchRejected` —
   нормальна ситуація (стратегія пропускає URL), а не аварія стратегії.
8. Ліміти не зашиваються: усі числа — з `ctx.limits` або конфігурації стратегії.

## `ctx.fetch`: що спільне з ядром і що повертає (версія 1.1, R03)

Запит стратегії проходить **ту саму** політику й ті самі ресурси, що й запити черги ядра:

| Що | Як |
|---|---|
| scope, `exclude` | для URL і кожного кроку переадресації → `FetchRejected("out_of_scope")` |
| `robots.txt` / `owner_policy`, політика вихідних адрес | → `FetchRejected("access_denied_by_policy")` |
| ліміти на хост (інтервал, паралельність, `Crawl-delay`, `Retry-After`) | спільні з усіма зборами й `POST /v1/fetches` колектора (і з іншими екземплярами зі спільним сховищем стану, R15) |
| повтори, тайм-аути, розмір | `retries`; тайм-аути — з `limits` **стратегії**; тіло обрізається за `crawl.max_material_bytes` (`truncated`) |
| бюджети збору | запит рахується в `crawl.max_pages_per_run` / `max_bytes_per_run`; вичерпано → `FetchRejected("limit_exceeded")` |
| черга збору | URL стає рядком черги (один на канонічний URL): `material` видається як Material за правилами сторінки; `navigation` — ніколи |
| історія URL `state_key` | умовний запит (`conditional=True` і є валідатор) → 304 → `None`; `revisit` до `ctx.fetch` не застосовується |
| backpressure | для `kind="material"` — як для сторінки з черги |

Результат: `FetchedResource` з **будь-яким** кінцевим статусом, крім 304 (404/410/403/501 — теж ресурс);
`None` — 304, URL уже отримано в цьому процесі для цього збору або вже виданий матеріал, переадресація на відомий
URL, збій після повторів (мережа; 500/502/503/504, що так і лишились) — помилку ядро записало в `/errors`;
`FetchRejected("rate_limited")` — джерело просить чекати довше (`Retry-After`, `Crawl-delay`) за
`collector.max_retry_after_seconds` (службовий ліміт Web Collector із групи `collector` його налаштувань платформи,
не поле `limits.schema.json`) або відповідає 429 після повторів: стратегія має припинити запити в цьому зборі.

`on_fetched` ядро викликає для **кожної** відповіді з тілом, хай який статус (перевіряйте `resource.status`), але
не для 304, пропущених `revisit` сторінок, дублікатів (переадресація на відомий URL, відомий кінцевий чи
`rel=canonical` URL) і збоїв; ресурс із `ctx.fetch` отримують **усі інші** стратегії, але не та, що його запитала.

## API: POST і елементи як матеріали (версія 1.1, R22)

- `ctx.fetch(url, kind="navigation", method="POST", body=<JSON>)` — запит сторінки API методом POST з тілом JSON
  (`Content-Type: application/json`); лише для навігаційних документів, без умовних запитів; 307/308 повторюють
  POST з тілом, 301/302/303 продовжують GET; повтори — як для GET (запит має лише читати).
- `await ctx.emit_material(DiscoveredMaterial(url, strategy_id, body, fetched_at, media_type="application/json",
  ...))` — вміст, який стратегія вже має (елемент JSON), стає Material: `material_id` від канонічного `url`,
  scope і глибина стратегії, один матеріал на канонічний URL у зборі (URL закріплюється в черзі, інші стратегії
  його вже не завантажують), `revisit`/`dedup` за історією `state_key`, backpressure. `True` — матеріал видано.
  Так працює `api_feed` з `emit_items_as_materials: true`.

## Повторні збори (`mode: incremental`) і `lastmod` (R23)

- **Навігаційні документи** (sitemap, стрічки, сторінки API) стратегії читають через `ctx.fetch(...,
  conditional=False)` у кожному зборі повністю; матеріали, які вони перелічують, проходять `revisit`.
- **`lastmod`** кандидата (`DiscoveredUrl.lastmod`: sitemap з `use_lastmod_for_revisit`, `feed`, `api_feed` з
  `lastmod_path`), пізніший за попереднє завантаження URL (історія `state_key`), змушує ядро завантажити URL
  попри `revisit` (`never`, ще не сплилий `interval`); старіший або відсутній `lastmod` нічого не забороняє.
  Лічильник прогресу — `revisited_by_lastmod`.
- **Сторінки, з яких стратегія бере нові матеріали** (`listing`: категорії, пагінація, пошук), позначає
  необов'язковий хук `RefreshingStrategy.refresh_on_revisit(url) -> True`: ядро завантажує їх повністю в кожному
  зборі — без пропуску за `revisit` і без умовного запиту (304 обірвав би ланцюжок пагінації); елементи, які вони
  перелічують, проходять `revisit`. Лічильник — `refreshed`.
- **`recursive`** для пропущеної чи 304-сторінки отримує збережені посилання з історії URL, тож обхід іде далі.
- Обмеження: якщо сторінку списку в цьому зборі вже отримала інша стратегія до того, як `listing` про неї дізнався
  (посилання `rel=next` з попередньої сторінки), ядро не отримує її вдруге — ланцюжок на ній обривається.

## Очікувані перевірки на testsite (WP-01 `tests/fixtures/testsite/`)

- Кожна стратегія окремо знаходить очікуваний набір URL; у комбінації з `recursive` — об'єднання без дублів.
- Цикли посилань не зациклюють обхід; зовнішні посилання не завантажуються; `robots.txt` дотримано.
- `sitemap` читає index і `.gz`; `feed` — RSS і Atom; `listing` — пагінацію `rel=next` і параметром; `url_template` зупиняється після N поспіль 404.
