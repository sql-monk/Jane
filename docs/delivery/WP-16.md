## Рішення

1. **R04, 404 у `/v1/fetches`.** Обрано окремий `404 not_found` (а не лише документування 502) для обох
   колекторів: рішення клієнт приймає за `code` (конвенція контрактів), а «матеріалу немає» не повторюється
   (`retryable: false`), тоді як `source_unavailable` за каталогом повторюваний. Так само вже називала ці
   випадки помилка збору (`not_found` у `/errors` для HTTP 404/410). Це **зміна поведінки** Web Collector для
   сторінки 404/410 (було 502 з `details.http_status`, `details.http_status` лишився): у репозиторії `/v1/fetches`
   для неіснуючих сторінок не використовує жоден споживач (асистент має клієнт, але не викликає його; e2e
   `steps.py` бере наявні сторінки). Недоступний канал Telegram лишився `502` (`details.reason:
   channel_unavailable`): він може бути приватним чи без доступу, а не відсутнім.
2. **R04, монотонна `sequence`.** Значення лишилося в полі `revision.sequence` (його вже порівнюють storage й
   llm-обробник: `observed_at → sequence → observation_id`), але для Telegram це тепер `edit_date` × 1000 + номер
   ревізії з іншим текстом у межах секунди. Нові значення завжди більші за старі (секунди), тож порядок зі
   збереженими раніше спостереженнями не ламається; `source_revision` лишився «сирим» `edit_date`. Номер у межах
   секунди — порядок, у якому колектор **побачив** ревізії (Telegram дає лише поточний стан). Одноразовий fetch
   не веде стану й дає номер першої ревізії секунди. Файл стану старого формату мігрує при відкритті; екземпляри
   зі спільним `STATE_DIR` оновлюються разом (README).
3. **R15, межа.** Узгодження — через сховище стану, яке репліки вже ділять (SQLite на спільному томі одного
   вузла). Між вузлами спільного сховища у v1 немає (ADR-0007), тож екземпляри з різними каталогами стану лишаються
   незалежними колекторами — так і записано в `limits.schema.json`. Справедливість між екземплярами — FIFO-черга
   хоста: без неї (перша версія) зайнятий екземпляр, що миттєво забирав щойно звільнений слот, голодом морив
   інший (тест `overlap` це впіймав). Убитий екземпляр перестає обмежувати інших через
   `collector.shared_host_ttl_seconds` (120 с); його незавершений слот до того займає місце.
4. **R22, неоднозначності ТЗ/схеми.** (а) параметри пагінації (`cursor_param`, `page_param`) лишаються
   параметрами URL, `body` однаковий для всіх сторінок (схема не описує перенесення пагінації в тіло);
   (б) POST повторюється за `retries` як GET, тож `api_feed` POST має бути запитом лише на читання (так описано в
   схемі); 307/308 повторюють POST з тілом, 301/302/303 — продовжують GET; (в) елемент серіалізується як JSON
   (компактно, порядок ключів джерела) — це RAW елемента; `material_id` — від канонічного URL з `url_path`, тобто
   той самий об'єкт, що й HTML-сторінка за цим URL; (г) URL елемента не завантажується, тому `robots.txt` для нього
   не перевіряється (вміст отримано зі сторінки API, яку robots дозволив), але scope і глибина застосовуються;
   (д) елемент «закріплює» свій URL у черзі збору — один матеріал на канонічний URL, інша стратегія той самий URL у
   цьому зборі вже не завантажує; (е) `edited_at` — з `lastmod_path`, `http` і `locator.final_url` відсутні.
5. **R23, `lastmod`.** Найконсервативніше прочитання `use_lastmod_for_revisit`: `lastmod` лише **змушує**
   повторне відвідування (пізніший за попереднє завантаження), але ніколи не забороняє того, що дозволяє
   `revisit` — неправильний (застарілий) `lastmod` сайту не може приховати зміну. Сторінки списків —
   «навігаційні» за роллю: читаються повністю в кожному зборі (як sitemap/стрічки), бо 304 чи пропуск першої
   сторінки обривав ланцюжок пагінації; самі сторінки списку при цьому лишаються матеріалами (як було).
6. **R30, позначати чи пропускати.** Позначати: ТЗ §2/§5 — колектор віддає отриманий вміст із метаданими (RAW — до
   перетворень), а що обробляти, вирішує завдання умовами переходів (`material.metadata.service_action
   not_exists`). Пропуск дав би діри в `message_id`, які споживач не відрізнить від втрати даних, і незворотно
   прибрав би події каналу (закріплення, зміну назви). Службові повідомлення з оновлень (`getChannelDifference`)
   тепер теж видаються (раніше адаптер Telethon їх мовчки відкидав, а з історії — видавав), щоб поведінка не
   залежала від шляху читання.
7. **R03, `ctx.fetch`.** Контракт уже обіцяв `FetchRejected("rate_limited")`; код повертав `None`, і стратегія
   продовжувала запитувати джерело, яке просило зачекати. Виправлено код (не контракт). Збій після повторів
   (мережа, 5xx) лишився `None` з записом у `/errors` — так його вже обробляли стратегії WP-03.

## Відомі обмеження

- R15 діє між екземплярами з **одним** сховищем стану (один вузол); між вузлами — ні (v1, ADR-0007). Перевірено
  двома застосунками в одному процесі (окремі рушії, лімітери, з'єднання SQLite), окремими процесами ОС —
  не запускалось; багатопроцесні тести WP-02 (`test_multi_instance.py`) проходять із новим кодом.
- R15: кожен старт запиту робить одну-дві короткі транзакції SQLite (реєстрація, слот, розклад); у зайнятому
  сховищі запит чекає й пробує знову, не падає. Слот убитого екземпляра займає місце до `shared_host_ttl_seconds`.
- R04: понад 1000 різних ревізій за одну секунду отримали б однакову `sequence` (практично недосяжно);
  редагування, зроблені між зупиненим збором Telegram і тим, що дочитує історію без `pts`, не видно (як і до WP-16).
- R22: POST-запити й реальні JSON API зовнішніх сайтів **не перевірено на реальному сервісі** — лише testsite
  (POST — тестовий підклас незміненого обробника testsite, що відповідає на POST API як на GET).
- R23: якщо сторінку списку в зборі вже отримала інша стратегія до того, як `listing` про неї дізнався, ланцюжок на
  ній обривається (як і раніше, задокументовано).
- R30: розпізнавання `MessageService` в адаптері Telethon **не перевірено на реальному сервісі** (реальний канал
  2026-09-30 показав службове повідомлення з порожнім текстом через історію; тест — на записаному backend).
