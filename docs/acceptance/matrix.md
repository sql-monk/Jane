Стан на 2026-09-30: `main` містить WP-03 і код WP-12; повне приймання UI на реальному API
ще відкрите. На `main` `1306ad3` (злиття S-M2-03/08/09) повний `just e2e` дав `23 passed` без
skip: S-M1-01…06, S-M2-02, S-M2-03 (10), S-M2-05a, S-M2-08, S-M2-09, R-02, R-05, R-06; GitHub CI

LLM) поки лише на гілці `wp/13-acceptance` і в `main` не злиті. Це частина M1/M2, а не всі
критерії 1–12; приймання на одній фінальній ревізії `main` ще потрібне.

## Як читати

- **Що доводить** — яке спостережуване поводження системи вважаємо виконанням критерію.
- **Перевірка** показує, на чому саме проходить сценарій:
  - **Р** — реальний сервіс Jane або реальна інфраструктура (PostgreSQL, SQL Server, MongoDB, MinIO);
  - **З** — замінник *зовнішньої* системи, позначений явно: фейковий LLM-провайдер, записаний або фейковий
    клієнт Telegram, фейковий пошуковий провайдер, SeaweedFS замість AWS S3;
  - **Т** — тимчасовий замінник компонента Jane, якого ще немає в `main`. Він доказом не є, і коли WP злито,
    сценарій переходить на реальний компонент. Після WP-13t у сценаріях **Т** немає: оркестровані сценарії
    беруть архіви пакетів із реального registry, а `package-host` лишився тільки «шлюзом» `download_url`
    R-04 (**З** blob-сховища), архівів пакетів він не віддає. Повний e2e гілки WP-13t: [CI 37825596907](https://github.com/sql-monk/Jane/actions/runs/37825596907) на `b24ffc1`,
    `71 passed` без skip і xfail, з `JANE_E2E_REQUIRED=1`.
- **Вхід прямого виклику** — Material, який тест як сторонній застосунок сам формує з відповіді testsite
  (`jane_e2e.materials`, `collector.name = e2e-standin-collector`) і подає у прямий виклик виконавця
  (S-M2-05a, R-04 під час роботи). Це не **Т**: у такому сценарії немає ланки Jane, яку він заміщує, а
  перевіряється поводження виконавця з його вхідними даними (критерій 1: сторонній застосунок подає свої
  дані). Висновків про Web Collector із таких сценаріїв не роблять.
- **Віха** — plan.md §6. Критерій прийнято, коли його сценарії пройшли на **одній ревізії `main`**
  (plan.md §5, WP-13). Сценарії з **З** звітуються окремо від тих, що пройшли на реальних сервісах.
- **Докази WP** — перевірки з інших WP, що частково покривають критерій. Це тести самих WP, найчастіше з
  моками сусідів, тому вони **не замінюють** e2e-сценарію. Гілки, що ще не злиті в `main`, позначено «гілка».

## Критерії детально

### 1. Незалежний запуск і використання колектора та екстрактора стороннім застосунком
- **Що доводить.** Сторонній клієнт (тест як окремий процес) викликає колектор (`collector.v1`) і
  runtime екстрактора (`handler.v1`) напряму. Оркестратор, репозиторій і сховище при цьому не запущені або
  не використовуються. Пакет екстрактора береться локально (inline-архів), а не з репозиторію.
- **Сервіси.** web-collector, telegram-collector, handler-runtime, testsite.
- **Сценарії.** S-M1-01 (колектор `POST /v1/fetches` і runtime з локальним пакетом), S-M1-02
  (колекція з підтвердженням), S-M1-04
  (колектор `POST /v1/collections` + читання матеріалів, runtime через CLI на файлі), S-M2-02 (Telegram).
- **Перевірка.** Р для runtime і Web Collector; З для Telegram (записаний клієнт, реальний канал — лише за
  тестового доступу).
- **Віха.** M1 (Telegram — M2).
- **Докази WP.** WP-06 (main): CLI-тести пакета без інших сервісів (`test_isolation.py::test_example_package_tests_pass_through_cli`).
  WP-02 (main): `tests/test_autonomy.py::test_third_party_app_uses_collector_without_orchestrator`
  (окремий процес, реальний testsite). WP-04 (main): `test_collect.py::test_one_shot_fetch`
  (записаний клієнт). WP-05 (main): експортований пакет запускається в CLI runtime без репозиторію.
- **Стан e2e.** S-M1-01, 02 і 04 пройшли на гілці WP-13 з реальним Web Collector і runtime. Telegram
  перевіряється окремо в M2.

### 2. Налаштування ланцюжка з розгалуженням, екстракцією та збереженням
- **Що доводить.** Завдання оркестратора з DAG: `collect` → (`store-raw` ‖ `extract` → `store-products` ‖
  `analyze-problems`). Воно виконується на реальних виконавцях. RAW потрапляє у files, сутності — у PostgreSQL,
  а простежуваність `GET /v1/materials/{id}/trace` зв'язує матеріал, етап, результат і версію пакета.
- **Сервіси.** orchestrator, web-collector, handler-runtime, storage, llm, testsite, postgres.
- **Сценарії.** S-M1-01 (обидві гілки без оркестратора), S-M1-03 (M1-завдання через оркестратор), S-M2-11
  (розгалуження з умовами `when` і LLM-етапом).
- **Перевірка.** Р; LLM-етап — З (фейковий провайдер WP-10).
- **Віха.** M1 (без LLM-етапу), M2 (повний).
- **Докази WP.** WP-09 (main): `test_pipeline.py::test_m1_chain_web_to_raw_and_extraction_to_results`, де всі
  сусіди — контрактні фейки. WP-07 (main): `test_adapter_swap.py` на прикладах контрактів.
- **Стан e2e.** S-M1-01 і 03 пройшли на гілці WP-13 з реальними Web Collector, orchestrator, storage і
  handler-runtime. S-M2-11 пройшов на гілці `wp/13-llm-routing` з реальними orchestrator, Web Collector,
  handler-runtime, storage і llm: гілки за `material.format.media_type` і `result.status` виконуються
  лише за умов, LLM-етап отримує лише проблемні результати екстрактора, валідний вихід LLM записано в
  PostgreSQL, вихід поза схемою відхилено (`schema_mismatch`) і не записано, trace показує шлях
  матеріалу. LLM — З (фейковий провайдер WP-10). Архіви пакетів-фікстур тоді давав `package-host` (**Т**);
  після WP-13t S-M1-03 і S-M2-11 публікують екстрактор і LLM-пакет у реальному registry (погоджено), етапи
  посилаються на `package_id@version` з дайджестом registry, runtime і LLM-шлюз завантажують архів із
  registry й перевіряють дайджест.

### 3. Зміна сховища без зміни коду колектора й екстрактора
- **Що доводить.** Той самий вихід колектора й екстрактора (байт у байт) записується в інше сховище. Для цього
  змінюються лише `handler.package_id` і `connections.target` етапу, тобто конфігурація завдання. Код і образи
  колектора й екстрактора не змінюються.
- **Сервіси.** storage (усі адаптери), handler-runtime, orchestrator (варіант через завдання).
- **Сценарії.** S-M1-05 (PostgreSQL ↔ files через конфігурацію завдання), S-M2-08 (заміна в `TaskConfig` через
  `PUT /v1/tasks/{id}`, прогін на кожному з 6 адаптерів).
- **Перевірка.** Р (S3 — З: SeaweedFS).
- **Віха.** M1 (files ↔ PostgreSQL), M2 (усі адаптери, через оркестратор).
- **Докази WP.** WP-07 (main): `tests/test_adapter_swap.py`. WP-08 (main): ядро не змінено, образ містить 6 адаптерів.
- **Стан e2e.** S-M1-05 пройшов на гілці WP-13: стан сутності в PostgreSQL і files збігається.
  S-M2-08 пройшов для шести адаптерів на гілці WP-13 і в незалежному повторі, а після злиття —
  на `main` `1306ad3` (`just e2e` 23 passed, CI `36694741989` успішний). S3 — SeaweedFS (**З**).
  У тих прогонах архів екстрактора етапів давав `package-host` (**Т**). WP-13t перевів S-M1-05 і S-M2-08
  на реальний registry: екстрактор опубліковано й погоджено, етап зафіксовано дайджестом registry.

### 4. Підготовка екстрактора через LLM за матеріалами нового джерела
- **Що доводить.** Асистент отримує назву нового джерела (testsite) і робить таке: пошук через фейковий
  пошуковий провайдер, адаптивна вибірка сторінок через реальний колектор, кілька варіантів збору з
  оцінкою, пакет (прив'язка готового, форк або новий) у реальному репозиторії, тести пакета в реальному runtime.
  Після вибору варіанта користувачем створюються джерело й завдання.
- **Сервіси.** assistant, llm, registry, web-collector, handler-runtime, orchestrator, storage.
- **Сценарії.** S-M2-06.
- **Перевірка.** З для LLM (детермінований фейковий провайдер WP-10, **не** власний фейк асистента) і для
  пошукового провайдера (`SEARCH_PROVIDER=static`); решта — Р. Реальний LLM — «не перевірено на реальному
  сервісі», доки немає тестового доступу.
- **Віха.** M2.
- **Докази WP.** WP-11 (main): `test_onboarding.py::test_new_source_by_name_to_proposals_package_and_tests`
  та інші. Сусіди там — контрактні фейки, LLM — власний фейк асистента.
- **Стан e2e.** На інтеграційній гілці пройшли обидва варіанти S-M2-06: запит лише за назвою
  (`product` 17, `category` 7, `article` 8 у вибірці 54) та з підказками обходу (`product` 3,
  `category` 7, `article` 2 у вибірці 16). Другий варіант перевірив реальні registry/runtime,
  створення завдання і 17 збережених сутностей. Повний `just e2e` на цій ревізії: 33 passed; у `main`
  сценарій ще не інтегровано. LLM і пошук — **З**.

### 5. Окремі завдання повного збору товарів і періодичної перевірки цін
- **Що доводить.** Два незалежні завдання оркестратора: `shop-catalog` (повні картки) і `shop-price-check`
  (розклад, лише ціна й наявність). Друге оновлює лише передані поля (`completeness: partial`) і не стирає
  решту. Зміна або скасування одного не впливає на інше. Спеціального перемикання екстракторів немає.
- **Сервіси.** orchestrator, web-collector, handler-runtime, storage, registry, testsite.
- **Сценарії.** S-M2-04.
- **Перевірка.** Р; ціна змінюється штатним `PUT /_e2e/products/{slug}` testsite (WP-01e).
- **Віха.** M2.
- **Докази WP.** WP-09 (main): `test_done_when.py::test_full_collection_and_price_check_tasks_are_independent`
  (фейки сусідів). WP-07 (main): часткове оновлення (C-03).
- **Стан e2e.** S-M2-04 (`test_m2_prices.py`) пройшов 3 рази поспіль на гілці `wp/13e-price-check`, кожен
  прогін — в окремому Compose-проєкті з прибиранням. Використано пакети й документи WP-14 з реального

  `next_run_at` перевірки цін. Зміна її ліміту (2 сторінки) не вплинула на каталог: він і далі читав 23
  сторінки. Після WP-01e той самий S-M2-04 пройшов у e2e

### 11. Без увімкненої опції невідома сторінка не йде в LLM автоматично, після ввімкнення — іде
- **Що доводить.** Завдання з прив'язками екстракторів проходить testsite, де є сторінки типу `unknown`
  (`page_types`). Якщо `forward_unknown_to_llm: false`, лічильник викликів фейкового провайдера LLM (`GET
  /v1/usage`) не зростає, а матеріали видно в `/v1/unknown-materials`. Після ввімкнення прапорця на джерелі
  або завданні й повторного прогону виклики LLM є, і вони прив'язані до невідомих матеріалів.
- **Сервіси.** orchestrator (`GET /v1/unknown-materials`), web-collector, llm, assistant (S-M2-05a), handler-runtime, storage.
- **Сценарії.** S-M1-03 (без прапорця), S-M2-05a (асистент + LLM-шлюз напряму), S-M2-05 (маршрутизація в завданні).
- **Перевірка.** З для LLM, решта — Р. У S-M2-05a матеріал — **вхід прямого виклику** асистента: тест як
  сторонній застосунок формує його з відповіді testsite. Перевіряється політика прапорця асистента й
  виклики LLM, не Web Collector. Матеріал Web Collector тут не взято: його URL `http://testsite:8080/…`
  збігся б зі скриптом класифікації асистента у `tests/e2e/config/llm-seed.yaml` (S-M2-06).
- **Віха.** M2.
- **Докази WP.** WP-09 (main): `test_features.py::test_unknown_material_goes_to_llm_only_with_flag` (фейки).
  WP-11 (main): `test_unknown.py::test_flag_off_refuses_without_calling_llm`, `test_flag_on_*`. WP-10 (main):
  облік викликів і бюджети (`test_budget.py::test_exhausted_task_budget_stops_provider_calls[memory|postgres]`),
  ін'єкція в даних не змінює поведінки (`test_injection.py`).
- **Стан e2e.** S-M2-05a пройдено на реальних асистенті й LLM-шлюзі (LLM — З, фейковий провайдер WP-10):
  без прапорця `POST /v1/unknown-materials` дає 403 `access_denied_by_policy`, а лічильник запитів шлюзу
  (`GET /v1/usage`) не змінюється. З прапорцем job асистента завершується `succeeded`, і шлюз фіксує запити.
  S-M1-03 на гілці WP-13 підтвердив відсутність автоматичного forwarding. S-M2-05 пройшов на гілці
  `wp/13-llm-routing` через завдання оркестратора: з вимкненим прапорцем джерела 3 невідомі сторінки
  testsite лише зареєстровано (`forwarded_to_llm: false`), `GET /v1/usage` шлюзу — 0 запитів; після
  `PUT /v1/sources/{id}` з прапорцем повторний прогін передав рівно ці 3 матеріали етапу
  `unmatched_materials`, виклики LLM-обробника прив'язані до їхніх `material_id`, облік (`/v1/usage`,
  `Run.costs.llm`) ведеться. LLM — З. Архіви пакетів тоді давав `package-host` (**Т**); після WP-13t
  екстрактор і `e2e.llm-page-triage` беруться з реального registry за `package_id@version` і дайджестом.
  WP-01f додав пряму `/pages/faq-injection`; WP-13n провів її поруч зі звичайним FAQ через реальні
  testsite → Web Collector → Orchestrator → LLM ([CI 37002784428](https://github.com/sql-monk/Jane/actions/runs/37002784428)).
  Сторінка з ін'єкцією проходить як дані (**З**): обидві сторінки класифіковано як `faq`, два запити
  враховано, `hijacked` у виході немає. Виявити вплив ін'єкції цей сценарій не може: сід фейкового
  провайдера відповідає `faq` на будь-які дані з `<h1>FAQ</h1>` (`tests/e2e/config/llm-seed.yaml`).
  Стійкість до ін'єкції — unit WP-10 (`services/llm/tests/test_injection.py`); на реальній LLM не перевірено.
  Обмеження WP-09: визначення «невідомого» працює лише за наявності хоча б одного етапу з
  `bindings`, тож сценарій це враховує.

### 12. Збереження тестових RAW і результатів кожним початковим адаптером (або замінником)
- **Що доводить.** Для кожного адаптера (filesystem, PostgreSQL, SQL Server, MongoDB, MinIO, S3) через реальний
  storage-сервіс робиться таке: RAW-сторінка testsite записується (для files — `.html` байт у байт), сутність
  записується й читається через `storage.v1`, повтор дає дубль. Дані перевіряються і в самому сховищі.
- **Сервіси.** storage (+ адаптери WP-08), postgres, sqlserver, mongodb, minio, s3 (SeaweedFS).
- **Сценарії.** S-M1-01 (files, PostgreSQL), S-M2-08 (усі 6).
- **Перевірка.** Р; S3 — З (SeaweedFS, незалежна від MinIO реалізація; AWS S3 — «не перевірено на реальному сервісі»).
- **Віха.** M1 (2 адаптери), M2 (6).
- **Докази WP.** WP-07 (main): набір сумісності C-01…C-16 для files і PostgreSQL. WP-08 (main): той самий набір
  для SQL Server 2022, MongoDB 8, MinIO, SeaweedFS.
- **Стан e2e.** S-M1-01 перевірив files і PostgreSQL. S-M2-08 пройшов для всіх шести адаптерів

  повторі й на `main` `1306ad3` (`just e2e` 23 passed, CI `36694741989` успішний); S3 — SeaweedFS
  (**З**).

### 13. Зміна лімітів виконання без зміни коду; перевірені початкові профілі
- **Що доводить.** Ліміт (наприклад, `rate.requests_per_second_per_host`, `sandbox.wall_time_ms`,
  `crawl.max_pages_per_run`) змінюється через `PUT /v1/limits/platform`, конфігурацію джерела чи завдання
  або змінну середовища. `GET /v1/limits/effective` показує новий ефективний ліміт із походженням, а
  поведінка наступного прогону відповідає новому ліміту. Образи сервісів не перезбираються. Профілі
  `dev-laptop`, `ci`, `single-node` (ADR-0007) виміряно й перевірено — це WP-14.
- **Сервіси.** orchestrator, усі виконавці (`GET /v1/info` → `limits`).
- **Сценарії.** S-M2-09.
- **Перевірка.** Р.
- **Віха.** M2 (зміна лімітів), M3 (профілі WP-14).
- **Докази WP.** WP-06 і WP-07 (main): ліміти з `LIMITS_FILE` і змінних середовища, `min(запит, hard_caps)`.
  WP-09 (main): `test_done_when.py::test_changing_limits_needs_no_code_change`. WP-10 (main):
  `test_service.py::test_input_limit_from_config`, `test_rate_limit_per_scope`; WP-11 (main):
  `test_units.py::test_limits_resolution_and_hard_caps`; WP-02, 04 (main) — тести лімітів із конфігурації. У e2e вже видно, що ліміти запиту діють без зміни коду:
  `limits.sandbox.wall_time_ms` задається з `JANE_E2E_SANDBOX_WALL_TIME_MS`.
- **Стан e2e.** S-M2-09 пройшов на гілці WP-13, незалежно і на `main` `1306ad3` (`just e2e`
  23 passed, CI `36694741989` успішний) для `crawl.max_pages_per_run=1→2` (platform→task):
  ефективне значення, походження й фактичні лічильники колектора/оркестратора збігаються (архів екстрактора
