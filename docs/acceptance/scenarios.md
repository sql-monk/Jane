# Приймальні сценарії

Сценарії, якими перевіряються критерії приймання ТЗ §12. Кожен сценарій виконується автоматично в `tests/e2e/` на справжніх сервісах у Docker; запуск і прибирання — [tests/e2e/README.md](../../tests/e2e/README.md), відповідність критеріям і докази — [матриця приймання](README.md).

Ідентифікатори: `S-M1-*`, `S-M2-*`, `S-M3-*` — функціональні сценарії віх M1–M3; `R-*` — надійність (збої, повтори, репліки); `L2` — спільні ліміти хоста.

## Перший наскрізний зріз (M1)

| Сценарій | Що демонструє | Тест |
|---|---|---|
| S-M1-01 | Сторонній застосунок без Orchestrator: Web Collector отримує сторінку → RAW HTML у файли й паралельно локальний екстрактор → сутності в PostgreSQL; повторна доставка — дубль | `test_m1.py::test_s_m1_01_collector_fetch_to_files_and_extraction_to_postgres` |
| S-M1-02 | Збір `collector.v1` із курсором і підтвердженням; непідтверджена сторінка видається повторно з тим самим `observation_id`; кожен матеріал проходить ланцюжок | `test_m1.py::test_s_m1_02_collection_pull_with_ack_then_chain` |
| S-M1-03 | Завдання Orchestrator: збір → збереження RAW ‖ екстракція (прив'язка до `/product/*`) → збереження сутностей; простежуваність і «рівно один раз» | `test_m1.py::test_s_m1_03_orchestrated_task_web_to_files_and_postgres` |
| S-M1-04 | Рекурсивний обхід лише через `collector.v1` з правилами в запиті; екстрактор через CLI Handler Runtime на зібраній сторінці | `test_m1.py::test_s_m1_04_collector_and_extractor_used_by_a_third_party_app` |
| S-M1-05 | Два завдання відрізняються лише етапом збереження (PostgreSQL або файли): той самий колектор, той самий пакет і дайджест екстрактора, той самий стан сутностей | `test_m1.py::test_s_m1_05_storage_swap_is_task_configuration_only` |
| S-M1-06 | Повторне отримання того самого матеріалу (другий запуск) — нове спостереження: новий RAW і нова подія історії | `test_m1.py::test_s_m1_06_new_observation_is_a_new_record` |

## Функціональні сценарії M2

| Сценарій | Що демонструє | Тест |
|---|---|---|
| S-M2-01 | Пакети всіх типів в одному Registry: незмінні архіви, завантаження в runtime за дайджестом, `digest_mismatch`, незмінний форк, явне перенесення змін батька | `test_m2_registry.py`, `test_m2_registry_types.py` |
| S-M2-02 | Telegram (записаний бекенд): історія, нове повідомлення й редагування — окремі спостереження; технічна повторна доставка — ні | `test_m2_telegram.py` |
| S-M2-03 | Стратегії пошуку Web Collector окремо (рекурсія, Sitemap, стрічки, категорії, пошук, API, шаблон URL) і в комбінаціях | `test_m2_discovery.py` |
| S-M2-04 | Окремі завдання повного каталогу й перевірки цін за розкладом; часткове оновлення полів | `test_m2_prices.py` |
| S-M2-05 | Невідомі сторінки потрапляють у LLM лише після ввімкнення прапорця джерела; ін'єкція інструкцій у сторінці не змінює класифікації | `test_m2_llm_routing.py`; варіант через Assistant — `test_m2.py` (S-M2-05a) |
| S-M2-06 | Нове джерело за назвою: кандидати, адаптивна вибірка через справжній колектор, плани збору з охопленням, вартістю й ризиками, новий екстрактор від LLM із тестами, джерело й завдання в Orchestrator, збережені сутності | `test_m2_assistant.py` |
| S-M2-07 | Вдосконалення екстрактора на проблемних прикладах: нова версія проходить старі й нові тести для всіх прив'язок, активація, повторна обробка, відкат; заборона автоматичних змін | `test_m2_assistant.py` |
| S-M2-08 | Одне завдання по черзі на всіх шести адаптерах Storage (PostgreSQL, SQL Server, MongoDB, MinIO, S3, файли) лише зміною ревізії завдання | `test_m2_storage.py` |
| S-M2-09 | Ліміт сторінок рівня платформи, потім рівня завдання, змінює реальний збір без перезбирання | `test_m2_limits.py` |
| S-M2-11 | DAG завдання з умовами `when` на типі матеріалу й статусі результату; LLM-етап отримує лише проблемні результати; вихід LLM перевіряється схемою | `test_m2_llm_routing.py` |

## Надійність

| Сценарій | Що демонструє | Тест |
|---|---|---|
| R-01 | Дві репліки Orchestrator на одній базі: репліку з орендою довгого виклику вбито; інша перехоплює оренду, отримує `409 idempotency_in_progress`, потім збережений результат; спроба не витрачається | `test_reliability_orchestrated.py` |
| R-02 | Результат, доставлений до збою (`docker kill` Storage і Handler Runtime), після перезапуску — дубль; перезапуск Registry зберігає пакети | `test_reliability.py`, `test_r06_storage_registry.py` |
| R-03 | Розрив мережі до Storage посеред запуску: повтор чекає backoff, дублікатів немає | `test_reliability_orchestrated.py` |
| R-04 | Повтор із тим самим `Idempotency-Key`/`delivery_key` до кожного виконавця — після виконання й поки перший запит ще триває; LLM не списує бюджет двічі | `test_r04_idempotency.py`, `test_r04_active_replays.py` |
| R-05 | Запізніле старіше спостереження потрапляє в історію, а не в актуальний стан | `test_reliability.py` |
| R-06 | Кілька екземплярів Handler Runtime, Storage, Registry, Assistant ділять стан ідемпотентності й дані | `test_reliability.py`, `test_r06_storage_registry.py`, `test_r06_assistant_replicas.py` |
| R-07 | Вдосконалення з `docker kill` Assistant або Handler Runtime посередині, під навантаженням: публікується рівно одна версія; перерваний job завершується після оренди | `test_r07_improvement_restarts.py` |
| R-08 | Обмежена черга: колектор призупиняє збір (`paused_by_backpressure`) і ніколи не тримає більше `queue.max_unacked_materials` непідтверджених матеріалів | `test_reliability_orchestrated.py` |
| L2 | Дві репліки Web Collector ділять паралельність і темп запитів до одного хоста; слот убитої репліки звільняється за TTL | `test_shared_host_replicas.py` |

Зовнішні сервіси замінено: LLM — провайдер `fake`, Telegram — записані канали, пошук — статичний список, сайти — тестовий сайт ([замінники](../../tests/e2e/README.md#замінники-зовнішніх-сервісів)).
