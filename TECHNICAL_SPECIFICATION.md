# Jane — технічне завдання

## Модульна платформа збору та обробки даних

**Версія:** 0.2 — деталізовано налаштування обходу, роль LLM, адаптери та ліміти  
**Дата:** 2026-09-27  
**Статус:** проєктування, без початку реалізації

## 1. Призначення

Створити **Jane** — модульну платформу, яка отримує матеріали із зовнішніх джерел, перетворює їх на структуровані дані та передає результати в обрані сховища або інші системи. Початкові джерела — сайти та Telegram-канали.

Користувач задає, звідки отримати матеріали, які дані потрібні, як їх обробити та коли виконувати завдання. Наприклад, Jane може зібрати повні картки товарів, окремим завданням регулярно перевіряти їхні ціни або витягувати події з новинних повідомлень.

Велика мовна модель (LLM) допомагає визначити доступні сутності, підібрати або створити код їх витягування та вдосконалювати його на проблемних прикладах. Користувач зберігає можливість переглядати, редагувати, тестувати й активувати цей код через адміністративний інтерфейс.

Jane має складатися з автономних компонентів: їх можна поєднати в платформу або використовувати окремо у сторонніх застосунках.

Проєкт названо на честь докторки Джейн Гудолл. Він не має офіційного зв’язку з Jane Goodall Institute; назва не означає його підтримки або схвалення.

## 2. Основний принцип

Терміни, використані в документі:

| Термін | Значення |
|---|---|
| **Джерело** | Сайт, Telegram-канал або інше зовнішнє місце отримання даних |
| **Колектор** | Компонент, який отримує матеріали з джерела та повертає їх разом із метаданими |
| **RAW** | Оригінальний вміст у вигляді, отриманому колектором, до подальших перетворень |
| **Обробник** | Компонент, який виконує операцію над переданими даними: збереження, витягування, виклик LLM або інше перетворення |
| **Екстрактор** | Тип обробника, який витягує структуровані поля й сутності з матеріалу |
| **Сутність** | Об’єкт, описаний набором полів, наприклад товар із назвою та ціною або подія з описом і часом |
| **Оркестратор** | Сервіс, який запускає етапи завдання, передає між ними дані та контролює виконання |
| **Завдання** | Налаштований процес збору й обробки даних з одноразовим запуском або розкладом |

Загальна модель роботи:

```text
Збір даних → Обробка → Обробка → …
```

Обробка може розгалужуватися. Наприклад, отриману сторінку можна одночасно передати на збереження оригіналу та витягування товарів:

```text
Колектор
  ├── Збереження RAW
  └── Екстрактор
        ├── Збереження результатів
        └── Проблемні приклади → Аналіз LLM
```

Порядок етапів, умови переходів і розгалуження задаються в конфігурації завдання. Збереження RAW є окремим етапом, а не прихованою функцією колектора.

## 3. Компоненти платформи

| Компонент | Відповідальність |
|---|---|
| **Data Collectors** | Отримання даних із зовнішніх джерел |
| **Обробники** | Виконання операцій над отриманими даними |
| **Репозиторій обробників** | Зберігання пакетів обробників різних типів, їхніх версій, тестів та форків |
| **Оркестратор** | Виконання завдань, розклади, передача даних між етапами, контроль стану й помилок |
| **Адміністративний інтерфейс** | Налаштування платформи, редагування коду, тестування та спостереження за роботою |

Початкові колектори:

- **Web Collector** — отримання вебсторінок та інших вебматеріалів.
- **Telegram Collector** — отримання повідомлень, історії та редагувань каналів.

Початкові види обробників:

- збереження RAW або результатів;
- виконання Python-екстракторів;
- звернення до LLM.

Архітектура має дозволяти додавати нові колектори й обробники без перероблення ядра оркестратора.

## 4. Автономність і взаємодія

Кожен сервіс має власну конфігурацію, документований API, тести та інструкцію незалежного запуску.

Колектор можна використати зі стороннього застосунку, отримавши від нього дані без оркестратора, екстрактора чи сервісу збереження. Аналогічно екстрактор може обробити передані користувачем дані з локальним пакетом правил.

Міжсервісна взаємодія відбувається через **версіоновані API**. Сервіси не звертаються безпосередньо до внутрішніх таблиць інших сервісів.

Короткі операції можуть повертати результат одразу. Тривалі виконуються асинхронно: API повертає ідентифікатор завдання, за яким доступні стан, прогрес і результат. Для великих матеріалів передбачається потокове передавання або передавання посилання.

Компоненти повинні підтримувати незалежне масштабування кількома екземплярами.

## 5. Дані та збереження

Колектор повертає структуру, що містить отриманий вміст і метадані:

- джерело та ідентифікатор матеріалу;
- URL або інше посилання на першоджерело;
- час отримання;
- час публікації та редагування, якщо їх надає джерело;
- відомості про формат і ревізію матеріалу.

Обробник повертає результат за своїм контрактом та діагностику: екстрактор — структуровані сутності, обробник LLM — результат запиту, обробник збереження — підтвердження запису та ідентифікатори або посилання на збережені об’єкти. Результат повинен бути пов’язаний із вхідними даними та версією пакета обробника.

**Колектори та екстрактори не зберігають бізнес-результати безпосередньо в БД.** Для цього використовуються обробники збереження. Початковий набір адаптерів: PostgreSQL, SQL Server, MongoDB, MinIO, S3 та файлова система. Файловий адаптер за замовчуванням зберігає RAW вебсторінок у HTML, а інші результати — у JSON; формат можна перевизначити в конфігурації етапу.

PostgreSQL за замовчуванням використовується оркестратором для конфігурації, розкладів, стану завдань і службової інформації. Він не є обов’язковою залежністю кожного компонента.

## 6. Завдання та розклади

Завдання визначає:

- джерело або перелік матеріалів;
- колектор і його параметри;
- послідовність обробників, їхні версії та параметри;
- умови розгалуження;
- одноразовий запуск або розклад;
- правила повторних спроб та обмеження виконання.

Для вебджерела конфігурація також визначає один або комбінацію способів пошуку матеріалів:

- явний перелік початкових URL;
- рекурсивний перехід за знайденими посиланнями в дозволених межах сайту;
- читання Sitemap і Sitemap Index;
- читання RSS/Atom-стрічок;
- обхід сторінок категорій, пагінації, пошуку або URL за заданим шаблоном;
- отримання переліку матеріалів із документованого API або JSON-каналу сайту;
- автоматичне дослідження джерела за допомогою LLM.

Режими можна комбінувати: наприклад, Sitemap дає початкові URL, а рекурсивний обхід знаходить пов'язані матеріали, відсутні в ньому. Для кожного режиму налаштовуються межі доменів і шляхів, правила дозволу та виключення URL, глибина, розклад повторного відвідування, дедуплікація, пріоритети й ресурсні ліміти. Колектор має поважати правила доступу джерела, зокрема `robots.txt`, якщо користувач явно не налаштував іншу правомірну політику для контрольованого ним ресурсу.

Завдання є самостійними. Для первинного збору й подальших перевірок створюються окремі завдання.

**Приклад: товари**

| Завдання | Дія |
|---|---|
| Зібрати каталог | Прочитати сторінки, витягнути повні картки товарів, зберегти |
| Перевірити ціни | За розкладом прочитати задані URL, витягнути лише ціну й наявність, зберегти |

Спеціальний механізм автоматичного перемикання з «первинного» екстрактора на «оновлювальний» не потрібен.

Частковий результат оновлює лише передані поля ідентифікованого об’єкта. Пропущене поле не означає його видалення; явне очищення має позначатися окремо.

## 7. Репозиторій обробників

Репозиторій містить пакети обробників різних типів: витягування даних, збереження, звернення до LLM та інших перетворень. Екстрактор є одним із типів обробника й використовує ті самі механізми версіонування, тестування та форкування.

Пакет обробника містить:

- тип, опис призначення та код або опис способу виконання;
- вхідний контракт, параметри та необхідні залежності й доступи;
- контракт результату; для екстрактора — схеми вихідних сутностей;
- тестові приклади й очікувані результати;
- історію версій і походження.

Python є початковою мовою коду екстракторів. Пакети містять вимоги до підключень, але не секрети: облікові дані сховищ і провайдерів LLM задаються окремо в середовищі виконання та не копіюються під час форкування.

Кожен етап завдання явно посилається на конкретну версію пакета обробника та задає параметри виконання. Для екстракторів також визначаються відповідні джерела; для вебджерел прив’язка може уточнюватися до розділу або шаблону URL.

Наявність пакета в репозиторії не означає його застосування до всіх матеріалів. Наприклад, до новинного каналу не застосовуються товарні екстрактори, якщо це не налаштовано.

**Форк — незалежна копія пакета з посиланням на батьківський пакет і вихідну версію.**

Зміни батька не впливають на форк. В інтерфейсі можна побачити оновлення та порівняти відмінності. Перенесення змін можливе лише за явною командою користувача, без автоматичного застосування системою або LLM.

## 8. Використання LLM

Платформа має налаштування провайдерів LLM, моделей, підключень і лімітів витрат.

LLM використовується у двох сценаріях:

1. Як обробник у заданому ланцюжку.
2. Як засіб створення та вдосконалення правил колекторів і екстракторів.

Під час підключення джерела користувач може задати лише назву сайту чи Telegram-каналу або надати точне посилання, очікувані типи даних і правила обходу. Якщо налаштувань недостатньо, система отримує достатню різноманітну вибірку сторінок або повідомлень, щоб розрізнити основні типи матеріалів. Фіксована кількість наперед не задається: дослідження триває в межах налаштованого бюджету до достатньої впевненості або повертає користувачу повідомлення про недостатність вибірки.

Після дослідження джерела LLM:

- визначає тип джерела, доступні способи його обходу та типи матеріалів;
- визначає доступні сутності та поля;
- пропонує користувачу кілька варіантів правил збору із поясненням охоплення, вартості й ризиків;
- шукає відповідні пакети типу «екстрактор» у репозиторії обробників;
- перевіряє їх на прикладах;
- пропонує прив’язку готового пакета, адаптує форк або створює новий пакет;
- може створити або змінити версіоновані правила для колектора;
- готує схеми результатів і тести.

Готові екстрактори працюють без обов’язкового звернення до LLM, якщо такого звернення не передбачає їхня логіка.

Для вебматеріалу, якому не відповідає жоден налаштований обробник, LLM не викликається автоматично. Такий матеріал передається LLM лише коли в налаштуваннях джерела або завдання ввімкнено опцію **«Передавати в LLM невідомі сторінки»**. Створені LLM правила колектора чи екстрактора проходять версіонування, тестування та встановлений користувачем режим погодження або автоматичної активації.

## 9. Вдосконалення екстракторів

Система розрізняє:

- успішну обробку;
- коректну відсутність потрібних сутностей;
- невідомий або частково розібраний формат;
- помилку виконання чи невідповідність результату схемі.

Проблемні матеріали групуються за джерелом і характером проблеми. LLM отримує вибірку, поточний код, діагностику та попередні успішні приклади.

Виправлення створюється як нова версія й перевіряється на нових і попередніх тестах. Зміни спільного пакета перевіряються для всіх його прив’язок або оформлюються окремим форком.

Підтримуються ручне погодження та автоматична активація після визначених перевірок. Користувач може заборонити автоматичні зміни конкретного пакета.

Кількість спроб і витрати LLM обмежуються. Невирішені проблеми відображаються в адмінці. Розширення очікуваних типів даних джерела пропонується користувачу.

## 10. Адміністративний інтерфейс

Адмінка повинна дозволяти:

- керувати джерелами, завданнями, розкладами та ланцюжками обробки;
- налаштовувати LLM і підключення до сховищ;
- переглядати пакети обробників і правила колекторів, створювати незалежні форки та налаштовувати їх використання в завданнях;
- редагувати код і запускати тести без запису в робочі дані;
- переглядати відмінності версій, активувати їх і виконувати відкат;
- переглядати матеріали, результати, помилки, прогрес і витрати;
- скасовувати завдання та повторно обробляти збережені матеріали.

## 11. Надійність і безпека

Повторне отримання матеріалу з джерела є новим спостереженням. Повторна технічна доставка того самого результату є дублем і не повинна створювати повторних записів або дій.

Оркестратор має забезпечувати підтвердження приймання результатів, повторні спроби, відновлення після збоїв і простежуваність проходження даних між етапами.

Для оновлень потрібно враховувати порядок спостережень: запізнілий результат не повинен непомітно замінювати новіший.

Виконання коду обмежується за часом, ресурсами й доступами. Секрети передаються через керовані підключення. Вміст сайтів і повідомлень розглядається як дані, а не як інструкції для LLM.

## 12. Критерії приймання

Платформа повинна продемонструвати:

1. Незалежний запуск і використання колектора та екстрактора стороннім застосунком.
2. Налаштування ланцюжка з розгалуженням, екстракцією та збереженням.
3. Зміну сховища без зміни коду колектора й екстрактора.
4. Підготовку екстрактора через LLM за матеріалами нового джерела.
5. Окремі завдання повного збору товарів і періодичної перевірки цін.
6. Вдосконалення екстрактора на проблемних прикладах із тестуванням та відкатом.
7. Незмінність форку після оновлення батьківського пакета.
8. Відновлення після збою та коректну обробку повторної доставки.
9. Використання пакетів різних типів із єдиного репозиторію обробників із фіксацією версій і незалежним форкуванням.
10. Окреме й комбіноване використання рекурсивного обходу, Sitemap та щонайменше одного додаткового способу пошуку матеріалів.
11. Відсутність автоматичного виклику LLM для невідомої сторінки без увімкненої опції та його виклик після явного ввімкнення.
12. Збереження тестових RAW-сторінок і структурованих результатів кожним початковим типом адаптера або сумісним тестовим замінником зовнішнього сервісу.
13. Зміну лімітів виконання без зміни коду та наявність перевірених початкових профілів для підтримуваних середовищ розгортання.

## 13. Рішення та питання для наступного етапу проєктування

### 13.1. Зафіксовані рішення

1. **Обхід сайтів налаштовується як комбінація стратегій.** Підтримуються автоматичне дослідження джерела моделлю, рекурсивний обхід від початкової або головної сторінки, Sitemap/Sitemap Index, RSS/Atom, явні списки та шаблони URL, сторінки категорій і пагінації, а також доступні API/JSON-канали. Кожна прочитана сторінка може додавати нові посилання до черги після перевірки області обходу, правил виключення та дедуплікації.
2. **LLM допомагає налаштувати нове джерело.** Якщо користувач указав лише назву сайту або каналу, платформа знаходить джерело, аналізує достатню вибірку різних сторінок або повідомлень і пропонує кілька варіантів збору. Остаточний варіант обирає користувач, якщо він не дозволив автоматичну активацію.
3. **Невідомі сторінки передаються LLM лише за явним налаштуванням.** Опція має назву «Передавати в LLM невідомі сторінки». LLM може створювати версії правил для колектора й екстрактора; до них застосовуються тести, аудит, погодження та відкат.
4. **Початкові адаптери збереження:** PostgreSQL, SQL Server, MongoDB, MinIO, S3 і файлова система. Для файлового адаптера базові формати — HTML для RAW вебсторінок і JSON для інших даних.
5. **Числові ліміти не зашиваються в архітектуру.** Паралельність, частота запитів, глибина й обсяг обходу, тайм-аути, повторні спроби, розміри черг і матеріалів, бюджети LLM та інші обмеження конфігуруються на рівні платформи, джерела й завдання. Команда або агенти, що реалізують і розгортають компонент, повинні визначити, протестувати й задокументувати безпечні початкові значення для цільового середовища. Значення за замовчуванням мають враховувати доступні ресурси та не скасовують окремих обмежень конкретного сайту чи зовнішнього сервісу.
6. **Точні API-контракти є результатом технічного проєктування реалізації, а не вхідною вимогою від замовника.** Їх визначають агенти-розробники з дотриманням уже погоджених вимог: автономність компонентів, версіонування, документованість, асинхронні операції, ідемпотентність, діагностика та передавання великих матеріалів. Контракти мають бути зафіксовані в машинозчитуваній специфікації та перевірятися контрактними тестами.

### 13.2. Відкрите рішення

На наступному етапі потрібно обрати технологію зберігання та розповсюдження пакетів обробників і правил колекторів. Вибір має підтримувати версії, незмінні артефакти, залежності, тести, походження, форки, контроль доступу та можливість автономного використання пакета без оркестратора.

Ці рішення мають зберігати головну властивість платформи: **кожен компонент можна використовувати окремо, а оркестратор лише поєднує їх у налаштовані процеси.**
