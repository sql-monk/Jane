### Додатковий пункт координатора: `StorageClient.material`

Дефект: клієнт завжди читав `getObjectContent` і підписував байти `media_type` матеріалу, тож RAW, збережений як
JSON-документ Material (`format.raw = json`), потрапляв до моделі й тестів пакета як сам документ-обгортка; відповідь
`getObject` без `material` давала хибне `validation_failed`. Тепер ([`clients.py`](../../services/assistant/src/jane_assistant/clients.py)):

1. `material.content` inline і це не документ Material → береться як є (нова поведінка storage, другого запиту немає);
2. інакше читаються байти об'єкта: документ Material (`material_id`, `observation_id`, `fetched_at`, `content.data`;
   за наявності `material` — той самий `material_id`) → цей Material з його внутрішнім вмістом inline (новий storage без
   `material` для великого вмісту; старий storage з blob-посиланням чи inline-документом); інші байти → початковий
   вміст `material` (як було для HTML-файлів);
3. `material` немає й об'єкт — не документ Material → **501 `not_implemented`** з поясненням «передайте приклад inline
   як `material`». **Рішення:** це не помилка запиту (тож не `validation_failed`): асистент не може відновити матеріал
   без метаданих, які storage не повернув; job вдосконалення завершується явною причиною, а не тихим пропуском
   прикладу — ТЗ §9 вимагає, щоб LLM отримала саме проблемні приклади, і невирішене має бути видно (так само
   асистент поводиться з `s3://` без `download_url`).

Тести: [`test_storage_material.py`](../../services/assistant/tests/test_storage_material.py) — 7, фейк storage
відповідає лише в межах `storage.v1` (кожна відповідь перевіряється схемою): HTML-файл, новий inline, без `material`,
старий blob і старий inline-документ, об'єкт без `material` → `not_implemented`, наскрізно — вдосконалення бачить сам
HTML. На старому коді клієнта 6 із 7 падають (HTML-випадок — регресійний). Сумісно і зі старою, і з новою поведінкою
storage (WP-17).

### API для WP-20 (R24)

Обидві операції — scope `assistant:use`, курсорна пагінація за конвенціями (`limit` 1…, понад
`pages.max_page_size` асистента (500) обрізається; `cursor` — непрозорий рядок із `next_cursor`; `next_cursor: null` —
остання сторінка; чужий/зіпсований курсор чи невідомий `status` — 422 `validation_failed`).

```text
GET /api/assistant/v1/onboarding-sessions?limit=&cursor=&status=<OnboardingStatus>[&status=…]
200 {"items": [OnboardingSessionSummary…], "next_cursor": "…" | null}
OnboardingSessionSummary = {session_id, status, query, created_at        (обов'язкові)
                            selected_candidate_id?, proposal_count, costs?{amount,currency},
                            job_id? (останній job сесії), error? (Problem)}
порядок: created_at ↓, потім session_id ↓; запущені сесії звірено з їхнім job (як у GET сесії)
повний стан — GET /v1/onboarding-sessions/{session_id}

GET /api/assistant/v1/improvement-runs?limit=&cursor=&package_id=&source_id=&problem_group_id=&status=<JobStatus>[&status=…]
200 JobList = {"items": [Job kind=improvement…], "next_cursor": "…" | null}
Job.labels = {package_id, source_id?, problem_group_id?}; Job.result (succeeded) = ImprovementResult
(outcome, version, test_reports, activated, unresolved_reason, suggested_entity_types, costs, proposal?)
порядок: created_at ↓, потім job_id ↓; job загиблого екземпляра — уже failed
```

Для UI: список сесій замінює `localStorage` «нещодавніх сесій» (WP-12); id сесії зі старту — `Job.labels.session_id`
/ `Job.links.session`; завершені операції в мок-режимі — `Prefer: example=onboardingSucceeded|acceptanceSucceeded|
improvementSucceeded|improvementProposalOnly|unknownSucceeded` для `GET /v1/jobs/{id}`, `Prefer: example=onboarding`
для 202 старту; згенеровані типи — `web/admin/src/api/generated/assistant.ts`.

## Рішення

| Питання | Рішення | Обґрунтування |
|---|---|---|
| `amount: 0` | «LLM вимкнено»: жодного виклику, навіть безкоштовної моделі | Так уже поводились і шлюз (`spent >= limit` у `reserve`), і асистент; найконсервативніше; `exhausted` тоді має чітке значення «у вікні не пройде жоден виклик». Для «лише безкоштовні моделі» — мала додатна сума (як `ci`: 0.01 USD/day, резерв платного виклику не вміщується) |
| `run` без `run_id` | вікно = сам запит (усі повтори за схемою) | Бюджет ніколи не пропускається (раніше — пропускався); 422 зламав би автономне використання з бюджетом платформи `…/run` |
| Бюджет запиту з іншим періодом | ще одна перевірка, не підміна | «Лише звужує» (ТЗ §13.1 п. 5, контракт лімітів) |
| Run асистента | сесія підключення (усі її job), job вдосконалення, job невідомого матеріалу | Одиниця роботи, яку бачить користувач; лічильник шлюзу спільний для екземплярів |
| Тайм-аут моделі (R12) | власний `provider.request_timeout_ms` llm; з'єднання й повтори — контрактні | Профіль платформи розрахований на веб; окреме контрактне поле потребувало б нового поля в `limits.schema.json` і jane-kit — не потрібне, бо значення специфічне для llm |
| Асистент і довгий виклик | синхронно з `llm_call.request_timeout_ms` = 15 хв (типово), `async` — опція | `sync` не змінює взаємодію (e2e, R-04/R-07); 15 хв покривають найгірший випадок шлюзу з профілем (2 × 3 × 120 с ≈ 12 хв) і дорівнюють `reservation_ttl_seconds` шлюзу |
| `min_onboarding_confidence` | контрактне поле (а не внутрішній ліміт) | ТЗ §8: поріг достатності — ліміт дослідження; має бути видимим і налаштовуваним як інші `llm.*`. Перейменування змінної середовища: стара `…__ONBOARDING__MIN_CONFIDENCE` зупиняє старт як невідомий ліміт (у репозиторії не використовувалась) |
| Пропозиція `proposal_only` | змінені файли + маніфест + diff, обмежено `improvement.max_proposal_bytes` | Користувач бачить зміну й може сам опублікувати (`based_on` + `files`); тестові матеріали можуть бути великими — тому межа й `omitted_files` |
| Списки R24 | окремі ресурси (`GET` на тих самих шляхах, що й `POST`), короткий підсумок сесії | Узгоджено з REST-формою API; повні сесії великі (варіанти, правила) |

## Відомі обмеження

- Лічильник бюджету рахує лише виклики, на які цей бюджет діяв: визначення, створене посеред доби, і бюджет запиту
  на рівні без збереженого бюджету не бачать раніших викликів вікна (так було й раніше; описано в README llm).
- Бюджет запиту з періодом `day`/`week`/`month`/`total` звужує **спільний** лічильник найконкретнішого рівня: для
  онбордингу (без source/task) — лічильник платформи, тобто денний бюджет асистента порівнюється з витратами всієї
  платформи за добу. Консервативно; окремого рівня «асистент» у шлюзі немає.
- Список сесій з фільтром `status` фільтрує за збереженим станом, потім звіряє запущені з їхнім job — сторінка може
  бути коротшою за `limit` (дозволено конвенцією).
- `async`-режим асистента перевірено проти справжнього шлюзу в процесі, але не в стеку з рестартами (R-04/R-07).
- `StorageClient.material` читає весь об'єкт без окремої межі розміру (як і раніше); межа вмісту застосовується вже до
  відновленого матеріалу (`content.max_material_bytes` читача).

## Неперевірені інтеграції

- Реальний провайдер LLM — **не перевірено на реальному сервісі** (тайм-аути розраховані, не виміряні).
- Справжній storage з новою поведінкою WP-17 — лише контрактний фейк `storage.v1` (обидві поведінки).
- Адмінка (WP-20) нові операції ще не використовує; @mock/@hybrid e2e адмінки не запускались (типові тіла моків не
  змінювались, лише додано приклади).
