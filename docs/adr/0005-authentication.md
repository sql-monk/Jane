# ADR-0005. Автентифікація сервісів і адмінки

**Статус:** прийнято (WP-00, 2026-09-27)

## Контекст
Сервіси викликають один одного (оркестратор → колектори/обробники/registry/llm, асистент →
llm/registry/колектор/runtime) і використовуються сторонніми застосунками автономно (ТЗ §4).
Адмінка — браузерний застосунок (WP-12) з керуванням підключеннями, кодом і лімітами. Потрібна
проста для dev і Windows схема, яку можна посилити в прод без зміни контрактів.

## Рішення
1. **Контракт один для всіх режимів:** `Authorization: Bearer <token>` (`bearerAuth` у кожному
   OpenAPI). `/v1/health` — без автентифікації. `/v1/info` повертає `auth_mode`.
2. **Режими сервісу** (конфігурація `auth.mode`, реалізує `jane-kit`):
   - `none` — лише для локальних тестів; сервіс слухає `127.0.0.1` і пише попередження в журнал;
   - `api_key` — статичні ключі з конфігурації (зберігаються хешем; значення — через `secret_refs`),
     кожному ключу призначено scopes; **типовий режим dev-стеку**;
   - `jwt` — JWT (RS256/ES256), перевірка за JWKS URL, `iss`/`aud`/`exp`, scopes у claim `scope`;
     **рекомендований для прод**. Сервісні облікові записи отримують токени через OAuth2
     client credentials у зовнішнього IdP (Keycloak, Entra ID тощо).
3. **Scopes** (перевіряє кожен сервіс для своїх операцій): `collector:read`, `collector:run`,
   `handler:invoke`, `handler:test`, `connections:write`, `storage:read`, `registry:read`,
   `registry:write`, `registry:approve`, `orchestrator:read`, `orchestrator:write`,
   `orchestrator:admin` (ліміти платформи, підключення), `llm:invoke`, `llm:admin`,
   `assistant:use`. Брак scope — 403 `forbidden`.
4. **Адмінка:** OIDC Authorization Code + PKCE у зовнішнього IdP; адмінка звертається до API
   сервісів через reverse proxy (WP-01) з префіксами `/api/<service>/v1/...`, передаючи
   access token користувача. Ролі IdP відображаються на scopes (`viewer`, `operator`, `admin`).
   Для dev — режим `api_key` з ключем адміністратора, який вводиться на сторінці входу адмінки й
   зберігається лише в `sessionStorage`.
5. **Делегування:** оркестратор і асистент викликають інші сервіси **власним** сервісним
   токеном; ідентичність користувача передається в `requested_by` (аудит), а не як токен.
6. mTLS між сервісами — опційно на рівні розгортання (service mesh/проксі), контракти не змінює.

## Наслідки
- Автономний сервіс можна використати з одним ключем API без IdP.
- Прод отримує стандартні JWT/OIDC без змін коду сервісів — лише конфігурація.
- Кожен сервіс сам перевіряє токен (немає централізованого шлюзу як єдиної точки відмови).

## Альтернативи
- **Лише mTLS** — складно для сторонніх застосунків і браузера.
- **Сесії в оркестраторі для адмінки і проксі всіх API через нього** — робить оркестратор
  обов'язковою залежністю й вузьким місцем; суперечить автономності.
- **Власний IdP у складі Jane** — поза обсягом; стандартний OIDC дешевший і безпечніший.
