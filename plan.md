# Jane — план реалізації для паралельної роботи агентів

**Дата:** 2026-09-27  
**Основа:** [TECHNICAL_SPECIFICATION.md](TECHNICAL_SPECIFICATION.md) v0.2 (далі — ТЗ). Якщо план і ТЗ розходяться, пріоритет має ТЗ.  
**Стан на старті:** у репозиторії лише документація, коду ще немає.

Агентові, який виконує пакет робіт, досить прочитати ТЗ, цей план і прийняті результати своїх залежностей. Інших джерел контексту немає.

## 1. Ролі

- **Координатор** (людина або головний агент). Ініціалізує git-репозиторій і комітить ТЗ та план. Далі запускає агентів, веде `docs/delivery/status.md`, призначає рев'юерів, зливає гілки в `main` і вирішує конфлікти власності.
- **Виконавець.** Один агент на один пакет робіт (WP), працює в гілці `wp/NN-коротка-назва`.
- **Рев'юер.** Інший агент, який не був автором цього WP. Він перевіряє DoD (§4) і відповідність ТЗ. Якщо є зауваження, WP повертається виконавцю, а після виправлення рев'ю проходить повторно.

Статуси WP: `ready → active → review → accepted` (або `blocked` із причиною).

## 2. Базові технічні рішення

Ці рішення вже прийняті, щоб паралельні агенти не обирали стек кожен по-своєму. Змінити їх може лише WP-00, і тільки через ADR до старту хвилі 1.

| Питання | Рішення за замовчуванням |
|---|---|
| Мова сервісів і екстракторів | Python 3.12+, FastAPI, Pydantic v2; монорепозиторій на uv workspace |
| Адмінка | TypeScript, React, Vite; API-клієнти генеруються з контрактів |
| Контракти | OpenAPI 3.1 і JSON Schema 2020-12 у `contracts/`, кожен API має версію (`/v1`) |
| Взаємодія | Синхронний HTTP для коротких операцій. Тривалі операції повертають `202` з `job_id`, а стан, прогрес і результат читаються за цим id |
| Великі матеріали | Передаються за посиланням на blob-сховище (MinIO/S3/файли), а не в тілі запиту |
| Службове сховище й черга оркестратора | PostgreSQL (задачі через `SELECT … FOR UPDATE SKIP LOCKED`), без окремого брокера |
| Середовище розробки | Docker Compose; скрипти працюють на Windows і Linux |
| Тести | pytest, testcontainers, контрактні моки з OpenAPI, Playwright для адмінки |

Технологію репозиторію пакетів (ТЗ §13.2), пісочницю для Python-коду, автентифікацію й перелік цільових середовищ розгортання обирає WP-00.

## 3. Правила паралельної роботи

1. **Власність шляхів.** Кожен WP змінює лише шляхи, закріплені за ним у §5. Якщо потрібна зміна в чужій області, виконавець описує її у своєму звіті й передає координатору, а той доручає її власникові.
2. **Контракти спільні.** Після прийняття WP-00 контракт змінюється лише через координатора: зміна має бути зворотно сумісною або супроводжуватися оновленням усіх споживачів.
3. **Розробка проти моків.** Кожен сервіс розробляють і тестують проти моків сусідів, згенерованих із контрактів. Мок не замінює інтеграційного приймання (§7).
4. **Ізоляція.** Кожен агент працює у власному checkout. Тестові стеки мають унікальні імена compose-проєктів, порти й томи.
5. **Секрети** не потрапляють у код, пакети, тести й звіти. Якщо до зовнішнього сервісу немає доступу, у звіті пишуть «не перевірено на реальному сервісі».
6. **Без зашитих лімітів.** Паралельність, тайм-аути, глибина, розміри, бюджети тощо читаються з конфігурації (платформа → джерело → завдання). Безпечні значення за замовчуванням задокументовані.
7. **Автономність.** Жоден сервіс не читає таблиць іншого сервісу. Колектори, runtime, збереження, репозиторій і LLM запускаються й працюють без оркестратора (ТЗ §4).

## 4. Спільне визначення готовності (DoD) сервісного WP

- API реалізовано за контрактом із `contracts/`, контрактні тести зелені.
- Є unit- та інтеграційні тести; вони запускаються однією командою, описаною в README сервісу.
- README містить опис незалежного запуску, конфігурацію, ліміти з типовими значеннями й приклад виклику зі стороннього застосунку.
- Є Dockerfile, health-check, структуровані журнали й базові метрики. Сервіс можна запустити кількома екземплярами.
- Звіт `docs/delivery/WP-NN.md` містить результат, команди перевірки та їхній вивід, відомі обмеження, неперевірені інтеграції й запити до інших власників.

### Хвиля 2 — інтеграція та приймання

**WP-13. Інтеграція й приймання** — `tests/e2e/`, `docs/acceptance/`
- Стартує одразу, як з'являється вільний слот у хвилі 1: готує сценарії й матрицю 13 критеріїв ТЗ §12 за контрактами.
- Проводить віхи M1 і M2 (§6).
- Перевіряє надійність: kill і рестарти сервісів, розриви мережі, повторну доставку, запізнілі результати, кілька екземплярів кожного компонента, повний цикл LLM → тести → активація → відкат.
- Дефекти передає власникам WP через координатора.
- **Готово, коли:** критерії 1–12 підтверджені на одній ревізії `main`, а сценарії, що використовують замінники, позначені окремо від перевірених на реальних сервісах.

**WP-14. Профілі лімітів і експлуатація** — `deploy/profiles/`, `docs/operations/`, `examples/`
- Стартує після M1. Вимірює цільові середовища, обрані в WP-00, і готує перевірені профілі лімітів.
- Документація: незалежний і спільний запуск, міграції, резервне копіювання й відновлення.
- Відтворювані приклади: каталог товарів + окреме завдання перевірки цін; події з Telegram.
- **Готово, коли:** критерій 13 підтверджено, а приклади відтворюються з чистого checkout за документацією.

## 6. Порядок, віхи й критичний шлях

```text
Хвиля 0:  WP-00 ‖ WP-01                        (паралельно)
                ▼ M0
Хвиля 1:  02 03 04 05 06 07 08 09 10 11 12     (паралельно, проти моків)
          M1 = 02 + 06 + 07 + база 09;  M2 = усі WP хвилі 1
Хвиля 2:  WP-13: сценарії, щойно є слот → M1 → M2 ─┐
          WP-14: від M1 ──────────────────────────┴→ M3
```

- **M0.** WP-00 і WP-01 прийняті — хвиля 1 стартує.
- **M1, перший наскрізний зріз.** Web → збереження RAW у files і, паралельно, екстракція локальним пакетом → результати в PostgreSQL. Потрібні WP-02, 06, 07 і базова частина WP-09. Далі підключаються репозиторій, Telegram, інші адаптери, LLM і адмінка.
- **M2.** Усі WP хвилі 1 прийняті, повний стек працює на реальних компонентах.
- **M3.** Прийняті WP-13 і WP-14. Усі 13 критеріїв підтверджені на фінальній ревізії, пройдено незалежне фінальне рев'ю.

**Критичний шлях:** WP-00 → довший із WP-09 і WP-11 → M2 → WP-13 → M3.

**Якщо агентів менше, ніж WP**, слоти заповнюють у такому порядку: 09, 02, 06, 07 (для M1) → 11, 05, 10 → 12, 03, 04, 08 → 13, а 14 — після M1. Наступний WP, у якого виконані залежності, запускають одразу, не чекаючи кінця хвилі. Рев'ю займає окремий слот.

## 7. Інтеграція

- Координатор зливає в `main` лише прийняті WP і після кожного злиття проганяє CI на спільній ревізії.
- Інтеграційні дефекти виправляє власник області. Якщо власник WP уже звільнений, координатор призначає нового агента на ту саму область.
- Проєкт готовий, коли досягнуто M3 і людина або новий агент може відтворити запуск лише за документацією. Розгортання в робочому середовищі — окремий етап поза цим планом.
