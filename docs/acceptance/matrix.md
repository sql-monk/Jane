# Матриця приймання: 13 критеріїв ТЗ §12

Веде WP-13. Сценарії описано в [scenarios.md](scenarios.md), код лежить у [`tests/e2e/`](../../tests/e2e).
Стан на 2026-09-27, ревізія `main` `894cbf0`: у `main` злито WP-00, 01, 06 і 07.

## Як читати

- **Що доводить** — яке спостережуване поводження системи вважаємо виконанням критерію.
- **Перевірка** показує, на чому саме проходить сценарій:
  - **Р** — реальний сервіс Jane або реальна інфраструктура (PostgreSQL, SQL Server, MongoDB, MinIO);
  - **З** — замінник *зовнішньої* системи, позначений явно: фейковий LLM-провайдер, записаний або фейковий
    клієнт Telegram, фейковий пошуковий провайдер, SeaweedFS замість AWS S3;
  - **Т** — тимчасовий замінник компонента Jane, якого ще немає в `main`. Він доказом не є, і коли WP злито,
    сценарій переходить на реальний компонент.
- **Віха** — plan.md §6. Критерій прийнято, коли його сценарії пройшли на **одній ревізії `main`**
  (plan.md §5, WP-13). Сценарії з **З** звітуються окремо від тих, що пройшли на реальних сервісах.
- **Докази WP** — перевірки з інших WP, що частково покривають критерій. Це тести самих WP, найчастіше з
  моками сусідів, тому вони **не замінюють** e2e-сценарію. Гілки, що ще не злиті в `main`, позначено «гілка».

## Критерії детально

### 1. Незалежний запуск і використання колектора та екстрактора стороннім застосунком
- **Що доводить.** Сторонній клієнт (тест як окремий процес) викликає колектор (`collector.v1`) і
  runtime екстрактора (`handler.v1`) напряму. Оркестратор, репозиторій і сховище при цьому не запущені або
  не використовуються. Пакет екстрактора береться локально (inline-архів), а не з репозиторію.
- **Сервіси.** web-collector, telegram-collector, handler-runtime, testsite.
- **Сценарії.** S-M1-01 (runtime з локальним пакетом), S-M1-02 (колектор `POST /v1/fetches`), S-M1-04
  (колектор `POST /v1/collections` + читання матеріалів, runtime через CLI на файлі), S-M2-02 (Telegram).
- **Перевірка.** Р для runtime і Web Collector; З для Telegram (записаний клієнт, реальний канал — лише за
  тестового доступу). У S-M1-01 колектор поки що Т.
- **Віха.** M1 (Telegram — M2).
- **Докази WP.** WP-06 (main): CLI-тести пакета без інших сервісів (`test_isolation.py::test_example_package_tests_pass_through_cli`).
  WP-02 (гілка): `tests/test_autonomy.py::test_third_party_app_uses_collector_without_orchestrator`
  (окремий процес, реальний testsite). WP-04 (гілка, звіту ще немає): `test_collect.py::test_one_shot_fetch`
  (записаний клієнт). WP-05 (гілка): експортований пакет запускається в CLI runtime без репозиторію.
- **Стан e2e.** Частину про runtime доведено S-M1-01. Частина про колектор чекає злиття WP-02 (S-M1-02, S-M1-04).

### 2. Налаштування ланцюжка з розгалуженням, екстракцією та збереженням
- **Що доводить.** Завдання оркестратора з DAG: `collect` → (`store-raw` ‖ `extract` → `store-products` ‖
  `analyze-problems`). Воно виконується на реальних виконавцях. RAW потрапляє у files, сутності — у PostgreSQL,
  а простежуваність `GET /v1/materials/{id}/trace` зв'язує матеріал, етап, результат і версію пакета.
- **Сервіси.** orchestrator, web-collector, handler-runtime, storage, llm (гілка з LLM-обробником), testsite, postgres.
- **Сценарії.** S-M1-01 (обидві гілки без оркестратора), S-M1-03 (M1-завдання через оркестратор), S-M2-11
  (розгалуження з умовами `when` і LLM-етапом).
- **Перевірка.** Р; LLM-етап — З (фейковий провайдер WP-10).
- **Віха.** M1 (без LLM-етапу), M2 (повний).
- **Докази WP.** WP-09 (гілка): `test_pipeline.py::test_m1_chain_web_to_raw_and_extraction_to_results`, де всі
  сусіди — контрактні фейки. WP-07 (main): `test_adapter_swap.py` на прикладах контрактів.
- **Стан e2e.** Обидві гілки M1 на реальних storage і runtime пройдено (S-M1-01). Оркестрація чекає WP-02 і WP-09.

### 3. Зміна сховища без зміни коду колектора й екстрактора
- **Що доводить.** Той самий вихід колектора й екстрактора (байт у байт) записується в інше сховище. Для цього
  змінюються лише `handler.package_id` і `connections.target` етапу, тобто конфігурація завдання. Код і образи
  колектора й екстрактора не змінюються.
- **Сервіси.** storage (усі адаптери), handler-runtime, orchestrator (варіант через завдання).
- **Сценарії.** S-M1-05 (PostgreSQL ↔ files на рівні виклику обробника), S-M2-08 (заміна в `TaskConfig` через
  `PUT /v1/tasks/{id}`, прогін на кожному з 6 адаптерів).
- **Перевірка.** Р (S3 — З: SeaweedFS).
- **Віха.** M1 (files ↔ PostgreSQL), M2 (усі адаптери, через оркестратор).
- **Докази WP.** WP-07 (main): `tests/test_adapter_swap.py`. WP-08 (гілка): ядро не змінено, образ містить 6 адаптерів.
- **Стан e2e.** S-M1-05 пройдено: стан сутності в PostgreSQL і у files збігається.

### 4. Підготовка екстрактора через LLM за матеріалами нового джерела
- **Що доводить.** Асистент отримує назву нового джерела (testsite) і робить таке: пошук через фейковий
  пошуковий провайдер, адаптивна вибірка сторінок через реальний колектор, кілька варіантів збору з
  оцінкою, пакет (прив'язка готового, форк або новий) у реальному репозиторії, тести пакета в реальному runtime.
  Після вибору варіанта користувачем створюються джерело й завдання.
- **Сервіси.** assistant, llm, registry, web-collector, handler-runtime, orchestrator, storage.
- **Сценарії.** S-M2-06.
- **Перевірка.** З для LLM (детермінований фейковий провайдер WP-10, **не** власний фейк асистента) і для
  пошукового провайдера (`SEARCH_PROVIDER=static`); решта — Р. Реальний LLM — «не перевірено на реальному
  сервісі», доки немає тестового доступу.
- **Віха.** M2.
- **Докази WP.** WP-11 (гілка): `test_onboarding.py::test_new_source_by_name_to_proposals_package_and_tests`
  та інші. Сусіди там — контрактні фейки, LLM — власний фейк асистента.
- **Стан e2e.** Чекає WP-11, 10, 05, 02, 09. Треба узгодити фейковий сценарій LLM-провайдера WP-10 з
  підказками асистента (див. запити в звіті WP-13).

### 5. Окремі завдання повного збору товарів і періодичної перевірки цін
- **Що доводить.** Два незалежні завдання оркестратора: `shop-catalog` (повні картки) і `shop-price-check`

  решту. Зміна або скасування одного не впливає на інше. Спеціального перемикання екстракторів немає.
- **Сервіси.** orchestrator, web-collector, handler-runtime, storage, testsite.
- **Сценарії.** S-M2-04.
- **Перевірка.** Р.
- **Віха.** M2.
- **Докази WP.** WP-09 (гілка): `test_done_when.py::test_full_collection_and_price_check_tasks_are_independent`
  (фейки сусідів). WP-07 (main): часткове оновлення (C-03).
- **Стан e2e.** Чекає WP-09 і WP-02. Для перевірки цін потрібен пакет-екстрактор ціни (див. запити).

### 6. Вдосконалення екстрактора на проблемних прикладах із тестуванням та відкатом
- **Що доводить.** Проблемні результати (`unrecognized`/`failed`) групуються (`/v1/problem-groups`). Асистент
  через LLM створює нову версію пакета в репозиторії, яка проходить нові й старі тести в реальному runtime
  і перевіряється на всіх прив'язках. Далі вона активується в етапі завдання (`activations`), і наступний
  прогін дає `success`. Після відкату на попередню версію поведінка повертається, а аудит фіксує обидві дії.
- **Сервіси.** orchestrator, assistant, llm, registry, handler-runtime, storage, web-collector.
- **Сценарії.** S-M2-07, R-07 (повний цикл як сценарій надійності).
- **Перевірка.** З для LLM, решта — Р.
- **Віха.** M2.
- **Докази WP.** WP-11 (гілка): `test_improvement.py::test_problem_samples_to_new_version_activation_and_rollback`.
  WP-09 (гілка): `test_features.py::test_activation_rollback_and_auto_activate_policy`. WP-06 (main): тестовий
  прогін без запису (`test_test_run_reports_every_case`).
- **Стан e2e.** Чекає WP-11, 09, 05, 10.

### 7. Незмінність форку після оновлення батьківського пакета
- **Що доводить.** У реальному репозиторії: пакет P@1.0.0 → форк F (посилання на P@1.0.0) → P@1.1.0.
  Після цього вміст F і його дайджест не змінилися, `upstream` показує наявне оновлення, `diff` — відмінності.
  Перенесення змін відбувається лише явною командою (`upstream-ports`) і створює нову версію F. Етап
  завдання, прив'язаний до F, виконується тим самим кодом.
- **Сервіси.** registry, handler-runtime, orchestrator (прив'язка), admin (UI).
- **Сценарії.** S-M2-01, S-M2-10 (UI).
- **Перевірка.** Р (PostgreSQL + MinIO як сховище registry).
- **Віха.** M2.
- **Докази WP.** WP-05 (гілка): `tests/test_forks.py::test_parent_update_does_not_change_fork[real]` на реальних
  PostgreSQL і MinIO.
- **Стан e2e.** Чекає WP-05; UI-частина чекає WP-12 (на гілці WP-12 комітів ще немає).

### 8. Відновлення після збою та коректна обробка повторної доставки
- **Що доводить.** Повторна технічна доставка (той самий `delivery_key`) не створює записів чи дій:
  `duplicate: true`, стан не змінюється. Це стосується кожного виконавця, і після рестарту, і на іншому
  екземплярі. Після kill воркера, колектора чи виконавця посеред ланцюжка прогін завершується без подвійних
  ефектів. Запізнілий результат не замінює новішого.
- **Сервіси.** усі.
- **Сценарії.** S-M1-01 (повторна доставка RAW і сутностей), R-01 (kill воркера оркестратора), R-02 (kill і
  рестарт виконавців), R-03 (розрив мережі), R-04 (повторна доставка на кожен виконавець), R-05 (запізнілі
  результати), R-06 (кілька екземплярів).
- **Перевірка.** Р.
- **Віха.** M1 (storage + runtime), M2 (усі сервіси).
- **Докази WP.** WP-07 (main): C-01…C-08, `test_app.py` (`redelivery`, `after_restart`). WP-06 (main):
  `tests/test_state.py` (два екземпляри на PostgreSQL). WP-02 (гілка): `test_resume_after_kill.py`,
  `test_multi_instance.py`. WP-09 (гілка): `test_worker_killed_mid_chain_completes_without_double_effects`
  (фейки). WP-08 (гілка): `test_recovery.py` для s3 і mongodb.
- **Стан e2e.** Пройдено S-M1-01, R-02 (kill + рестарт storage і runtime, повтор — дубль), R-05 (запізніла ціна
  потрапляє лише в історію), R-06 (два екземпляри runtime, повтор на іншому — дубль із тим самим
  `invocation_id`). R-01 і R-03 чекають WP-09.

### 9. Пакети різних типів з одного репозиторію з фіксацією версій і незалежним форкуванням
- **Що доводить.** В одному реальному репозиторії опубліковано екстрактор, пакети збереження (`jane.storage-*`),
  LLM-пакет і правила колектора. Етапи завдання посилаються на `package_id@version` з дайджестом, і
  кожен виконавець отримує саме цю версію (runtime — архів із перевіркою хешу). Форк кожного типу
  незалежний. Нова версія батька не змінює поведінки завдання, поки не активовано нову версію.
- **Сервіси.** registry, handler-runtime, storage, llm, web-collector (правила), orchestrator.
- **Сценарії.** S-M2-01.
- **Перевірка.** Р.
- **Віха.** M2.
- **Докази WP.** WP-05 (гілка): `test_api.py`, `test_export.py`, `test_forks.py`. WP-07 (main): публікація пакетів
  збереження лише на моку registry. WP-06 (main): завантаження з фейкового репозиторію.
- **Стан e2e.** Чекає WP-05. Є відомий ризик: розбіжність канонічного архіву й дайджесту між SDK (deflate) і
  registry або storage (stored). Цей запит уже відкрито в status.md.

### 10. Рекурсія, Sitemap і щонайменше ще один спосіб пошуку — окремо й разом
- **Що доводить.** Реальний Web Collector на testsite. Кожна стратегія окремо (рекурсія, sitemap/index з `.gz`,
  RSS/Atom, категорії/пагінація, API/JSON, шаблон URL) дає рівно набір `expected_urls.json` → `sets.*`.
  Комбінації (sitemap + рекурсія, API + рекурсія) дають об'єднання, у тому числі URL із наборів `only:*`.
  При цьому немає виходу за межі, `robots.txt` дотримано, пастку `/calendar/` не зачеплено.
- **Сервіси.** web-collector (+ стратегії WP-03), testsite.
- **Сценарії.** S-M2-03.
- **Перевірка.** Р (testsite — фікстура WP-01, яку вважаємо «джерелом»).
- **Віха.** M2.
- **Докази WP.** WP-02 (гілка): рекурсія (`test_crawl_testsite.py::test_recursive_crawl_has_no_cycles_and_stays_in_bounds`).
  Комбінацію з sitemap там перевірено лише на плагіні-замінникові. Пакета WP-03 ще немає.
- **Стан e2e.** Чекає WP-02 і WP-03.

### 11. Без увімкненої опції невідома сторінка не йде в LLM автоматично, після ввімкнення — іде
- **Що доводить.** Завдання з прив'язками екстракторів проходить testsite, де є сторінки типу `unknown`
  (`page_types`). Якщо `forward_unknown_to_llm: false`, лічильник викликів фейкового провайдера LLM (`GET
  /v1/usage`) не зростає, а матеріали видно в `/v1/unknown-materials`. Після ввімкнення прапорця на джерелі
  або завданні й повторного прогону виклики LLM є, і вони прив'язані до невідомих матеріалів.
- **Сервіси.** orchestrator, web-collector, llm, assistant (`/v1/unknown-materials`), handler-runtime, storage.
- **Сценарії.** S-M2-05.
- **Перевірка.** З для LLM, решта — Р.
- **Віха.** M2.
- **Докази WP.** WP-09 (гілка): `test_features.py::test_unknown_material_goes_to_llm_only_with_flag` (фейки).
  WP-11 (гілка): `test_unknown.py::test_flag_off_refuses_without_calling_llm`.

### 12. Збереження тестових RAW і результатів кожним початковим адаптером (або замінником)
- **Що доводить.** Для кожного адаптера (filesystem, PostgreSQL, SQL Server, MongoDB, MinIO, S3) через реальний
  storage-сервіс робиться таке: RAW-сторінка testsite записується (для files — `.html` байт у байт), сутність
  записується й читається через `storage.v1`, повтор дає дубль. Дані перевіряються і в самому сховищі.
- **Сервіси.** storage (+ адаптери WP-08), postgres, sqlserver, mongodb, minio, s3 (SeaweedFS).
- **Сценарії.** S-M1-01 (files, PostgreSQL), S-M2-08 (усі 6).
- **Перевірка.** Р; S3 — З (SeaweedFS, незалежна від MinIO реалізація; AWS S3 — «не перевірено на реальному сервісі»).
- **Віха.** M1 (2 адаптери), M2 (6).
- **Докази WP.** WP-07 (main): набір сумісності C-01…C-16 для files і PostgreSQL. WP-08 (гілка): той самий набір
  для SQL Server 2022, MongoDB 8, MinIO, SeaweedFS.
- **Стан e2e.** files і PostgreSQL пройдено (S-M1-01: файл `.html` на томі storage збігається з відповіддю
  testsite байт у байт, сутність читається через `storage.v1`). Решта чекає WP-08.

### 13. Зміна лімітів виконання без зміни коду; перевірені початкові профілі
- **Що доводить.** Ліміт (наприклад, `rate.requests_per_second_per_host`, `sandbox.wall_time_ms`,
  `crawl.max_pages_per_run`) змінюється через `PUT /v1/limits/platform`, конфігурацію джерела чи завдання
  або змінну середовища. `GET /v1/limits/effective` показує новий ефективний ліміт із походженням, а
  поведінка наступного прогону відповідає новому ліміту. Образи сервісів не перезбираються. Профілі
  `dev-laptop`, `ci`, `single-node` (ADR-0007) виміряно й перевірено — це WP-14.
- **Сервіси.** orchestrator, усі виконавці (`GET /v1/info` → `limits`).
- **Сценарії.** S-M2-09.
- **Перевірка.** Р.
- **Віха.** M2 (зміна лімітів), M3 (профілі WP-14).
- **Докази WP.** WP-06 і WP-07 (main): ліміти з `LIMITS_FILE` і змінних середовища, `min(запит, hard_caps)`.
  WP-09 (гілка): `test_done_when.py::test_changing_limits_needs_no_code_change`. Для WP-02, 04, 10, 11
  (гілки) — тести лімітів із конфігурації. У e2e вже видно, що ліміти запиту діють без зміни коду:
  `limits.sandbox.wall_time_ms` задається з `JANE_E2E_SANDBOX_WALL_TIME_MS`.
- **Стан e2e.** Чекає WP-09. Профілі — WP-14 після M1.
