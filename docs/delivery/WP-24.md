їхній існуючий контракт, без вигаданого processing status. since включно, until виключно за stored_at.

## Виправлення після рев’ю R1 (guardian)

Фінальна реалізація замінює опис початкового inventory вище. ConnectionTest повертає лише health;
повна інвентаризація винесена в `POST /v1/storage-status/checks`, connections:write + Idempotency-Key,
202 Job + Location. GET jobs та cancel задокументовано; result успішного job — StorageStatus.
Помилка статистики після успішного health зберігає availability available, counts null та reason
statistics_check_failed. Unknown connection — 404 до job; replay повертає той самий job.

Файловий worker інвентаризації має cooperative stop event, який timeout/cancel встановлює та який
перевіряється перед кожним metadata record; повний scan не продовжується після timeout.
JobRunner керує concurrency, queue, retention та job_timeout; request_timeout обмежує сам probe.
Попередній slow inventory тест мав неправильний спосіб конфігурації та створював другий job;
його доказ виправлено незалежним рев’ю R2 нижче. Попередній прохід тесту сам по собі не підтверджував бюджет 1 ms.

## Виправлення після рев’ю R2 (доказ фонового виконання)

Виправлено лише тест і звіт. Бюджет задається підтримуваним limits_file у формі PlatformLimits/defaults;
тест перевіряє через реальний `/v1/info` sync_response_max_ms=1 та request_timeout_ms=5000.
Wrapper реального filesystem aggregate чекає asyncio.Event: після HTTP 202 job уже увійшов у inventory,
GET саме original Location/job_id показує running та відсутній result, event іще не відпущено.

Location/job_id до succeeded та перевіряє результат справжнього aggregate. Другий job не створюється,
штучних counts немає, тест не залежить від швидкості Windows scheduling або короткого elapsed threshold.
