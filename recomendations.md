# Jane — рекомендації щодо інструментів для агентів

**Дата:** 2026-09-27  
**До плану:** [plan.md](plan.md)  
**Агенти:** Anthropic Claude Opus 5.5 (Claude Code)

Мета — закрити типові ризики паралельної роботи: агенти лізуть у чужі файли, вигадують контракти, звітують про тести, які не запускали, і послаблюють тести, щоб ті пройшли. Пункти впорядковано за пріоритетом.

## 1. `CLAUDE.md` у корені — обов'язково

Обсяг до 60 рядків, щоб агенти його справді читали. Вміст:

- **Що це і де правда:** посилання на ТЗ і `plan.md`; пріоритет має ТЗ.
- **Команди** (з'являться після WP-01): `just check`, `just test <service>`, `docker compose -p <унікальне-ім'я> up`.
- **Мови:** документація й звіти українською; код, ідентифікатори й коміти англійською.
- **Заборони, з якими Opus найчастіше помиляється:**
  - не редагувати поза своїми шляхами WP;
  - не вигадувати поля контракту — описати потребу у звіті;
  - не послаблювати й не видаляти тести, щоб вони пройшли;
  - не мокати сам компонент, який тестуєш;
  - не зашивати ліміти в код;
  - не писати «тести зелені», не показавши їхній вивід;
  - не додавати функціональність понад свій WP.
- **Кросплатформність:** Windows і Linux, шляхи через `pathlib`, без bash-only скриптів у ключових командах.

Кожен WP додає у свій сервіс короткий `CLAUDE.md` з трьох рядків: як запустити, як протестувати, де контракт.

## 2. Хуки — найбільший виграш для паралельності

| Хук | Що робить | Навіщо |
|---|---|---|
| **PreToolUse на Edit і Write: захист власності шляхів** | Читає файл `.jane-wp` у checkout, де записані номер WP і дозволені glob-шаблони, і блокує запис поза ними | Прямо реалізує правило §3.1 плану. Без нього агенти рано чи пізно «трохи поправлять» чужий `jane-kit` або контракт |
| **PreToolUse на Bash: заборони** | Блокує `git push --force`, `git merge`/`checkout` у `main`, `docker compose down -v` без `-p` | Зливає лише координатор; агент не повинен знести томи іншого агента |
| **PostToolUse на Edit і Write: форматування** | Запускає `ruff format` + `ruff check --fix` для змінених `.py`, `prettier` для `web/` | Менше шуму в рев'ю й конфліктів через стиль |
| **Сканування секретів** | Git pre-commit з gitleaks плюс PreToolUse на `git commit` | Правило про секрети, яке перевіряється, а не лише декларується |
| **Stop: перевірка звіту (м'яко)** | Якщо `docs/delivery/WP-NN.md` немає або в ньому немає виводу команд, нагадати агентові | Проти звіту «готово» без доказів. Повний прогін тестів сюди не ставити: буде повільно й можливі цикли |

## 3. Скіли — три штуки, не більше

1. **`jane-wp`** — процес виконання WP. Прочитати свій WP, створити гілку й `.jane-wp`, пройти DoD, заповнити шаблон звіту, оновити статус. По суті, це §8 плану, перетворений на чекліст із шаблоном звіту.
2. **`jane-contracts`** — конвенції API, щоб 11 агентів писали однаково. Що скіл має описувати:
   - версіонування `/v1`;
   - модель помилок;
   - `Idempotency-Key`;
   - асинхронні job: `202`, `job_id`, стан, скасування;
   - передавання великих матеріалів за посиланням;
   - пагінацію;
   - як згенерувати мок і клієнт;
   - як перевірити зворотну сумісність (наприклад, `oasdiff`).

   Цей скіл пише WP-00 як частину свого результату.
3. **`jane-handler-package`** — як виглядає пакет обробника: маніфест, схеми, тести, походження. Він потрібен WP-05, WP-06 і особливо WP-11: асистент джерел генерує такі пакети через LLM, тож той самий опис стане основою його промптів.

Для WP-08 підходить уже встановлений скіл `sql-server-core`, його варто явно назвати в дорученні. Але там конвенції конкретного робочого середовища (AG, filegroups), тож агент має брати лише доречне для адаптера.

## 4. Субагенти (`.claude/agents/`)

- **`wp-reviewer`** — лише читання плюс Bash для запуску тестів. Промпт ставить його в роль скептика:
  - запустити команди зі звіту самому;
  - звірити критерій «Готово, коли» з ТЗ;
  - перевірити, чи тести справді перевіряють вимогу, а не мок;
  - перевірити, чи немає правок поза шляхами WP.

  Вердикт: `accepted` або нумерований список зауважень.
- **`contract-guardian`** — викликається, коли змінено `contracts/`. Перевіряє сумісність і те, що всі споживачі оновлені.

## 5. Налаштування запуску

- **Ізоляція:** кожен WP в окремому git worktree (`isolation: "worktree"`).
- **Рівень зусиль (effort):**
  - `high`: WP-00, WP-09, WP-11 і всі рев'юери;
  - `medium`: адаптери (WP-08), WP-03, WP-12.
- **Дозволи:** allowlist для `uv`, `pytest`, `ruff`, `pnpm`, `docker compose`, `git` (без push у `main`); deny на читання `.env*` і `**/secrets/**`.
- **MCP:** для WP-12 — Playwright, щоб агент сам проганяв UI-сценарії. Опційно — Context7 для актуальної документації бібліотек. Більше нічого не потрібно.
- **Координація:** хвилю 1 можна запускати як Workflow-скрипт: 11 агентів паралельно, кожен із циклом «виконання → рев'ю → виправлення». Це дорого за токенами, тож лише за явним рішенням.

## 6. Чого не додавати

- Окремий скіл на кожен WP: план і так це описує.
- Stop-хук з повним e2e: повільно, і можливі цикли.
- Велику бібліотеку промптів «на всякий випадок»: Opus 5.5 краще працює з коротким `CLAUDE.md` і чіткими заборонами, ніж з довгими інструкціями.
