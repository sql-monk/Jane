## Результат

- [Оркестратор](../../services/orchestrator/src/jane_orchestrator/runs.py) розрізняє кількість
  матеріалів, унікальних розібраних сутностей та підтверджених записів. Міграція 8 зберігає повні
  компактні ідентичності у власній БД оркестратора, у транзакції завершення елемента; читання чужих
  таблиць немає. Дублікати сутностей рахуються один раз, різні сховища — окремо. Імітація запису
  в тестовому режимі не збільшує число робочих записів.
- [Запуск](../../web/admin/src/pages/RunsPage.tsx) показує ці три числа, джерело, тривалість та
  останню зміну стану запуску або його елементів. Історичні обрізані виходи не стають вигаданими
  точними числами. Посилання використовують справжні `connection_id`, тип, область канонічного
  ключа й відкрито пояснюють, що актуальні дані можуть належати іншим запускам.
- Помилки зберігають фактичний код/тип збою обробника та trace; статус запуску не замінює їх
  загальним `upstream_conflict`. UI використовує безпечні пояснення й наступну дію зі спільного
  `ErrorBox`. Незавершений старт збору та повторна обробка RAW мають різні пояснення. Колектор
  обирається за типом зі знімка запуску; неоднозначний виконавець не підміняється випадковим.
- [Трасування](../../web/admin/src/pages/MaterialsPage.tsx) компактно показує типи виходів,
  посилання на конкретний ключ сутності та RAW-об'єкт. Великий JSON і технічні деталі згорнуті.
  Елементи запуску спочатку показують усі стани; порожня вибірка помилок пояснюється окремо.
- [Повторна обробка](../../web/admin/src/components/ReprocessForm.tsx) з рядка RAW типово надсилає
  лише його `object_ids`. Ширша вибірка явно описана й потребує підтвердження. Вибір наявного
  завдання та етапів, пошук/довантаження завдань, підключення, віджети часу і причина доступні
  до запуску. Зберігається перевірка порядку меж періоду.
- [Версії](../../web/admin/src/components/StageVersions.tsx) окремо показують погодження та
  стан тестів, включно з unknown. Відкат заблоковано, поки немає попередньої активації.
- [Огляд](../../web/admin/src/pages/DashboardPage.tsx) розрізняє групи проблем, невдалі запуски та
  невідомі матеріали. Межі вибірок пояснено; невідомі числа не видаються за нулі. Проблеми
  підтримують точний перехід `/problems?group_id=...` із журналу та захист чернетки примітки.
- [API адміністратора](../../services/orchestrator/src/jane_orchestrator/service.py) підтримує
  часові фільтри журналу `since <= at < until`, фактичні змінені значення before/after з прихованими
  секретами, а також помилку/число спроб/час повтору окремого виконавця синхронізації. `501`
  для непідтримуваного керування підключеннями відокремлено від справжніх помилок `404/405`.
  Нова спроба очищує попередню позначку unsupported, щоб вона не суперечила стану pending.

## Відомі обмеження

- У старих обрізаних трасуваннях немає повних ідентичностей: точні числа відсутні, підтверджені
  посилання залишаються. Для `entities_ref` без inline сутностей підсумок явно неповний.
- Запис `duplicate`/`stale` підтверджує існування, а не нове створення. Один канонічний запис
  у двох підключеннях — два підтверджені записи. UI не називає їх новими.
- Сховище показує поточний стан. Воно не має фільтра походження за run_id; цей фільтр не
  вигадано й глобальний результат не видається за результат лише конкретного запуску.
- Точний розмір широкої повторної обробки до виконання невідомий; UI повідомляє це до
  підтвердження. Робочий запуск із цього пакета не виконувався.
- Наявна відсутність очищення старих запусків не змінена: повні ідентичності живуть разом із
  run і видаляються каскадно при його видаленні. Нового механізму зберігання/очищення цей WP не додає.

## Неперевірені інтеграції

PostgreSQL у тестах справжній та ізольований. Колектор, runtime, registry і storage у backend
перевірках — контрактні замінники. Chromium запускає production build із контрактними mock API.
Повний сценарій на `jane-demo`, Linux CI, реальні провайдери, розгортання та GitHub main
**не перевірено на реальному сервісі виконавцем WP-30**; це наступні кроки WP-32 координатора.

## Виправлення після рев’ю 1

Незалежний reviewer виявив, що `problem_group.update` поряд із прихованими `before/after`
дублював початкові поля PATCH на верхньому рівні `details`. Примітка з фіктивним Bearer-значенням
у цій копії не приховувалася. Дублювання прибрано: подія містить лише фактичний diff через
`audit_changes`; примітка самої групи зберігається згідно з PATCH.

Додано API-регресію `test_problem_group_audit_redacts_whole_event_and_keeps_safe_changes`:
створення групи через реальне виконання з контрактним результатом unrecognized, три PATCH
(звичайна примітка → фіктивний Bearer → звичайна примітка), читання журналу через API.
Перевірка шукає фіктивне секретне значення в **усьому тексті відповіді журналу**, включно з
усіма подіями та полями. Окремі позитивні перевірки підтверджують збереження звичайних значень
і правильність before/after; секрет приховано як при записі, так і в наступному before.
