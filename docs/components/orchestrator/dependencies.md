# Залежності Orchestrator

Orchestrator обов'язково потребує лише PostgreSQL. Усі інші сервіси — виконавці, які він викликає через їхні API; набір виконавців задається конфігурацією ([configuration.md](configuration.md#виконавці)).

## Огляд

| Залежність | Обов'язковість | Протокол | Для чого |
|---|---|---|---|
| PostgreSQL | обов'язкова | драйвер `psycopg` | Конфігурація, запуски, черга елементів, аудит, ключі ідемпотентності |
| Колектор (`role: collector`) | для збору | `collector.v1` | Отримання матеріалів запуску |
| Обробник (`role: handler` або `llm`) | для етапів `handler` | `handler.v1` | Виклики пакетів обробників |
| Storage для читання (`role: storage_read`) | для повторної обробки | `storage.v1` | Читання збережених RAW |
| Registry (`role: registry`) | для активацій | `registry.v1` | Перевірка версії пакета, вибір обробника за типом пакета |
| LLM gateway (`role: llm`) | для бюджетів LLM | `llm.v1` | Синхронізація бюджетів джерел і завдань |
| Assistant (`role: assistant`) | ні | — | Лише показується в `GET /v1/executors` |

Колектори й обробники Orchestrator між собою не з'єднує: кожен виклик іде від Orchestrator до виконавця. Таблиці інших сервісів Orchestrator не читає.

## PostgreSQL

Власна база `jane_orchestrator` (DSN — `JANE_ORCHESTRATOR_DATABASE_URL`). Схема створюється й оновлюється автоматично під час старту ([міграції](operations.md#міграції)).

| Питання | Відповідь |
|---|---|
| Перевірена версія | `postgres:18` — образ dev-стеку ([infra/compose.yaml](../../../infra/compose.yaml)) і інтеграційних тестів |
| Мінімальна версія | не визначена й не перевірялася; код використовує `jsonb`, advisory-блокування, `FOR UPDATE SKIP LOCKED` |
| Права | власник схеми: міграції створюють таблиці й індекси |
| Пул з'єднань | `psycopg-pool`, розмір — `LIMITS__ENGINE__DB_POOL_MAX` (типово 10) на процес |

Поведінка за недоступності:

- **під час старту** — процес не стартує: пул чекає з'єднання, міграції не виконуються;
- **під час роботи** — `GET /v1/health` повертає перевірку `database` зі статусом помилки; запити API, яким потрібна база, завершуються помилкою; крок воркера пишеться в журнал (`worker step failed`) і повторюється через `LIMITS__ENGINE__POLL_INTERVAL_MS`. Після відновлення бази черга продовжується: незавершені елементи з простроченим lease забирає наступний воркер.

## Виконавці

Виконавця обирає Orchestrator за роллю й можливостями (`capabilities`) — правила в [internals.md](internals.md#вибір-виконавця). Помилка виклику класифікується як повторювана, якщо Problem виконавця має `retryable: true`, або (без цього поля) за відсутності відповіді чи статусу 408, 409, 425, 429, 500, 502, 503, 504.

| Виконавець | Недоступний або помиляється | Наслідок |
|---|---|---|
| Колектор | повторювана помилка | Подача матеріалів повторюється через затримку з `retries` завдання; запуск триває |
| Колектор | неповторювана помилка | Запуск `failed` з Problem виконавця |
| Колектор | виконавця не налаштовано | `503 service_unavailable` (повторювана): подача повторюється, доки запуск не перевищить `timeouts.run_timeout_ms` |
| Обробник | повторювана помилка або `failure.retryable` | Елемент `retrying` з backoff, доки є спроби `retries.max_attempts` |
| Обробник | неповторювана помилка, спроби вичерпано | Елемент `failed`; запуск триває або завершується за `on_failure` етапу |
| Обробник | не знайдено для пакета | Елемент повторюється з `service_unavailable` до вичерпання спроб |
| Storage (читання) | не налаштовано | `POST /v1/reprocessing` → `503 service_unavailable` |
| Registry | не налаштовано | Активація → `503 service_unavailable`; обробник обирається лише за `packages` або `default` |
| LLM gateway | не налаштовано | Бюджети джерел і завдань не синхронізуються (черга синхронізації не створюється) |

Підключення синхронізуються з кожним виконавцем, для якого це ввімкнено; помилки синхронізації видно в `GET /v1/connections/{connection_id}` (`sync_status: failed` з повідомленням).

## Поведінка без виконавців

- Джерела, завдання, підключення, ліміти, аудит працюють повністю.
- `POST /v1/tasks/{task_id}/runs` створює запуск; він переходить у `running`, але подача матеріалів отримує `503` і повторюється до `timeouts.run_timeout_ms` (типово 6 годин), після чого запуск `failed` з кодом `timeout`.
- `GET /v1/executors` повертає порожній список.

У dev-стеку ([infra/compose.yaml](../../../infra/compose.yaml)) сервіс `orchestrator` не має списку виконавців. Його задає локальний файл `infra/compose.local.yaml` — зразок у [compose.local.example.yaml](../../../infra/compose.local.example.yaml).
