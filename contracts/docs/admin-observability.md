# Матеріали, результати та діагностика адмінки

Довідка для додаткових полів API `/v1`. Джерела правди: [Storage OpenAPI](../openapi/storage.v1.yaml), [Orchestrator OpenAPI](../openapi/orchestrator.v1.yaml) і [контракт адаптера](storage-adapter.md). Попередні запити й обов’язкові поля не змінено; клієнти ігнорують незнайомі поля відповіді.

## Пошук результатів

Каталог показує фактично збережені типи, а не перелік потенційних виходів пакетів. Приклади GET нижче потребують звичайної автентифікації `storage:read`; секрети беруться з середовища клієнта.

```http
GET /v1/entity-types?connection_id=results-pg&limit=50
GET /v1/entities?connection_id=results-pg&entity_type=product&scope=actual-business-scope&search=Phone&limit=50
```

`search` застосовується в адаптері перед курсорною пагінацією. `%` та `_` — буквальні символи. Пошук і каталог дотримуються налаштованого `request_timeout_ms`; перевищення дає чинний Problem `timeout`. Файловий обхід припиняє читання метаданих після скасування.

`scope` визначає обробник. Не можна підставляти `source_id` замість невідомого scope. Канонічний ключ передається без розбору або повторного складання, з URL-кодуванням на рівні клієнта. Посилання запуску на connection/type/scope відкриває поточні результати цієї області; воно не обмежує записи одним запуском.

Файловий і PostgreSQL адаптери підтримують каталог та серверний пошук. Інші адаптери можуть повернути `501 not_implemented`: це відсутність можливості, а не порожнє сховище. Їхній попередній `list_entities` зберігається. Статистика RAW та необов’язкова статистика сутностей показуються окремо; відсутня кількість не дорівнює нулю.

## Підсумки запуску

`Run.source_id`, `collector_kind` походять зі знімка завдання. `updated_at` враховує активність елементів запуску. Необов’язковий `summary` має `basis=recorded_handler_outputs` і рахує унікальні сутності з зафіксованих виходів обробників; це не підрахунок усіх поточних рядків у сховищі.

| Поле | Значення |
|---|---|
| `complete=true` | Виходи цього запуску зафіксовані повністю; кількості доступні |
| `extracted_entities` | Унікальні сутності, отримані обробниками |
| `saved_records` | Фактично зафіксовані записи; імітації тестового режиму виключені |
| `result_groups` | Підтверджені тип, scope, необов’язкове підключення та кількість |
| `complete=false`, `legacy_trace=true` | Історичне трасування обрізане; точні кількості недоступні |
| `complete=false`, без `legacy_trace` | Наприклад, є `entities_ref` без inline-сутностей; відомі кількості лише нижня межа |

Записи однієї сутності у двох підключеннях рахуються окремо. Нові компактні ідентичності зберігаються незалежно від обмеження великого трасування. Старі записи не оголошуються повними заднім числом. Кількість матеріалів збору й кількості сутностей — різні показники.

## Синхронізація підключень

`ConnectionView.executors[]` може містити безпечний Problem `error`, число `attempts` і `next_retry_at`. Додатковий `unsupported_executors[]` містить виконавця та причину `managed_connections_not_supported`. Виконавець, який відповів 501, не позначається синхронізованим і не підміняється звичайною помилкою повторної спроби.

## Аудит і точна група проблем

```http
GET /v1/audit-events?subject_type=task&subject_id=shop-catalog&since=2026-10-11T00%3A00%3A00Z&until=2026-10-12T00%3A00%3A00Z&limit=50
GET /v1/problem-groups?group_id=pg_01J9ZQ4C0000000000000001&limit=50
```

Час — RFC 3339: `since` включно, `until` не включно. Ідентифікатор групи береться з реальної відповіді API. `group_id` фільтрується сервером; клієнт не завантажує весь каталог груп для пошуку одного посилання. Для наступних сторінок передається отриманий `next_cursor` як `cursor`.

Нові події змін можуть мати `details.changed`, `before`, `after`. Вкладені секретні поля та секретоподібний текст приховуються в усій події, включно з примітками. Історичний запис без різниці означає «різниця не записана», а не «нічого не змінилося». Технічний код дії збережено для старих клієнтів, а адмінка додає зрозумілу назву й посилання на об’єкт.

## Повторна обробка

Дія в рядку матеріалу типово передає тільки `stored_materials.object_ids` цього RAW. `material_ids` означає всі збережені спостереження матеріалу й потребує явного вибору та підтвердження ширшої області. Обов’язково вибираються наявне завдання й сховище; дати та точні ідентифікатори залишаються чинними полями контракту. Запуск зберігає звичайні правила `Idempotency-Key`, `202 + Job` та трасування.
