# Перевірка профілів лімітів

Стан на 2026-09-30: **лише перевірка форми JSON, без навантажувальних вимірювань**. Цільові
машини ADR-0007 поки не підтверджені людиною. Значення в `deploy/profiles/` повторюють
довідкові приклади WP-00 і не мають статусу безпечних виміряних налаштувань.

## Відтворюваний протокол для кожного середовища

1. Зафіксуйте тип хоста, ОС/версію Docker, фактичні vCPU/RAM/диск, версії образів, Git SHA,
   назву профілю, обсяг даних і всі overrides. Не записуйте паролі, токени або вміст матеріалів.
2. Розгорніть окремий стек із власними портами й томами. Для `ci` використовуйте тільки testsite
   та fake LLM. Для реальних сайтів/Telegram потрібні дозволені тестові джерела й їхні власні
   rate/flood обмеження. Не переносіть CI-частоту 50 запитів/с на зовнішній сайт.
3. Перевірте `GET /v1/limits/platform`, `/v1/info` кожного сервісу та
   `GET /v1/limits/effective` для platform/source/task/stage. Створіть окреме завдання з
   нижчим `limits` і доведіть за походженням, що нове значення діє без зміни коду. Перевірте
   `hard_caps` і що обмеження джерела не послаблюються.
4. На testsite запустіть малий smoke, потім задане навантаження каталогу й окрему перевірку цін.
   Для Telegram — контрольовану історію/нові повідомлення та повтор після перезапуску, якщо
   доступний тестовий канал. Проганяйте сценарії з різними профілями та повторюйте кожен
   після рестарту воркера. Зіставте очікувані URL і матеріали з testsite.
5. Збирайте часові ряди: CPU, RSS, диск/IO, розмір PostgreSQL і blob-сховища, глибину черги,
   кількість inflight, latency p50/p95/p99, 429/5xx, повтори, rate/flood waits, пропускну
   здатність і помилки. Запишіть метод збору метрик та інтервал; не підміняйте фактичні числа
   оцінками. Окремо перевірте заповнення черги, backpressure, kill/restart, дедуплікацію
   повторної доставки та відновлення з backup.
6. Приймайте профіль лише якщо всі контрольні сценарії завершилися коректно, немає втрат або
   дублів, ресурсний запас достатній для заданого навантаження й політика цільового джерела
   дотримана. Пороги запасу й допустимої latency потрібно погодити для реального SLA; без них
   не можна об'єктивно оголосити профіль перевіреним.

## Журнал доказів

Для кожного профілю зберігайте окремо: дату, оператора, SHA, інвентар хоста, файл профілю
та його digest, кількість повторів, конфігурацію джерела/завдання, команди запуску,
сирі метрики/логи без секретів, підсумок помилок, очікувані й фактичні результати, рішення
«прийнято/відхилено» та обґрунтування. Поки такого журналу немає, у WP-14 критерій 13
залишається **не підтвердженим**.
