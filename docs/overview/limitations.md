# Обмеження й нереалізоване

Межі поточної реалізації Jane, замінники зовнішніх сервісів у перевірках і відомі розбіжності між кодом, контрактами й ТЗ. Стан — ревізія `48389a3`; обмеження каталогу сутностей, типів і MongoDB — ревізія `118707e`. Обмеження окремого модуля описано також у його документації ([каталог модулів](../components/README.md)).

## Зовнішні сервіси та замінники

| Сервіс | Стан |
|---|---|
| Telegram | Типовий бекенд Telegram Collector — `recorded`: відтворює записані канали з файлів (`examples/telegram/recordings`). Реальний Telegram потребує бекенда `telethon` (збірка образу з `--extra telethon`) і облікового запису користувача; у цій документації не перевірявся |
| Провайдери LLM | Реалізовано провайдери `anthropic` і детермінований `fake`. Перевірки й приклади використовують `fake`; виклики Anthropic у цій документації не перевірялися |
| S3 | У dev-стеку S3 замінює SeaweedFS (`chrislusf/seaweedfs`), MinIO — збірка `pgsty/minio` стороннього постачальника; реальний AWS S3 не перевірявся |
| Автентифікація JWT | Режим `jwt` реалізовано в `jane-kit`, але dev-стек використовує `api_key`; з реальним постачальником ідентичності не перевірявся |

## Середовище виконання

- **Dev-стек** (`infra/compose.yaml`) призначений для розробки й перевірок: один вузол, порти лише на `127.0.0.1`, облікові дані генеруються локально. Готової конфігурації промислового розгортання в репозиторії немає — [розгортання](../architecture/deployment.md).
- **Зв'язування сервісів.** Базовий `infra/compose.yaml` не задає виконавців Orchestrator і адрес Registry для сервісів. Робочий ланцюжок дає `deploy/profiles/stack.py up` або локальний `infra/compose.local.yaml` за зразком `infra/compose.local.example.yaml` — [перший запуск](../getting-started/README.md).
- **Пісочниця екстракторів** потребує Docker або Podman. Handler Runtime у контейнері отримує сокет Docker хоста — це межа довіри: процес Handler Runtime може керувати контейнерами хоста. Тести ізоляції запускаються лише на Linux (`just isolation`).
- **Спільні файли.** Посилання `file://` на збережені RAW працюють лише на одному вузлі зі спільним томом Storage.
- **Стан без бази.** Handler Runtime і Assistant без `STATE_DSN` тримають стан у пам'яті: він втрачається після перезапуску й придатний лише для одного екземпляра.
- **Рендеринг JavaScript** у Web Collector (`fetch.render_js`) потребує образу з Playwright (`--extra render`).

## Функції, яких немає або які обмежені

- **Стратегія `llm_explore`** у правилах колектора зарезервована: Web Collector її не виконує. Дослідження нового джерела за допомогою LLM виконує Assistant.
- **Секрети `vault:`** допускає схема підключення, але обидва механізми розв'язання секретів у `jane-kit` їх відхиляють; підтримуються `env:` і `file:`.
- **Мережа для екстракторів.** Handler Runtime відхиляє пакет, маніфест якого вимагає `access.network` інше, ніж `none`.
- **Каталог, пошук і статистика сутностей** Storage є лише в адаптерів `filesystem`, `postgresql` і `mongodb`. Для `sqlserver`, `s3` і `minio` каталог і пошук відповідають `501 not_implemented`, а статистика — `null` — [Storage: читання](../components/storage/integration.md#читання-результатів).
- **Зміна типу сутності** не переносить дані: якщо розділ сайту віднесено до іншого типу, наступний збір створює нову сутність в іншій колекції — [ADR-0011](../adr/0011-data-placement.md).
- **MongoDB dev-стеку без окремої ролі.** Storage під'єднується до MongoDB кореневим користувачем стеку, а не роллю з правами лише на базу `jane_results`.
- **Частковий запуск.** Запуск із невдалими елементами етапу, який має `on_failure: continue`, завершується станом `succeeded`; окремого стану «частково виконано» немає — невдачі видно в лічильниках етапів і групах проблем.
- **Профілі лімітів** `dev-laptop`, `ci`, `single-node` описують типові середовища; стенд для їх вимірювання — `deploy/profiles` (`check.py`, `harness/`). У цій документації профілі не вимірювалися; для іншого середовища значення потрібно перевірити.

## Розбіжності з ТЗ і контрактами

| Тема | Що в коді | Джерело |
|---|---|---|
| Режим автентифікації | Типове значення в коді — `auth_mode=none`: без налаштування сервіс приймає будь-який запит, але лише на loopback-адресі. Dev-стек вмикає `api_key` змінними середовища | `libs/jane-kit/src/jane_kit/auth.py` |
| Стан колекторів | [Карта власності даних](../../contracts/docs/data-ownership.md) згадує PostgreSQL `jane_web_collector` для кількох екземплярів Web Collector; у налаштуваннях колекторів є лише SQLite у `state_dir`, а такої бази dev-стек не створює | `services/web-collector/src/jane_web_collector/settings.py` |
| Стан Handler Runtime | Карта власності даних згадує SQLite; код підтримує PostgreSQL (`STATE_DSN`) або пам'ять | `services/handler-runtime/src/jane_handler_runtime/state.py` |
| Код `upstream_conflict` | Orchestrator позначає ним помилку виклику з HTTP 502; [модель помилок](../../contracts/docs/errors.md) визначає його як 409 для злиття форків | `services/orchestrator/src/jane_orchestrator/engine.py` |
| `schedule.overlap: queue` | Окремо не обробляється: запуск створюється в черзі й чекає завершення активного, як за `allowed = 1` | `services/orchestrator/src/jane_orchestrator/engine.py` |
| Ключ доставки | Код будує `item_key` як `<upstream item_id>#<stage_id>#<edge index>`; схема `handler-invocation` рекомендує `<upstream invocation_id>/<index>` | `services/orchestrator/src/jane_orchestrator/routing.py` |
| Дослідження джерела LLM | ТЗ §6 перелічує його серед способів пошуку матеріалів колектора; реалізовано як сценарій Assistant, а не стратегію колектора | `services/web-collector/src/jane_web_collector/discovery/registry.py` |
